# Пучки связей МТС

> **Статус:** **historical accepted semantics МТС v0.2**, сохраняемая для совместимости и воспроизводимости.
>
> Этот документ **не является универсальной семантикой Foundation v2**. В частности, set-like схлопывание уже разрешённых значений, старые `◁/▷` context projections и другие v0.2 конструкции не переносятся в exact-occurrence Foundation v2 автоматически. Если пучки войдут в следующую версию, их semantics должна быть заново выведена и проверена поверх exact occurrence identity.
>
> Для текущей модели начинайте с [Оснований МТС](Основания%20МТС.md) и [Формальной нотации МТС](../specs/Формальная%20нотация%20МТС.md).

## 1. Зачем нужен пучок

Одна связь выражает одно отношение двух полюсов. Но часто требуется говорить не об одной связи, а сразу о некоторой совокупности уже различённых связей: например, о нескольких допустимых концах, обо всех связях с данным началом или о результате раскрытия двух совокупностей полюсов.

Для этого historical МТС v0.2 использует фигурную запись:

```text
{a, b, c}
```

В v0.2 эта запись имеет **две статически различимые роли**:

1. **пучок условий** — совместное предъявление нескольких локальных суждений;
2. **пучок значений** — плоская совокупность разрешённых связей.

Одинаковый внешний знак не означает одну и ту же семантическую категорию. Роль определяется из формы выражения **до интерпретации**, а не угадывается по содержимому памяти.

## 2. Пучок условий

Пучок условий использовался в корневых формулах v0.2:

```text
∞ : {◁ = ∞, ▷ = ∞}
(=) : {♀◁ = ♀▷, ◁♂ = ▷♂}
```

Здесь фигурные скобки означают совместное выполнение нескольких условий в одном локальном контексте. Такой пучок не является самостоятельным множеством связей.

Пустой пучок условий

```text
{}
```

не предъявляет ни одного дополнительного условия и потому успешно выполняется без какого-либо действия.

> Для Foundation v2 эти две формулы являются частью historical accepted root program, а не текущим определением `K` или local `=`.

## 3. Пучок значений

Если элементы фигурной записи являются формами связей, а не суждениями, запись в v0.2 может обозначать **плоский пучок значений**:

```text
{a, b}
```

Каждое вхождение такого пучка сначала разрешается независимо. Только после этого полученные связи рассматриваются как единое значение-пучок.

Это существенно: запись сохраняет историю отдельных вхождений, но historical v0.2 смысл пучка определяется не их текстом и не порядком записи, а тем, **какие связи были получены после разрешения**.

Отсюда для уже разрешённых связей в v0.2 следует множественный характер плоского пучка:

```text
{a, b} = {b, a}
{a, a} = {a}
```

если соответствующие вхождения действительно разрешены в одни и те же связи.

### Foundation-v2 boundary

Exact-occurrence substrate допускает два разных occurrences одной пары:

```text
P1 = A ⟼ B
P2 = A ⟼ B
P1 ≠ P2
```

Поэтому выражение «одни и те же связи» в будущей Foundation-v2 версии должно быть формализовано особенно строго. Historical set-like bundle equality нельзя использовать как скрытый способ уничтожить multiplicity/provenance exact сети.

## 4. Почему нельзя схлопывать одинаковые знаки заранее

Особенно важно различать одинаковую запись и одинаковую связь.

Например:

```text
{[], []}
```

содержит два независимых historical v0.2 вхождения `[]`. Они не становятся одним элементом только потому, что выглядят одинаково.

В одном контексте они могут разрешиться в одну и ту же связь, в другом — в разные. Поэтому утверждение

```text
{[], []} = {[]}
```

**не является безусловной аксиомой МТС**.

Оно истинно только в рамках принятой v0.2 bundle semantics после независимого разрешения в один и тот же набор связей.

Таким образом уже historical модель фиксировала важную идею:

```text
одинаковая запись ≠ одинаковая сущность
```

Foundation v2 усиливает эту границу до exact occurrence identity.

## 5. Пучок и одиночная связь — разные виды значения

В historical v0.2 пучок из одной связи не отождествляется автоматически с самой связью:

```text
{a} != a
```

Даже если внутри пучка находится только одна разрешённая связь, пучок остаётся значением другого рода в этой версии языка.

Это historical typed-value различение не объявляется новым онтологическим типом `Link` Foundation v2. При re-derivation пучков их роль должна быть выражена сетью/evidence без скрытого semantic tag в примитивной связи.

## 6. Плоский характер v0.2

В принятой версии v0.2 пучок значений **плоский**.

Смысл вложенных пучков не определяется:

```text
{{a, b}}
```

Поэтому вложенный пучок значений в v0.2 отвергается как неопределённая форма.

Foundation v2 пока не принимает иной вариант автоматически.

## 7. Раскрытие пучка

Historical v0.2 позволяет использовать пучок как множество допустимых полюсов связи.

Например:

```text
a{b, c}
```

означает: выбрать среди **уже существующих** связей те, начало которых соответствует `a`, а конец принадлежит разрешённому пучку `{b, c}`.

Аналогично:

```text
{a, b}c
{a, b}{c, d}
```

выбирают существующие связи по допустимым множествам первого и второго полюсов.

## 8. Особый смысл пустого пучка в позиции раскрытия

Как самостоятельное historical v0.2 значение пустой пучок является пустым множеством:

```text
{}
```

Но в статически известной позиции полюса раскрытия пустой пучок означает отсутствие ограничения на этот полюс:

```text
a{}   — все существующие связи с началом a
{}b   — все существующие связи с концом b
{}{}  — все существующие связи рассматриваемой памяти
```

Эта convention относится к v0.2 query language и не является primitive wildcard semantics Foundation v2.

## 9. Раскрытие ничего не создаёт

Это положение сохраняет ценность и для Foundation v2:

```text
интерпретация ≠ материализация
```

Historical bundle expansion является операцией чтения. Если связи нет, раскрытие не создаёт её автоматически.

```text
раскрытие ≠ создание
раскрытие ≠ удаление
```

Именно эта граница сегодня обобщена в архитектуре апамяти как:

```text
find / read / replay != materialize / delete
```

См. [Апамять и управление сетью связей](../specs/Апамять%20и%20управление%20сетью%20связей.md).

## 10. Что v0.2 намеренно не определяет

Для плоских пучков значений v0.2 не принимаются без отдельной теории:

- вложенные пучки значений;
- определение имени непосредственно через непустой пучок значений;
- автоматическое распространение `⟼`, `♀`, `♂`, `¬` на пучок;
- создание отсутствующих связей при раскрытии;
- удаление связей через пустой пучок;
- глобальное переписывание равенств пучков.

Foundation v2 не снимает эти ограничения молча.

## 11. Связь с historical корневой системой

Принятие пучков значений в v0.2 **не изменяло десять historical корневых определений МТС**.

Фигурные скобки, присутствующие в определениях `∞` и `(=)`, играли роль пучков условий. Пучок значений появлялся только там, где статическая форма выражения требовала значения, а не совокупности суждений.

Сегодня эта система сохраняется как reproducible accepted history.

Текущая Foundation-v2 линия не обязана наследовать её host/static categories. Перед включением пучков в следующую версию требуется отдельное решение, которое ответит как минимум на вопросы:

```text
что является exact identity bundle artifact?
сохраняется ли multiplicity?
что означает equality пучков при duplicate occurrences?
как bundle query выражается через апамять?
является ли wildcard explicit form/evidence?
как отделено read от materialize?
```

До такого решения этот документ следует читать именно как **спецификацию исторически принятой v0.2 возможности**, а не как недостающую часть уже принятой Foundation v2.
