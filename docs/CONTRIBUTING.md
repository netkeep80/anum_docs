# Руководство по вкладу

Изменения активного ядра вносятся через запрос на слияние.

## Канонические области

| Содержимое | Каталог |
|---|---|
| текущее ядро на `TypeScript` | `ts/src/` |
| исполнимые проверки соответствия и выпуска | `ts/test/` |
| браузерная интеграция | `ts/browser/` |
| версионированные машинные контракты | `contracts/` |
| свидетельство принятия выпуска | `cutover/` |
| нормативная теория | `docs/theory/` |
| технические спецификации | `docs/specs/` |
| ненормативные исследования | `docs/research/` |

Исторические варианты не сохраняются рядом с current surface: история находится в Git, задачах и запросах на слияние.

## Язык канонического изложения

Теория МТС, определения и нормативная документация излагаются **по-русски**. Английское написание сохраняется только для буквальных имён программных сущностей, протоколов, файлов и полей, например `LinkHandle`, `ReadMemory`, `schema`.

Новый теоретический термин сначала определяется по-русски и только затем при необходимости получает программное имя.

## Текущая модель

Уровни должны оставаться разделены:

```text
L0 — онтология
L1 — семантическая модель
L2 — формальный язык
L3 — сериализация
L4 — исполнение
L5 — теория вывода
```

Одинаковый видимый знак на разных уровнях не получает тождество смысла автоматически.

Критические границы:

```text
смысловая связь != технический идентификатор
смысловая связь != вхождение / позиция / история
представление != интерпретация
читать / искать / проверять / replay != materialize / write
не найдено != не существует
```

## Разработка МТС через контракты

Главное направление зависимости:

```text
нормативная теория
      ↓
кандидатный контракт
      ↓
корпус соответствия + отрицательные векторы
      ↓
проверка на опровержение
      ↓
эталонная реализация
      ↓
независимая / дифференциальная проверка
      ↓
явное принятие
      ↓
текущий принятый контракт
```

Реализация является свидетельством реализуемости, а не источником теории.

Неверно:

```text
реализация делает X
=> МТС означает X
```

Правильно:

```text
теория задаёт X
контракт фиксирует наблюдаемое X
реализация воплощает X
```

## Обязательная синхронизация документации

README и нормативная теория являются частью результата semantic work, а не последующим необязательным отчётом.

Для изменения смысловой или contract boundary обязательна последовательность:

```text
semantic decision
→ reconciliation нормативной теории
→ candidate contract / conformance
→ implementation
→ docs:sync
→ docs:check
→ full CI + repo-guard
→ explicit acceptance
```

Команды:

```bash
npm --prefix ts run docs:sync
npm --prefix ts run docs:check
```

`docs:sync` **не выводит теорию из TypeScript-кода**. Он обновляет только ограниченный автоматически помеченный блок, построенный из current/previous machine contract state.

Содержательная теория вне этого блока изменяется человеком или исследовательским агентом только как явное смысловое решение.

`docs:check` пересчитывает ожидаемую проекцию и падает, если:

- marker отсутствует или продублирован;
- current/previous release устарели;
- F1 registry расходится с current contract;
- root/effect/carrier facts расходятся с current contract.

Проверка входит в обычный `npm run check`, поэтому stale current-state documentation блокирует CI.

Кроме этого, `repo-guard` требует совместного изменения README и обеих нормативных теорий при любом изменении versioned contract/conformance/acceptance surface. Таким образом semantic release нельзя принять с документацией предыдущей версии.

Для implementation-only refactor без observable semantic delta бессодержательный theory diff не требуется: `docs:check` всё равно доказывает, что current machine projection остаётся актуальной.

## Иерархия источников истины

1. **Нормативная теория** отвечает «что это означает?».
2. **Принятый машинный контракт** фиксирует переносимую наблюдаемую проекцию принятой теории.
3. **Корпус соответствия** делает эту границу проверяемой.
4. **Эталонная реализация** демонстрирует реализацию контракта.
5. **Независимые потребители** совпадают по observables, а не по внутренней архитектуре.
6. **Git, issues и PR** хранят процесс исследования и историю решений.

Если эти уровни расходятся, расхождение является defect. Нельзя автоматически выбрать runtime behavior как победившую семантику.

## Минимальная наблюдаемая граница

Контракт фиксирует только то, от чего зависит смысл или совместимость:

- семантическую роль входа;
- детерминированный наблюдаемый результат;
- переносимую категорию ошибки;
- границу чтения и эффекта;
- инварианты смыслового тождества;
- канонизацию;
- versioned surface relations;
- обязательные отрицательные векторы.

Без отдельной причины контракт не фиксирует:

- runtime pointer/object identity;
- локальный slot/ID;
- allocation order;
- устройство классов;
- кэш/индекс;
- traceback text;
- UI representation.

## Контракт и корпус соответствия

Для фундаментального инварианта желательно иметь три согласованных формы:

```text
1. русское нормативное определение
2. машиночитаемый invariant в contract
3. executable positive/negative conformance
```

Отрицательные векторы являются first-class частью release boundary.

## Проверка на опровержение

Challenge должен искать способ сломать candidate semantics, а не только подтвердить happy path.

Проверяются, где применимо:

- контрпримеры и малые конечные модели;
- циклы и самоссылки;
- атаки на тождество и псевдонимы;
- некорректные входы;
- read→write leakage;
- переименования и эквивалентные написания;
- межъязыковые неоднозначности.

## Жизненный цикл

```text
Research
→ Problem
→ Candidate
→ Challenged
→ Modeled
→ Accepted
→ Released
```

До `Accepted` кандидат остаётся экспериментальным, даже если его код и тесты зелёные.

## Критерии принятия

Перед фундаментальным acceptance проверяется:

- [ ] проблема сформулирована независимо от реализации;
- [ ] нормативная семантика определена;
- [ ] contract минимален и implementation-neutral;
- [ ] positive и negative corpus достаточны;
- [ ] циклы/self-reference проверены;
- [ ] technical identity не просочилась в semantics;
- [ ] read/effect boundary явна;
- [ ] malformed input fail-closed;
- [ ] reference model executable;
- [ ] independent/differential check есть там, где существенно;
- [ ] **теория, README, contract и conformance согласованы**;
- [ ] `docs:check` green;
- [ ] известен consumer/cutover plan;
- [ ] выполнено explicit owner acceptance;
- [ ] obsolete live semantics удаляется без compatibility mode.

## Версионирование

Version bump требуется при изменении принятой observable machine boundary либо current composition, требующей repin потребителя.

Не требуется автоматически для:

- внутреннего refactor;
- оптимизации;
- нового индекса/кэша;
- docs clarification без semantic delta;
- новых negative tests, которые только усиливают проверку уже действующего требования.

Неоднозначный старый accepted contract нельзя молча переписать с изменением результата.

## Доверенное ядро

Предпочтительная схема:

```text
поиск / эвристики / UI / оптимизация
        = недоверенный производитель

переносимое свидетельство
        ↓
маленький checker / replay
        = доверенный потребитель
```

## После принятия

1. потребители переводятся на новый канонический путь;
2. current contract/conformance/acceptance pointers обновляются явно;
3. `docs:sync` обновляет current-state projection;
4. содержательная теория уже должна отражать принятое решение;
5. устаревшая активная реализация удаляется после миграции;
6. история остаётся в Git, а не в compatibility directories.

## Проверка

Полный локальный gate:

```bash
npm --prefix ts ci
npm --prefix ts run check
```

Отдельно полезно проверить идемпотентность документации:

```bash
npm --prefix ts run docs:sync
npm --prefix ts run docs:check
```

Полный CI дополнительно выполняет repo structure checks и запрет на возвращение Python runtime. Кодировка текстовых файлов — UTF-8.

Защищённый файл `docs/research/Исходные мысли МТС.md` изменяется только владельцем репозитория.
