# Руководство по вкладу

Изменения активного ядра вносятся через запрос на слияние (PR).

## Канонические области

| Содержимое | Каталог |
|---|---|
| текущее TypeScript-ядро и публичная consumer-граница | `ts/src/` |
| исполнимые проверки соответствия и release gates | `ts/test/` |
| browser-интеграция общего semantic core | `ts/browser/` |
| версионированные внешние контракты | `contracts/` |
| текущее свидетельство принятия выпуска | `cutover/` |
| нормативная теория | `docs/theory/` |
| технические спецификации | `docs/specs/` |
| ненормативные исходные заметки | `docs/research/` |

Каждый активный документ должен иметь уникальную роль, а каждая функция — одну активную реализацию. Исторические варианты не сохраняются в `archive`, `legacy`, `old` или аналогичных каталогах: история уже находится в Git.

## Язык канонического изложения

Теория МТС, определения понятий, пояснения и нормативная документация излагаются **по-русски**.

Предпочтительные термины:

```text
reference model        → эталонная модель
graph carrier          → графовый носитель
identity               → тождество / идентификатор — по смыслу
occurrence             → вхождение
glyph                  → знак
metavariable           → метапеременная
runtime                → исполнение / среда исполнения
pattern                → образец
consumer               → потребитель
canonical path         → канонический путь
read-only              → только чтение
```

Английское написание сохраняется, когда речь идёт именно о буквальном имени программной сущности или внешнего протокола: например `LinkRef`, `ContextFrame`, `MemoryView`, имя функции, поле JSON, имя файла, значение `schema` или статус машинного контракта. В таком случае русское понятие должно оставаться основным в окружающем тексте.

Нельзя вводить новый теоретический термин только потому, что такое английское имя удобно в реализации. Сначала определяется русское понятие МТС, затем при необходимости указывается его программное представление.

## Текущая модель и уровни

Машинную границу текущего принятого выпуска задают [контракт `mts-contract/v0.8`](../contracts/mts-contract-v0.8.json) и [корпус соответствия `mts-conformance/v0.8`](../contracts/mts-conformance-v0.8.json). V0.8 меняет владельца и композицию текущего выпуска, но сохраняет принятую наблюдаемую семантику v0.7: `semanticBase = mts-contract/v0.7`, `observableSemanticDelta = false`.

Единственная текущая реализация — TypeScript-пакет `@mts/core`; рекомендуемая consumer-граница — package root, собираемый из `ts/src/public.ts`. Контракт и корпус v0.7 остаются неизменяемым свидетельством предыдущего выпуска. Python runtime, test-only oracle и режим совместимости удалены из активного дерева; история межъязыковой миграции остаётся в Git. Теоретические основания и формальная нотация задаются активными документами `docs/theory/` и `docs/specs/`.

Изменение одного уровня не должно скрыто менять другой:

```text
L0 — онтология
L1 — семантическая модель
L2 — формальный язык
L3 — сериализация
L4 — исполнение
L5 — теория вывода
```

Если одинаковый видимый знак используется на нескольких уровнях, тождество его денотаций должно быть задано отдельным явным правилом.

Для текущего L2 дополнительно зафиксировано:

```text
◁/▷ — атомарные контекстные местоимения;
↑ — отдельный подъём к внешнему контексту;
[`[`, `]`] не перегружаются контекстной нотацией;
[] — анонимная форма, локальная для конкретного вхождения;
interpret — операция только чтения;
realize — отдельная операция изменения памяти.
```

Для L3 текущий канонический путь — `anum-deserialization/v0.4`: алфавит состоит ровно из `[`, `]`, `1`, `0`; корень не является пятым абитом; пустой поток и пустая группа десериализуются в корень. Семантическая связь определяется своими упорядоченными полюсами, а технический идентификатор записи не создаёт дополнительного тождества связи.

Имена `interpret` и `realize` в этом фрагменте оставлены как буквальные имена машинного интерфейса; теоретическое различие формулируется по-русски как «интерпретация не является материализацией».

## Разработка МТС через контракты

МТС развивается через явное разделение смысла, машинной границы и реализации. Для связи с программной литературой используются следующие буквальные обозначения:

```text
candidate contract       → кандидатный контракт
conformance corpus       → корпус соответствия
negative vectors         → отрицательные векторы
challenge                → проверка на опровержение
reference implementation → эталонная реализация
explicit acceptance      → явное принятие
```

Рабочая последовательность:

```text
нормативная теория
      ↓
кандидатный контракт
      ↓
корпус соответствия + отрицательные векторы
      ↓
проверка на опровержение
      ↓
эталонная реализация
      ↓
независимая / дифференциальная проверка
      ↓
явное принятие
      ↓
текущий принятый контракт
```

Эта последовательность не означает, что любой шаг обязан создавать новый JSON-файл. Постоянный машинный артефакт добавляется только тогда, когда у него есть текущая нормативная роль или реальный потребитель.

### Иерархия источников истины

Роли источников должны быть различены явно.

1. **Нормативная теория** отвечает на вопрос «что это означает?». Она не обязана повторять структуру классов, модулей или хранилища конкретной реализации.
2. **Принятый машинный контракт** является машиночитаемой проекцией принятой теории на наблюдаемую границу. Он задаёт обязательные входы, результаты, эффекты, запреты и версионируемые поверхности.
3. **Корпус соответствия** делает контракт проверяемым через переносимые положительные и отрицательные примеры.
4. **Эталонная реализация** является свидетельством реализуемости контракта, но не источником смысла МТС.
5. **Независимые потребители** могут иметь другую архитектуру и обязаны совпадать по принятой наблюдаемой семантике, а не по внутреннему устройству эталонного кода.
6. **Git, задачи и запросы на слияние** хранят исследование, отклонённые варианты, обоснования проверок и историю переходов. Основная ветка хранит текущее состояние, а не процесс его получения.

Нельзя выводить теорию из случайного поведения реализации:

```text
реализация делает X
=> МТС означает X          # неверно
```

Правильное направление зависимости:

```text
теория / принятое решение задаёт X
контракт фиксирует наблюдаемое X
реализация воплощает X
```

### Минимальная наблюдаемая граница

Контракт фиксирует только то, от чего действительно зависит смысл или совместимость:

- семантическую роль входа;
- детерминированный наблюдаемый результат;
- переносимую категорию ошибки или отказа;
- границу чтения и эффекта;
- инварианты смыслового тождества;
- требования канонизации;
- отношение версионируемых поверхностей;
- обязательные отрицательные векторы запрета.

Без отдельного обоснования контракт не должен фиксировать:

- указатель или тождество объекта среды исполнения;
- локальный технический идентификатор;
- порядок выделения памяти;
- устройство дата-классов конкретного языка;
- разбиение по классам и модулям;
- внутренние кэши и индексы;
- текст трассировки исключения;
- случайный порядок обхода;
- идентификатор линии хранения;
- представление пользовательского интерфейса.

Особенно важно не возвращать техническое тождество в смысловую модель: разные координаты хранения или исполнения сами по себе не создают разные смысловые связи.

### Контракт и корпус соответствия образуют пару

Контракт без корпуса соответствия недостаточен: он задаёт норму, но не обеспечивает воспроизводимой проверки. Корпус соответствия без контракта также недостаточен: набор тестовых примеров не объясняет, что именно считается нормой.

Для фундаментального инварианта желательно иметь три согласованных представления:

```text
1. русское нормативное определение
2. машиночитаемый инвариант в контракте
3. исполнимые положительные и отрицательные проверки соответствия
```

Расхождение этих трёх представлений считается дефектом. Текущее поведение кода не используется как автоматический способ разрешить расхождение.

Отрицательные векторы являются частью границы выпуска наравне с положительными примерами. Для корневого тождества проверяются не только повторное получение `R ⟼ R` и переиспользование одной пары полюсов, но и запрет второго полностью самозамкнутого смыслового корня, дубликата той же пары и различения только по техническому идентификатору.

### Проверка на опровержение отличается от обычного модульного теста

Обычный модульный тест чаще подтверждает известное требование реализации. Проверка на опровержение целенаправленно ищет способ сломать кандидатную семантику.

Для фундаментальных кандидатов проверяются, где применимо:

- контрпримеры и малые конечные модели;
- циклы и самоссылки;
- атаки на тождество и псевдонимы;
- некорректные входные данные;
- утечка из чтения в изменение;
- эквивалентные написания и переименования;
- неоднозначности между языками и реализациями.

Проверка на опровержение может предшествовать формальному кандидатному контракту, если смысл ещё недостаточно ясен. Разработка через контракты не должна превращаться в бюрократию, преждевременно замораживающую слабую модель.

## Жизненный цикл фундаментального решения

Изменение онтологии, эталонной семантики, формальной нотации, базового протокола или доверенных правил доказательства не должно попадать прямо из исследовательской заметки в нормативное ядро.

Машинные статусы жизненного цикла сохраняются в принятом написании:

```text
Research
→ Problem
→ Candidate
→ Challenged
→ Modeled
→ Accepted
→ Released
```

В русском тексте им соответствуют этапы исследования, постановки проблемы, кандидата, проверки, моделирования, принятия и выпуска.

- `Research`: идея или наблюдение ещё не обязаны менять принятую семантику.
- `Problem`: противоречие или недостаток текущей модели формулируется независимо от реализации.
- `Candidate`: определена минимальная предполагаемая наблюдаемая граница либо достаточно точная семантическая гипотеза для проверки на опровержение.
- `Challenged`: кандидат прошёл необходимые попытки опровержения.
- `Modeled`: минимум одна эталонная реализация исполняет кандидат; для доверенной границы по возможности существует независимая проверка или повторное исполнение.
- `Accepted`: владелец теории явно принимает смысловое решение. Зелёные тесты сами по себе не являются принятием.
- `Released`: текущие указатели и привязки потребителей обновлены, а устаревшая активная семантика удалена после миграции.

До `Accepted` кандидат имеет экспериментальный статус, даже если для него уже существует код или тестовая модель.

Состояния `Rejected`, `Deferred` и `Superseded` не требуют сохранения старой реализации в рабочем дереве: история решения остаётся в Git и GitHub.

### Критерии принятия

Для фундаментального кандидата перед принятием проверяется:

- [ ] проблема сформулирована независимо от реализации;
- [ ] нормативная семантика определена;
- [ ] кандидатный контракт минимален и не зависит от устройства реализации;
- [ ] положительный корпус покрывает необходимые наблюдаемые результаты;
- [ ] отрицательный корпус покрывает критические запреты;
- [ ] циклы и самоссылки проверены там, где это существенно;
- [ ] техническое тождество не просочилось в семантику;
- [ ] граница чтения и эффекта задана явно;
- [ ] некорректные входные данные отклоняются закрыто и предсказуемо;
- [ ] существует исполнимая эталонная модель;
- [ ] независимая или дифференциальная проверка существует там, где она существенно уменьшает доверенную границу;
- [ ] документация, контракт и корпус соответствия согласованы;
- [ ] известен план миграции потребителей;
- [ ] выполнено явное принятие владельцем теории;
- [ ] устаревшая активная семантика удаляется после миграции без режима совместимости.

## Версионирование контрактов

Версия принятой машинной границы меняется, когда меняется наблюдаемая принятая семантика либо состав текущего выпуска так, что потребитель должен перепривязаться к новой версии.

Автоматическая смена версии не требуется для:

- внутреннего рефакторинга;
- оптимизации производительности;
- нового индекса или кэша;
- уточнения документации без наблюдаемого изменения;
- новых отрицательных тестов, которые только выявляют уже действующее требование.

Если старый принятый контракт оказался неоднозначным, нельзя молча переписать его так, чтобы менялся наблюдаемый результат. Нужно явно решить, является ли это исправлением уже принятой границы или новой смысловой версией.

Дочерняя поверхность может сохранить собственную версию при смене владельца реализации, если её наблюдаемая семантика не меняется. Сводный текущий выпуск может потребовать новой версии из-за нового принятого состава или перехода.

## Межъязыковое соответствие

Переносимый корпус должен по возможности исполняться текущей и независимыми реализациями. Во время миграции Python → TypeScript это выполнялось дифференциально; после принятого M13 cutover Python oracle удалён из активного дерева, а доказательная история сохранена Git.

Для будущей независимой реализации схема остаётся такой:

```text
portable fixture
   ├── @mts/core (TypeScript)
   └── independent implementation
            ↓
   normalized observable result
```

Нормализация не должна зависеть от тождества объектов среды исполнения.

Для сетей связей топология сравнивается с точностью до переименования технических ссылок. Корень различается структурно. Повтор одной смысловой пары не получает новое тождество из порядка выделения памяти. Позиция и происхождение сохраняются отдельной связевой структурой там, где они входят в семантику.

Для ошибок сравниваются переносимые категории ошибок и отказов, а не имена исключений языка или буквальный текст трассировки.

## Доверенное ядро и внешние инструменты

Контракт должен помогать уменьшать доверенную границу.

Предпочтительная схема для сложного поиска:

```text
search / heuristics / UI / optimization
        = недоверенный производитель

portable evidence
        ↓
small checker / replay
        = доверенный потребитель
```

Это не требует автоматически вводить отдельный объект передачи данных для каждого шага. Свидетельство может быть обычной корневой связевой структурой с явным словарём ролей и структурным чтением, если этого достаточно для независимой проверки.

## Принятие без копий совместимости

После принятия фундаментального кандидата:

1. все потребители переводятся на новый канонический путь;
2. версионированный машинный контракт обновляется, если изменилась принятая граница;
3. кандидатная или устаревшая реализация удаляется в том же запросе миграции либо сразу после перехода последнего потребителя;
4. CI запрещает возвращение параллельной активной реализации;
5. история остаётся в Git, задачах и запросах на слияние, а не в каталогах совместимости и новых постоянных плановых JSON-файлах.

Старые варианты доступны через историю Git и не должны участвовать в исполняемой системе.

## Ограничения

Изменение существующей теории, нотации, формата, эталонной модели или корневой формулы должно выполняться отдельной задачей. Рефакторинг не должен вводить новый анализатор, доказатель, интерпретатор, слой совместимости или нормативный документ без самостоятельного обоснования.

Зелёные тесты подтверждают реализацию текущих требований, но не принимают новую фундаментальную семантику автоматически.

Защищённый файл `docs/research/Исходные мысли МТС.md` изменяется только владельцем репозитория.

## Проверка

```bash
cd ts
npm ci
npm run typecheck
npm test
npm run browser:check
```

Полный CI дополнительно выполняет структурные и документационные проверки и отдельный no-Python veto. Кодировка текстовых файлов — UTF-8. Пользовательские ошибки должны проверяться явно.
