# Руководство по вкладу

Изменения активного дерева вносятся через запрос на слияние и проходят обязательные CI и repo-guard.

Главный принцип репозитория:

```text
main = current state
Git / closed Issues / closed PRs = history
ONE topic -> ONE active owner
```

История исследования не копируется в новые Markdown-файлы только потому, что она была полезна в процессе. Новый документ добавляется лишь тогда, когда он является отдельной актуальной нормативной или технической поверхностью.

Этот файл — единственный текущий владелец процесса разработки, проверки, принятия и публикации версий МТС. Он описывает методику, но не определяет семантику МТС.

## Канонические области

| Содержимое | Каталог |
|---|---|
| текущее ядро TypeScript | `ts/src/` |
| исполнимые проверки | `ts/test/` |
| браузерная интеграция | `ts/browser/` |
| версионированные машинные контракты | `contracts/` |
| свидетельства принятия | `cutover/` |
| нормативная теория | `docs/theory/` |
| актуальные технические спецификации | `docs/specs/` |
| первичный авторский исследовательский источник | `docs/research/Исходные мысли МТС.md` |

`docs/research/Исходные мысли МТС.md` защищён: он изменяется только владельцем репозитория. Автоматизированный запрос на слияние не редактирует и не удаляет этот файл.

Промежуточные исследовательские заметки, планы реализации, документы передачи контекста и альтернативные архитектурные проекции не сохраняются в активном дереве; для них используются задачи, обсуждение запросов на слияние и история Git.

## Первичный язык фундамента

При изложении основания порядок представлений обязателен:

```text
1. остенсивная форма МТС: ∞ / ♂e / b♀ / b⟼e
2. структурное уравнение
3. machine/reference representation, например Link(start,end)
```

Вторичная нотация языка реализации не должна вытеснять остенсивные формы. Одинаковый видимый знак на разных уровнях не получает одинаковый смысл автоматически: исходный знак, словарная запись, смысловое употребление и корневой абит необходимо различать.

## Иерархия источников истины

1. Нормативная теория определяет принятый смысл.
2. Принятый машинный контракт фиксирует переносимую наблюдаемую проекцию.
3. Корпус соответствия делает границу проверяемой.
4. Эталонная реализация свидетельствует реализуемость.
5. Git, задачи и запросы на слияние хранят исследовательскую историю.

Реализация не является источником семантики:

```text
реализация делает X
!=
МТС означает X
```

Но и машинный контракт сам по себе не создаёт реализованное поведение:

```text
в контракте записано X
!=
ядро доказанно реализует X
```

Для непринятого кандидата задача жизненного цикла или фундамента может зафиксировать, что его контракт требует ограниченной коррекции. До явного принятия такой кандидат не переписывает принятую теорию.

## Состояния изменения

В процессе разработки необходимо различать шесть состояний, которые нельзя сворачивать в одно.

| Состояние | Что это означает | Что не следует из него |
|---|---|---|
| смысловое основание | теоретически сформулированный смысл или ограничение в единственном предметном владельце | что механизм уже реализован |
| исследовательская гипотеза | проверяемое предположение, задача, отрицательный пример или экспериментальная ветка | что гипотеза является текущей нормой |
| исполняемое свидетельство | проверка на реальном ядре и фактический результат её выполнения | что версия уже принята |
| кандидат | рабочая версионная проекция контракта и корпуса соответствия | что кандидат имеет нормативный статус |
| принятие | отдельное явное решение после прохождения обязательной цепочки доказательств | что любой будущий выпуск автоматически совместим |
| выпуск | опубликованная версионированная проекция уже принятого состояния и указатели на неё | что публикация сама создаёт семантику |

Смысловое основание может породить исследовательскую гипотезу. Гипотеза должна стать опровержимой. Исполняемое свидетельство показывает, что именно выдержало проверку. Кандидат собирает доказанную границу в переносимую форму. Принятие меняет статус. Выпуск делает принятое состояние доступным читателю и инструментам.

## Разработка через контракты

Для смыслового изменения базовая траектория такова:

```text
problem / falsifier
-> решение в единственном active owner
-> нормативное утверждение или проверяемая гипотеза
-> RED witness
-> минимальное изменение рабочего ядра
-> GREEN witness
-> conformance projection
-> contract projection
-> docs:sync + docs:check
-> CI + repo-guard
-> explicit acceptance or rejection
-> current release projection
```

Кандидатные контракт и корпус соответствия могут появляться раньше как рабочие проверяемые артефакты, но до подтверждения ядром они не должны изображать доказанность. В частности, неполный кандидат не получает статус принятого только из-за существования файлов.

Правильное направление финальной фиксации:

```text
теория и исследование
        ↓
смысловое решение
        ↓
рабочее ядро
        ↓
исполняемые проверки
        ↓
реальные тестовые данные
        ↓
корпус соответствия
        ↓
версионный контракт
        ↓
человекочитаемая документация
        ↓
явное принятие
```

Неправильное направление:

```text
сначала объявить желаемое поведение принятой версией
        ↓
считать запись в JSON доказательством
        ↓
потом подгонять под неё ядро
```

Принятый контракт является машиночитаемой проекцией доказанной границы, а не заменой теории и не доказательством сам по себе.

## Исполняемое свидетельство

Записанное требование и проверенное требование — разные вещи.

Обязательная проверка версии должна использовать реальное ядро, а не отдельную тестовую модель, повторяющую ожидаемый ответ.

Если проверка требует нового поведения, используется цикл:

```text
RED
↓
минимальное изменение ядра
↓
GREEN
↓
уточнение корпуса соответствия и контракта
```

Красный тест до реализации допустим как исследовательское свидетельство проблемы. Зелёный тест после реализации подтверждает конкретное наблюдаемое свойство. Ни один из них сам по себе не выполняет действие принятия версии.

## Реальные переносимые тестовые данные

Для сериализации и границ между независимыми апамятями предпочтительны переносимые данные, проходящие через реальное ядро.

Основной сценарий:

```text
тестовый файл ачисла
        ↓
апамять A
        ↓
рабочий сериализатор
        ↓
передаваемое ачисло
        ↓
апамять B
        ↓
структурное сравнение A и B
```

Такой тест одновременно проверяет:

- десериализацию;
- работу реальной апамяти;
- сериализацию;
- перенос между независимыми апамятями;
- независимость от технических идентификаторов;
- каноничность повторной сериализации.

Для строковых и четверичных ачисел действует тот же принцип. Если такой путь для новой формы ещё невозможно выполнить, это обнаруженный пробел, а не основание заменить реальный путь фиктивной моделью.

## Постоянные свидетельства версии

Тест, который должен стать обязательным начиная с некоторой версии, помечается непосредственно в исходном тестовом файле:

```text
// mts-version-evidence: required-from=0.12
```

Проверки согласованности версий читают эти метки из `ts/test/**`. Если версия достигла указанной границы, а обязательное свидетельство отсутствует в её корпусе соответствия или не проходит на реальном ядре, версия не может считаться готовой к принятию.

Естественный порядок:

```text
сначала появился рабочий GREEN факт
потом версионная проекция зафиксировала этот факт
```

## Кандидат, принятие и выпуск

Наличие кандидатных файлов не меняет текущую принятую семантику.

Пока обязательные свидетельства неполны, кандидат должен оставаться неготовым:

```text
accepted = false
acceptanceReady = false
```

После закрытия всех обязательных доказательных границ кандидат может стать готовым к принятию, оставаясь ещё непринятым до отдельного явного действия.

Перед принятием проверяется вся цепочка:

```text
смысловое основание
        ↓
рабочее ядро
        ↓
обязательные GREEN проверки
        ↓
корпус соответствия
        ↓
контракт
        ↓
документация
        ↓
явное принятие
```

Критическое различие:

```text
GREEN != принято
нет GREEN => принять невозможно
```

После принятия текущий выпуск и предыдущая неизменяемая версия отражаются единственной генерируемой проекцией в README. Эта проекция сообщает состояние, но не становится новым источником теории.

Принятые версионные артефакты не переписываются ради удобства следующего кандидата. Новое смысловое изменение получает новую версионную границу.

## Команды проверки

```bash
npm --prefix ts run docs:sync
npm --prefix ts run docs:check
npm --prefix ts run check
```

`docs:sync` изменяет только явно разрешённую текущую проекцию. Содержательную теорию из TypeScript он не выводит.

## История и активное дерево

Текущий каталог репозитория описывает текущее состояние.

История исследований хранится в:

```text
Git
закрытых задачах GitHub
закрытых запросах на слияние
```

Не нужно сохранять в активном дереве несколько документов, повторяющих одну и ту же стадию рассуждений.

## Защита от разрастания

Перед добавлением задачи или Markdown-файла необходимо ответить на три вопроса:

```text
есть ли уже active owner этой темы?
содержит ли новый артефакт уникальную current authority/evidence?
нельзя ли сохранить обсуждение только в существующей Issue/Git history?
```

Если ответы указывают на дублирование, новый артефакт не создаётся.

При реорганизации предпочтителен отрицательный рост поверхности:

```text
active semantic paths after <= before
current documents after <= before
history remains recoverable from Git
```

## Язык

Нормативная теория и определения МТС излагаются по-русски. Английские имена используются для буквальных программных сущностей, протоколов и полей.

Новый теоретический термин сначала определяется в языке самой МТС, а программное имя получает только при необходимости реализации.
