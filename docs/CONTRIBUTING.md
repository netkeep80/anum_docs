# Руководство по вкладу
<!-- версия документа МТС; mts-doc-version: v0.13 -->
> **Документ относится к МТС v0.13**

Этот документ задаёт процесс изменения репозитория. Он **не определяет семантику МТС**.

Главный принцип:

```text
main = текущее состояние
Git / закрытые задачи / закрытые запросы на слияние = история
одна смысловая тема -> один текущий владелец
```

## 1. Текущая поверхность репозитория

Канонические области:

| Содержимое | Владелец |
|---|---|
| нормативное основание | `docs/theory/` |
| предметные спецификации | `docs/specs/` |
| терминологический индекс | `docs/Словарь терминов МТС.md` |
| исполнимое ядро | `ts/src/` |
| исполнимые свидетельства | `ts/test/` |
| машинные контракты | `contracts/` |
| корпус соответствия | `contracts/mts-conformance-*.json` |
| принятие и текущий выпуск | `cutover/` |
| прослеживаемость | `traceability/` |
| индекс доказательных результатов | `theorems/` |

Исследовательские авторские материалы в `docs/research/` находятся **вне текущей документации**. Они не переписываются только ради приведения к текущему изложению v0.13 и не используются как обязательный путь чтения текущей теории.

## 2. Иерархия источников истины

Порядок полномочий:

```text
нормативная теория
      ↓
принятый машинный контракт
      ↓
корпус соответствия
      ↓
исполняемые свидетельства
      ↓
эталонная реализация
```

Отсюда:

```text
реализация делает X
!=
МТС означает X
```

и:

```text
в JSON записано X
!=
X доказано
```

`theorems/registry.json` является **индексом доказательных результатов**, а не нормативным источником семантики.

## 3. Статусы знания и изменения

Необходимо различать:

| Статус | Смысл |
|---|---|
| принято v0.13 | часть текущей принятой семантики |
| производный результат | доказанный результат о принятой v0.13, не новый закон контракта |
| исполнимое свидетельство | конкретная проверка свойства |
| исследовательская гипотеза | проверяемое, но ещё не установленное утверждение |
| отложено | явно вне текущей принятой области |
| реализация | технический носитель принятого или исследуемого поведения |

Критические неследования:

```text
GREEN != принято
реестр теорем != доказательство сам по себе
доказанный производный результат != новый принятый закон
исследовательский тест != текущая норма
```

## 4. Разработка смыслового изменения

Базовая траектория:

```text
problem / falsifier
-> один смысловой владелец
-> проверяемая формулировка
-> RED witness
-> минимальное изменение
-> GREEN witness
-> conformance projection
-> contract projection
-> documentation
-> CI + repo-guard
-> явное принятие или отклонение
```

Нельзя начинать с желаемого JSON и считать его доказательством.

Правильное направление:

```text
смысл
-> проверяемая гипотеза
-> ядро
-> исполнимое свидетельство
-> машинная проекция
-> человекочитаемая документация
-> принятие
```

## 5. Доказательная база

Для нетривиального утверждения желательно разделять:

```text
statement
assumptions
scope
dependencies
evidence
status
```

Реестр `theorems/registry.json` хранит эти связи как индекс.

Статус `scoped` означает, что утверждение установлено в явно указанной области. Он не разрешает молча расширять результат за пределы этой области.

Независимые доказательные средства — например `Lean`, собственное доказательство МТС или внешний проверяющий — могут усиливать доверие, но не должны переписывать смысл теоремы через собственную модель.

## 6. Текущая документация описывает только v0.13

Все текущие читательские Markdown-документы:

- описывают только МТС v0.13;
- не содержат рассказа о предыдущих версиях;
- не объясняют миграции;
- не учат устаревшей семантике;
- имеют ровно одну явную версионную пометку.

Формат:

```markdown
# Заголовок
<!-- версия документа МТС; mts-doc-version: CURRENT -->
> **Версия МТС: текущая**
```

Для процессного документа допустима видимая форма:

```markdown
> **Документ относится к МТС v0.13**
```

История версий восстанавливается из Git и неизменяемых версионированных машинных артефактов.

## 7. Имена current-документов не содержат версию

Версия является свойством содержимого, а не пути.

Правильно:

```text
docs/specs/Пучки связей.md
docs/specs/Ачисла и сериализация.md
docs/Словарь терминов МТС.md
```

Неправильно:

```text
Документ v0.13.md
Спецификация 0.13.md
```

При новом принятом выпуске обновляется содержимое того же current-документа.

Версионированные машинные артефакты `contracts/`, `cutover/`, `traceability/` под это правило не подпадают.

## 8. Один смысловой факт — один владелец

Нормативный факт должен иметь одного канонического владельца.

Другие документы:

- дают краткое объяснение;
- ссылаются на владельца;
- не создают конкурирующее полное определение.

Для L1–L13 действуют уникальные якоря владельцев, контролируемые `repo-policy.json`.

Если смысловой факт уже имеет владельца, новый Markdown-файл для той же темы не создаётся.

## 9. Словарь терминов

`docs/Словарь терминов МТС.md` — единый current терминологический индекс.

Каждая статья содержит:

```text
preferred term
краткое определение
слой
статус
Подробнее -> canonical owner section/anchor
Не путать с
другие имена
```

Словарь **не переопределяет** канонический owner.

Если формулировки расходятся:

```text
canonical owner
>
glossary summary
```

Ссылки `Подробнее` проверяются исполнимым тестом.

## 10. Обязательный план файла перед переписыванием документа

Current-документ нельзя существенно переписывать без отдельного плана.

План файла должен содержать:

1. роль и уникального владельца;
2. текущие дефекты;
3. источники полномочий;
4. список того, что обязано сохраниться;
5. целевое оглавление;
6. действие по каждому разделу;
7. обязательные примеры;
8. запрещённые утверждения;
9. связи с другими документами;
10. критерии приёмки;
11. точный PR scope;
12. открытые вопросы и блокеры.

Допустимые действия по разделам:

```text
KEEP
REWRITE
MOVE WITHIN FILE
MERGE
DELETE
```

История версии не является отдельным current-разделом.

## 11. Новый документ

Новый текущий Markdown-документ допустим только при доказанном пробеле владения.

Перед созданием нужно ответить:

```text
есть ли уже владелец темы?
создаёт ли новый файл уникальную current функцию?
можно ли решить задачу ссылкой или разделом существующего owner?
```

Если путь должен стать исключением из общего ограничения роста документации, governance-изменение выполняется **до** создания файла.

Пример такого процесса в текущей структуре — отдельное предварительное разрешение пути терминологического словаря.

## 12. Переименование документа

Переименование current-документа выполняется атомарно:

```text
новый путь
+ все входящие ссылки
+ repo-policy canonical path
+ docs checks
+ тестовые path assumptions
- старый путь
```

Активный дубликат со старым именем не оставляется.

## 13. Язык документов

Current теория и определения пишутся по-русски.

Английские слова допустимы для буквальных:

- имён типов и функций;
- протоколов;
- полей;
- принятые идентификаторы;
- устоявшихся технических aliases.

Если английское имя является термином реализации, предпочтительный русский термин определяется первым, а английское имя указывается как дополнительное.

## 14. Формальное и техническое нельзя смешивать

Программное имя не создаёт семантику:

```text
поле start
!=
доказательство START

switch("9")
!=
полномочие FORMAL

memory.outgoing(theory)
!=
определение Theory
```

Код может быть исполнимым свидетельством уже сформулированного правила.

## 15. Чтение и изменение

Проверяющие механизмы и воспроизведение по умолчанию должны зависеть только от возможности чтения.

```text
read
search
resolve
verify
replay
!=
ensure
materialize
write
```

Если тест проверяет отсутствие побочных эффектов, он должен использовать реальный интерфейс памяти и явно проверять отсутствие записи.

## 16. Реальные переносимые свидетельства

Для сериализации и межпамятного переноса тест должен проходить через реальные независимые апамяти:

```text
апамять A
-> рабочее представление
-> переносимые данные
-> апамять B
-> структурное сравнение
```

Локальный технический `handle` не переносится как смысловое тождество.

## 17. Постоянные свидетельства версии

Тест, который является обязательным начиная с текущей принятой границы, может содержать:

```text
// mts-version-evidence: required-from=0.13
```

Версионная проекция фиксирует уже существующий GREEN-факт, а не создаёт его.

## 18. Принятие и выпуск

Для следующего кандидата должны быть отдельно различены:

```text
candidate
acceptanceReady
explicit acceptance
current release
```

Автоматическое принятие запрещено.

```text
GREEN != принято
нет GREEN => принять невозможно
```

Принятые версионные машинные артефакты не переписываются ради удобства будущего кандидата.

Текущий README показывает только текущий принятый выпуск.

## 19. Проверки

Основные команды:

```bash
npm --prefix ts run docs:sync
npm --prefix ts run docs:check
npm --prefix ts run check
```

Также обязательны:

- CI;
- `repo-guard`;
- проверки якорей владельцев;
- проверки ссылок словаря;
- защита неизменяемых и защищённых путей.

`docs:sync` имеет право изменять только явно разрешённые генерируемые блоки. Он не выводит теорию из TypeScript.

## 20. Защита от разрастания

Перед добавлением файла, слоя или параллельной реализации нужно проверить:

```text
есть ли уже active owner?
можно ли расширить текущий owner?
останется ли после изменения одна current поверхность?
```

Предпочтение:

```text
меньше параллельных owner'ов
меньше дублирования
больше явных ссылок
история остаётся в Git
```

После merge временные ветки должны удаляться, если больше не нужны.

## 21. Критерий внешнего читателя

Текущая документация считается согласованной, если читатель может восстановить МТС v0.13 без чтения истории задач и запросов на слияние.

Если для понимания текущей семантики требуется исследовательское обсуждение, документация ещё не завершена.

## Итог

Рабочий цикл репозитория:

```text
один owner
-> проверяемое изменение
-> evidence
-> governed PR
-> GREEN CI/repo-guard
-> merge
-> current documentation remains one coherent v0.13 surface
```
