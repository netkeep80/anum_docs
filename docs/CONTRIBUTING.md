# Руководство по вкладу

Изменения активного дерева вносятся через запрос на слияние и проходят обязательные CI и repo-guard.

Главный принцип репозитория:

```text
main = current state
Git / closed Issues / closed PRs = history
ONE topic -> ONE active owner
```

История исследования не должна копироваться в новые Markdown-файлы только потому, что она была полезна в процессе. Новый документ добавляется лишь тогда, когда он является отдельной актуальной нормативной или технической поверхностью.

## Канонические области

| Содержимое | Каталог |
|---|---|
| текущее ядро TypeScript | `ts/src/` |
| исполнимые проверки | `ts/test/` |
| браузерная интеграция | `ts/browser/` |
| версионированные машинные контракты | `contracts/` |
| свидетельства принятия | `cutover/` |
| нормативная теория | `docs/theory/` |
| актуальные технические спецификации | `docs/specs/` |
| первичный авторский исследовательский источник | `docs/research/Исходные мысли МТС.md` |

`docs/research/Исходные мысли МТС.md` защищён: он изменяется только владельцем репозитория. Автоматизированный запрос на слияние не редактирует и не удаляет этот файл.

Промежуточные исследовательские заметки, планы реализации, документы передачи контекста и альтернативные архитектурные проекции не сохраняются в активном дереве; для них используются задачи, обсуждение запросов на слияние и история Git.

## Текущий жизненный цикл

```text
accepted/current = MTS v0.11
candidate = MTS v0.12 / NOT ACCEPTED
candidate lifecycle owner = #1134
foundation/architecture owner = #1167
C7+ = BLOCKED until #1167 is resolved
global roadmap = #657
```

Не создавать параллельную задачу фундамента или жизненного цикла для мысли, которая ещё относится к #1167. Отдельная задача допустима для самостоятельно исполнимого ограниченного результата после того, как его зависимость и владелец определены в глобальном плане.

## Первичный язык фундамента

При изложении основания порядок представлений обязателен:

```text
1. остенсивная форма МТС: ∞ / ♂e / b♀ / b⟼e
2. структурное уравнение
3. machine/reference representation, например Link(start,end)
```

Вторичная нотация языка реализации не должна вытеснять остенсивные формы. Одинаковый видимый знак на разных уровнях не получает одинаковый смысл автоматически: исходный знак, словарная запись, смысловое употребление и корневой абит необходимо различать.

## Иерархия источников истины

1. Нормативная теория определяет принятый смысл.
2. Принятый машинный контракт фиксирует переносимую наблюдаемую проекцию.
3. Корпус соответствия делает границу проверяемой.
4. Эталонная реализация свидетельствует реализуемость.
5. Git, задачи и запросы на слияние хранят исследовательскую историю.

Для непринятого кандидата задача жизненного цикла или фундамента может зафиксировать, что его контракт требует ограниченной коррекции. До явного принятия такой кандидат не переписывает принятую теорию.

## Разработка через контракты

Для смыслового изменения:

```text
problem / falsifier
→ решение в единственном active owner
→ normative statement
→ candidate contract + conformance
→ implementation / evidence
→ docs:sync + docs:check
→ CI + repo-guard
→ explicit acceptance or rejection
```

Реализация не является источником семантики:

```text
реализация делает X
!=
МТС означает X
```

Команды проверки:

```bash
npm --prefix ts run docs:sync
npm --prefix ts run docs:check
npm --prefix ts run check
```

`docs:sync` изменяет только блоки между `мтс-текущая-проекция:*`; содержательную теорию из TypeScript он не выводит.

## Защита от разрастания

Перед добавлением задачи или Markdown-файла необходимо ответить на три вопроса:

```text
есть ли уже active owner этой темы?
содержит ли новый артефакт уникальную current authority/evidence?
нельзя ли сохранить обсуждение только в существующей Issue/Git history?
```

Если ответы указывают на дублирование, новый артефакт не создаётся.

При реорганизации предпочтителен отрицательный рост поверхности:

```text
active semantic paths after <= before
current documents after <= before
history remains recoverable from Git
```

## Язык

Нормативная теория и определения МТС излагаются по-русски. Английские имена используются для буквальных программных сущностей, протоколов и полей.

Новый теоретический термин сначала определяется в языке самой МТС, а программное имя получает только при необходимости реализации.
