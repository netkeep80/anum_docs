# Руководство по вкладу

Изменения активного ядра вносятся через запрос на слияние.

## Канонические области

| Содержимое | Каталог |
|---|---|
| текущее ядро на `TypeScript` | `ts/src/` |
| исполнимые проверки соответствия и выпуска | `ts/test/` |
| браузерная интеграция | `ts/browser/` |
| версионированные машинные контракты | `contracts/` |
| свидетельство принятия выпуска | `cutover/` |
| нормативная теория | `docs/theory/` |
| технические спецификации | `docs/specs/` |
| ненормативные исследования | `docs/research/` |

Исторические варианты не сохраняются рядом с текущим состоянием: история находится в Git, задачах и запросах на слияние.

## Язык канонического изложения

Теория МТС, определения и нормативная документация излагаются по-русски. Английское написание сохраняется только для буквальных имён программных сущностей, файлов, протоколов и полей, например `LinkHandle`, `ReadMemory`, `schema`.

Новый теоретический термин сначала определяется по-русски и только затем при необходимости получает программное имя.

## Разделение уровней

```text
L0 — онтология
L1 — семантическая модель
L2 — формальный язык
L3 — сериализация
L4 — исполнение
L5 — теория вывода
```

Одинаковый видимый знак на разных уровнях не получает одинаковый смысл автоматически.

Критические границы:

```text
смысловая связь != технический идентификатор
смысловая связь != вхождение / позиция / история
представление != интерпретация
читать / искать / проверять / воспроизводить != материализовать / записывать
не найдено != не существует
```

## Разработка МТС через контракты

Направление зависимости:

```text
нормативная теория
      ↓
кандидатный контракт
      ↓
корпус соответствия и отрицательные векторы
      ↓
проверка на опровержение
      ↓
эталонная реализация
      ↓
независимая или дифференциальная проверка
      ↓
явное принятие
      ↓
текущий принятый контракт
```

Реализация является свидетельством реализуемости, а не источником теории.

Неверно:

```text
реализация делает X
=> МТС означает X
```

Правильно:

```text
теория задаёт X
контракт фиксирует наблюдаемое X
реализация воплощает X
```

## Обязательная синхронизация документации

`README.md` и нормативная теория являются частью результата смысловой работы, а не необязательным отчётом после кода.

Для смыслового изменения обязательна последовательность:

```text
смысловое решение
→ согласование нормативной теории
→ кандидатный контракт и корпус соответствия
→ реализация
→ docs:sync
→ docs:check
→ полный CI и repo-guard
→ явное принятие
```

Команды:

```bash
npm --prefix ts run docs:sync
npm --prefix ts run docs:check
```

`docs:sync` не выводит теорию из кода `TypeScript`. Команда обновляет только ограниченные блоки между специальными маркерами. Эти блоки являются машинной проекцией уже принятого состояния контракта.

Содержательная теория вне автоматического блока изменяется только как явное смысловое решение.

`docs:check` заново строит ожидаемую проекцию и завершает проверку ошибкой, если:

- отсутствует или продублирован маркер;
- устарела текущая или предыдущая версия;
- реестр F1 расходится с текущим контрактом;
- корневые, эффектные или транспортные факты расходятся с текущим контрактом.

Проверка входит в обычную команду `npm run check`, поэтому устаревшая документация блокирует CI.

Для внутреннего рефакторинга без наблюдаемого смыслового изменения бессодержательная правка теории не требуется: `docs:check` всё равно подтверждает актуальность машинной проекции.

## Иерархия источников истины

1. **Нормативная теория** определяет смысл.
2. **Принятый машинный контракт** фиксирует переносимую наблюдаемую проекцию принятой теории.
3. **Корпус соответствия** делает границу проверяемой.
4. **Эталонная реализация** показывает реализацию контракта.
5. **Независимые потребители** должны совпадать по наблюдаемым результатам, а не по внутренней архитектуре.
6. **Git, задачи и запросы на слияние** хранят процесс исследования и историю решений.

Если эти уровни расходятся, это дефект. Поведение среды исполнения не выбирается автоматически как победившая теория.

## Минимальная наблюдаемая граница

Контракт фиксирует только то, от чего зависит смысл или совместимость:

- роль входа;
- наблюдаемый результат;
- переносимую категорию ошибки;
- границу чтения и эффекта;
- инварианты смыслового тождества;
- требования канонизации;
- отношения версионируемых поверхностей;
- обязательные отрицательные векторы.

Без отдельной причины контракт не фиксирует технический указатель, локальный идентификатор, порядок выделения памяти, устройство классов, внутренний кэш, буквальный текст исключения или пользовательский интерфейс.

## Три формы фундаментального инварианта

Желательно иметь одновременно:

```text
1. русское нормативное определение
2. машиночитаемый инвариант в контракте
3. исполнимые положительные и отрицательные проверки соответствия
```

Расхождение этих форм считается дефектом.

## Проверка на опровержение

Проверка кандидата должна искать способ сломать предложенную семантику. Где применимо, проверяются контрпримеры, циклы, самоссылки, псевдонимы, повреждённые входы, утечка чтения в запись, переименования и межъязыковые неоднозначности.

## Жизненный цикл

```text
Research
→ Problem
→ Candidate
→ Challenged
→ Modeled
→ Accepted
→ Released
```

До явного принятия кандидат остаётся экспериментальным, даже если его код и тесты зелёные.

## Критерии принятия

Перед принятием фундаментального изменения проверяется:

- [ ] проблема сформулирована независимо от реализации;
- [ ] нормативная семантика определена;
- [ ] контракт минимален и не зависит от устройства реализации;
- [ ] положительный и отрицательный корпуса достаточны;
- [ ] циклы и самоссылки проверены;
- [ ] техническое тождество не просочилось в семантику;
- [ ] граница чтения и эффекта задана явно;
- [ ] повреждённый вход отклоняется предсказуемо;
- [ ] существует исполнимая эталонная модель;
- [ ] независимая проверка есть там, где она существенно уменьшает доверенную границу;
- [ ] `README.md`, теория, контракт и корпус соответствия согласованы;
- [ ] `docs:check` проходит;
- [ ] известен план перехода потребителей;
- [ ] выполнено явное принятие владельцем теории;
- [ ] устаревшая действующая семантика удаляется без режима совместимости.

## Версионирование

Новая версия требуется при изменении принятой наблюдаемой машинной границы либо состава текущего выпуска, требующего перепривязки потребителя.

Новая версия не требуется автоматически для внутреннего рефакторинга, оптимизации, нового индекса, уточнения документации без смыслового изменения или новых отрицательных тестов уже действующего требования.

## Доверенное ядро

Предпочтительная схема:

```text
поиск / эвристики / интерфейс / оптимизация
        = недоверенный производитель

переносимое свидетельство
        ↓
маленькая проверка / воспроизведение
        = доверенный потребитель
```

## После принятия

1. Потребители переводятся на новый канонический путь.
2. Текущие указатели контрактов и свидетельства принятия обновляются явно.
3. `docs:sync` обновляет автоматическую проекцию текущего состояния.
4. Содержательная теория уже должна отражать принятое решение.
5. Устаревшая действующая реализация удаляется после миграции.
6. История остаётся в Git, а не в слоях совместимости.

## Проверка

Полный локальный прогон:

```bash
npm --prefix ts ci
npm --prefix ts run check
```

Отдельная проверка документации:

```bash
npm --prefix ts run docs:sync
npm --prefix ts run docs:check
```

Кодировка текстовых файлов — UTF-8.

Защищённый файл `docs/research/Исходные мысли МТС.md` изменяется только владельцем репозитория.
