# Руководство по вкладу

Изменения активного ядра вносятся через запрос на слияние (PR).

## Канонические области

| Содержимое | Каталог |
|---|---|
| корневые определения и проверки соответствия | `tests/` |
| эталонное исполняемое ядро и валидация | `core/` |
| версионированные внешние контракты | `contracts/` |
| практические преобразования | `converters/` |
| нормативная теория | `docs/theory/` |
| технические спецификации | `docs/specs/` |
| ненормативные исходные заметки | `docs/research/` |

Каждый активный документ должен иметь уникальную роль, а каждая функция — одну активную реализацию. Исторические варианты не сохраняются в `archive`, `legacy`, `old` или аналогичных каталогах: история уже находится в Git.

## Язык канонического изложения

Теория МТС, определения понятий, пояснения и нормативная документация излагаются **по-русски**.

Предпочтительные термины:

```text
reference model        → эталонная модель
graph carrier          → графовый носитель
identity               → тождество / идентификатор — по смыслу
occurrence             → вхождение
glyph                  → знак
metavariable           → метапеременная
runtime                → исполнение / среда исполнения
pattern                → образец
consumer               → потребитель
canonical path         → канонический путь
read-only              → только чтение
```

Английское написание сохраняется, когда речь идёт именно о буквальном имени программной сущности или внешнего протокола: например `LinkRef`, `ContextFrame`, `MemoryView`, имя функции, поле JSON, имя файла, значение `schema` или статус машинного контракта. В таком случае русское понятие должно оставаться основным в окружающем тексте.

Нельзя вводить новый теоретический термин только потому, что такое английское имя удобно в реализации. Сначала определяется русское понятие МТС, затем при необходимости указывается его программное представление.

## Текущая модель и уровни

Машинную границу текущей принятой версии задают [единый контракт `mts-contract/v0.7`](../contracts/mts-contract-v0.7.json) и [единый корпус соответствия `mts-conformance/v0.7`](../contracts/mts-conformance-v0.7.json). Текущий исполняемый путь — единое корневое ядро через `core/foundation_v2.py`; историческая реализация Python после C7 удалена и не имеет режима совместимости. Контракт и корпус v0.6 остаются неизменяемым свидетельством предыдущего выпуска, но не являются текущим реестром владельцев исполнения. Теоретические основания и формальная нотация задаются активными документами `docs/theory/` и `docs/specs/`; старые реализации выпусков не сохраняются в активном дереве ради истории.

Изменение одного уровня не должно скрыто менять другой:

```text
L0 — онтология
L1 — семантическая модель
L2 — формальный язык
L3 — сериализация
L4 — исполнение
L5 — теория вывода
```

Если одинаковый видимый знак используется на нескольких уровнях, тождество его денотаций должно быть задано отдельным явным правилом.

Для текущего L2 дополнительно зафиксировано:

```text
◁/▷ — атомарные контекстные местоимения;
↑ — отдельный подъём к внешнему контексту;
[`[`, `]`] не перегружаются контекстной нотацией;
[] — анонимная форма, локальная для конкретного вхождения;
interpret — операция только чтения;
realize — отдельная операция изменения памяти.
```

Для L3 текущий канонический путь — `anum-deserialization/v0.4`: алфавит состоит ровно из `[`, `]`, `1`, `0`; корень не является пятым абитом; пустой поток и пустая группа десериализуются в корень. Семантическая связь определяется своими упорядоченными полюсами, а технический идентификатор записи не создаёт дополнительного тождества связи.

Имена `interpret` и `realize` в этом фрагменте оставлены как буквальные имена машинного интерфейса; теоретическое различие формулируется по-русски как «интерпретация не является материализацией».

## Разработка МТС через контракты

МТС развивается через явное разделение смысла, машинной границы и реализации:

```text
нормативная теория
      ↓
candidate contract
      ↓
conformance + negative vectors
      ↓
challenge
      ↓
эталонная реализация
      ↓
независимая / дифференциальная проверка
      ↓
explicit acceptance
      ↓
current accepted contract
```

Эта цепочка не означает, что любой шаг обязан создавать новый JSON-файл. Постоянный машинный артефакт добавляется только тогда, когда у него есть текущая нормативная роль или реальный потребитель.

### Иерархия источников истины

Роли источников должны быть различены явно.

1. **Нормативная теория** в `docs/theory/**` и `docs/specs/**` отвечает на вопрос «что это означает?». Теория не обязана повторять структуру классов, модулей или хранилища конкретной реализации.
2. **Accepted machine contract** — машинно читаемая проекция принятой теории на наблюдаемую границу. Он задаёт обязательные входы, результаты, эффекты, запреты и версионируемые поверхности.
3. **Conformance corpus** делает contract проверяемым через переносимые положительные и отрицательные примеры.
4. **Эталонная реализация** является свидетельством реализуемости contract, но не источником смысла МТС.
5. **Независимые потребители** могут иметь другую архитектуру и обязаны совпадать по принятой наблюдаемой семантике, а не по внутреннему устройству эталонного кода.
6. **Git, issues и PR** хранят исследование, отклонённые варианты, challenge reasoning и историю переходов. `main` хранит текущее состояние, а не процесс его получения.

Нельзя выводить теорию из случайного поведения реализации:

```text
Python делает X
=> МТС означает X          # неверно
```

Правильное направление зависимости:

```text
theory / accepted decision задаёт X
contract фиксирует наблюдаемое X
implementation реализует X
```

### Минимальная наблюдаемая граница

Contract фиксирует только то, от чего действительно зависит смысл или совместимость:

- семантическую роль входа;
- детерминированный наблюдаемый результат;
- переносимую категорию ошибки или отказа;
- границу чтения и эффекта;
- инварианты смыслового тождества;
- требования канонизации;
- отношение версионируемых поверхностей;
- обязательные отрицательные veto-векторы.

Без отдельного обоснования contract не должен фиксировать:

- runtime pointer или object identity;
- локальный slot/ID;
- порядок выделения памяти;
- Python dataclass layout;
- разбиение по классам и модулям;
- внутренний cache/index;
- текст traceback;
- случайный порядок обхода;
- storage lineage UUID;
- UI-представление.

Особенно важно не возвращать техническое тождество в смысловую модель: разные storage/runtime coordinates сами по себе не создают разные semantic Link.

### Contract и conformance образуют пару

Contract без conformance недостаточен: он задаёт норму, но не обеспечивает воспроизводимой проверки. Conformance без contract также недостаточен: набор тестовых примеров не объясняет, что именно считается нормой.

Для фундаментального инварианта желательно иметь три согласованных представления:

```text
1. русское нормативное определение
2. machine-readable invariant в contract
3. executable positive + negative conformance
```

Расхождение этих трёх представлений считается дефектом. Текущее поведение кода не используется как автоматический способ разрешить расхождение.

Negative vectors являются частью release boundary наравне с положительными примерами. Например для rooted identity должны проверяться не только повторное получение `R ⟼ R` и переиспользование одной пары полюсов, но и запрет второго полностью самозамкнутого semantic root, duplicate same pair и distinction, основанный только на technical ID.

### Challenge отличается от обычного unit test

Unit test обычно подтверждает известное требование реализации. Challenge пытается опровергнуть candidate semantics.

Для фундаментальных кандидатов проверяются, где применимо:

- контрпримеры и малые конечные модели;
- циклы и самоссылки;
- alias/identity attacks;
- malformed inputs;
- утечка `read -> write`;
- эквивалентные написания и переименования;
- неоднозначности между языками и реализациями.

Challenge может предшествовать формальному candidate contract, если смысл ещё недостаточно ясен. Contract-driven development не должен превращаться в бюрократическое «JSON-first», преждевременно замораживающее слабую модель.

## Жизненный цикл фундаментального решения

Изменение онтологии, эталонной семантики, формальной нотации, базового протокола или доверенных правил доказательства не должно попадать прямо из исследовательской заметки в нормативное ядро.

Машинные статусы жизненного цикла сохраняются в принятом написании:

```text
Research
→ Problem
→ Candidate
→ Challenged
→ Modeled
→ Accepted
→ Released
```

В русском тексте им соответствуют этапы исследования, постановки проблемы, кандидата, проверки, моделирования, принятия и выпуска.

- `Research`: идея или наблюдение ещё не обязаны менять current semantics.
- `Problem`: противоречие или недостаток current model формулируется независимо от реализации.
- `Candidate`: определена минимальная предполагаемая наблюдаемая граница либо достаточно точная семантическая гипотеза для challenge-first проверки.
- `Challenged`: candidate прошёл необходимые попытки опровержения.
- `Modeled`: минимум одна эталонная реализация исполняет candidate; для доверенной границы по возможности существует независимый checker/replay.
- `Accepted`: владелец теории явно принимает semantic decision. Зелёные тесты сами по себе не являются acceptance.
- `Released`: current pointers и consumer pins обновлены, а устаревшая активная семантика удалена после миграции.

До `Accepted` кандидат имеет статус `experimental`, даже если для него уже существует код или тестовая модель.

Состояния `Rejected`, `Deferred` и `Superseded` не требуют сохранения старой реализации в рабочем дереве: история решения остаётся в Git и GitHub.

### Definition of acceptance

Для фундаментального candidate перед принятием проверяется:

- [ ] проблема сформулирована независимо от реализации;
- [ ] нормативная семантика определена;
- [ ] candidate contract минимален и implementation-neutral;
- [ ] положительный corpus покрывает необходимые observables;
- [ ] отрицательный/veto corpus покрывает критические запреты;
- [ ] циклы и самоссылки проверены там, где релевантны;
- [ ] technical identity не просочилась в semantics;
- [ ] граница `read/effect` задана явно;
- [ ] malformed inputs fail-closed;
- [ ] существует исполнимая эталонная модель;
- [ ] independent/differential check существует там, где он существенно уменьшает trusted boundary;
- [ ] docs, contract и conformance согласованы;
- [ ] известен consumer/cutover plan;
- [ ] explicit owner acceptance выполнен;
- [ ] obsolete live semantics удаляется после миграции без compatibility mode.

## Версионирование контрактов

Версия accepted machine boundary меняется, когда меняется наблюдаемая принятая семантика либо composition current release так, что downstream должен перепривязаться к новой версии.

Автоматический version bump не требуется для:

- внутреннего рефакторинга;
- оптимизации производительности;
- нового индекса или cache;
- уточнения документации без observable delta;
- новых negative tests, которые только выявляют уже действующее требование.

Если старый accepted contract оказался неоднозначным, нельзя молча переписать его так, чтобы менялся наблюдаемый результат. Нужно явно решить, является ли это исправлением уже принятой границы или новой semantic version.

Leaf surface может сохранить собственную версию при смене owner implementation, если её observables не меняются. Umbrella/current release может потребовать новой версии из-за нового accepted composition или cutover.

## Межъязыковое соответствие

Один переносимый corpus должен по возможности исполняться эталонной и независимыми реализациями:

```text
portable fixture
   ├── Python oracle
   ├── TypeScript implementation
   └── future implementation
            ↓
   normalized observable result
```

Нормализация не должна зависеть от host identity.

Для сетей связей topology сравнивается modulo переименование технических handles; корень различается структурно; повтор одной semantic pair не получает новое тождество из allocation order; позиция и происхождение сохраняются отдельной связевой структурой там, где они входят в semantics.

Для ошибок сравниваются переносимые error/rejection categories, а не имена host exceptions или буквальный текст traceback.

## Доверенное ядро и внешние инструменты

Contract должен помогать уменьшать trusted boundary.

Предпочтительная схема для сложного поиска:

```text
search / heuristics / UI / optimization
        = недоверенный производитель

portable evidence
        ↓
small checker / replay
        = доверенный потребитель
```

Но это не требует автоматически вводить отдельный DTO для каждого шага. Evidence может быть обычной rooted link structure с явным словарём ролей и структурным reader, если этого достаточно для независимой проверки.

## Принятие без копий совместимости

После принятия фундаментального кандидата:

1. все потребители переводятся на новый канонический путь;
2. версионированный машинный контракт обновляется, если изменилась accepted boundary;
3. candidate или устаревшая реализация удаляется в том же PR миграции либо сразу после последнего consumer cutover;
4. CI запрещает возвращение параллельной активной реализации;
5. история остаётся в Git/issues/PR, а не в compatibility-каталогах и новых постоянных planning JSON.

Старые варианты доступны через историю Git и не должны участвовать в исполняемой системе.

## Ограничения

Изменение существующей теории, нотации, формата, эталонной модели или корневой формулы должно выполняться отдельной задачей. Рефакторинг не должен вводить новый анализатор, доказатель, интерпретатор, слой совместимости или нормативный документ без самостоятельного обоснования.

Зелёные тесты подтверждают реализацию текущих требований, но не принимают новую фундаментальную семантику автоматически.

Защищённый файл `docs/research/Исходные мысли МТС.md` изменяется только владельцем репозитория.

## Проверка

```bash
python -m pytest tests -v --tb=short
ruff check converters/ core/ tests/ --ignore E501,F401
git diff --check
```

Кодировка текстовых файлов — UTF-8. Пользовательские ошибки должны проверяться явно.
