# Руководство по вкладу

Изменения активного ядра вносятся через запрос на слияние.

## Канонические области

| Содержимое | Каталог |
|---|---|
| текущее ядро на `TypeScript` и публичная граница потребителя | `ts/src/` |
| исполнимые проверки соответствия и выпуска | `ts/test/` |
| браузерная интеграция общего семантического ядра | `ts/browser/` |
| версионированные внешние контракты | `contracts/` |
| текущее свидетельство принятия выпуска | `cutover/` |
| нормативная теория | `docs/theory/` |
| технические спецификации | `docs/specs/` |
| ненормативные исследовательские заметки | `docs/research/` |

Каждый активный документ должен иметь уникальную роль, а каждая функция — одну активную реализацию. Исторические варианты не сохраняются в специальных каталогах: история уже находится в Git.

## Язык канонического изложения

Теория МТС, определения понятий, пояснения и нормативная документация излагаются **по-русски**.

Предпочтительные термины:

```text
reference model        → эталонная модель
graph carrier          → графовый носитель
identity               → тождество / идентификатор — по смыслу
occurrence             → вхождение
glyph                  → знак
metavariable           → метапеременная
runtime                → исполнение / среда исполнения
pattern                → образец
consumer               → потребитель
canonical path         → канонический путь
read-only              → только чтение
```

Английское написание сохраняется, когда речь идёт о буквальном имени программной сущности или внешнего протокола: например `LinkHandle`, `Memory`, `ReadMemory`, имя функции, поле JSON, имя файла, значение `schema` или статус машинного контракта.

Нельзя вводить новый теоретический термин только потому, что такое имя удобно в реализации. Сначала определяется русское понятие МТС, затем при необходимости указывается его программное представление.

## Текущая модель и уровни

Машинную границу текущего принятого выпуска задают [контракт `mts-contract/v0.9`](../contracts/mts-contract-v0.9.json) и [корпус соответствия `mts-conformance/v0.9`](../contracts/mts-conformance-v0.9.json).

Топология выпуска:

```text
current  = MTS v0.9 accepted
previous = MTS v0.8 immutable evidence
semanticBase(v0.9) = mts-contract/v0.8
observableSemanticDelta = true
```

Единственная текущая реализация написана на `TypeScript` и поставляется как пакет `@mts/core`. Контракт и корпус v0.8 остаются неизменяемым свидетельством предыдущего выпуска. Среда исполнения Python, прежний эталон Python и режим совместимости отсутствуют в активном дереве.

Изменение одного уровня не должно скрыто менять другой:

```text
L0 — онтология
L1 — семантическая модель
L2 — формальный язык
L3 — сериализация
L4 — исполнение
L5 — теория вывода
```

Если одинаковый видимый знак используется на нескольких уровнях, тождество его денотаций должно быть задано отдельным явным правилом.

Для F1/L2 МТС v0.9 зафиксирован минимальный внутренний реестр:

```text
∞ [ ] 1 0 ( ) ⟼ : =
```

Отложены как внутренние знаки:

```text
≡ ♂ ♀ ↑ { } ¬ ↛
```

Только метаязык:

```text
∧ ⇔ ⇒ ≠ →
```

Контексты `Q` и `FORMAL` являются явной структурной частью v0.9. Знаки `[`/`]` и `(`/`)` участвуют в открытии и закрытии контекстов, а лексический родитель хранится структурой `K`, а не скрытым стеком среды исполнения. Возвращаемое значение `R` сохраняется как явная позиция через `ExactSequence`.

Для `STRING→QUATERNARY` принят канонический носитель по одному байту: один конверт `[8 bits]` на точный байт, без скрытой нормализации `Unicode` и без технического идентификатора байта как смыслового тождества.

Для L3 транспортный алфавит состоит ровно из `[`, `]`, `1`, `0`; корень не является пятым абитом; пустой поток и пустая группа десериализуются в корень.

Фундаментальная граница чтения и эффекта:

```text
интерпретация / поиск / проверка / replay
!=
материализация / изменение памяти
```

## Разработка МТС через контракты

МТС развивается через явное разделение смысла, машинной границы и реализации.

Рабочая последовательность:

```text
нормативная теория
      ↓
кандидатный контракт
      ↓
корпус соответствия + отрицательные векторы
      ↓
проверка на опровержение
      ↓
эталонная реализация
      ↓
независимая / дифференциальная проверка
      ↓
явное принятие
      ↓
текущий принятый контракт
```

Эта последовательность не означает, что любой шаг обязан создавать новый JSON-файл. Постоянный машинный артефакт добавляется только тогда, когда у него есть текущая нормативная роль или реальный потребитель.

### Иерархия источников истины

1. **Нормативная теория** отвечает на вопрос «что это означает?».
2. **Принятый машинный контракт** является машиночитаемой проекцией принятой теории на наблюдаемую границу.
3. **Корпус соответствия** делает контракт проверяемым через переносимые положительные и отрицательные примеры.
4. **Эталонная реализация** является свидетельством реализуемости контракта, но не источником смысла МТС.
5. **Независимые потребители** могут иметь другую архитектуру и обязаны совпадать по принятой наблюдаемой семантике.
6. **Git, задачи и запросы на слияние** хранят исследование, отклонённые варианты и историю переходов. Основная ветка хранит текущее состояние.

Нельзя выводить теорию из случайного поведения реализации:

```text
реализация делает X
=> МТС означает X          # неверно
```

Правильное направление:

```text
теория / принятое решение задаёт X
контракт фиксирует наблюдаемое X
реализация воплощает X
```

### Минимальная наблюдаемая граница

Контракт фиксирует только то, от чего действительно зависит смысл или совместимость:

- семантическую роль входа;
- детерминированный наблюдаемый результат;
- переносимую категорию ошибки или отказа;
- границу чтения и эффекта;
- инварианты смыслового тождества;
- требования канонизации;
- отношение версионируемых поверхностей;
- обязательные отрицательные векторы запрета.

Без отдельного обоснования контракт не должен фиксировать:

- технический указатель среды исполнения;
- локальный идентификатор;
- порядок выделения памяти;
- устройство классов конкретного языка;
- внутренние кэши и индексы;
- буквальный текст исключения;
- случайный порядок обхода;
- представление пользовательского интерфейса.

### Контракт и корпус соответствия образуют пару

Для фундаментального инварианта желательно иметь три согласованных представления:

```text
1. русское нормативное определение
2. машиночитаемый инвариант в контракте
3. исполнимые положительные и отрицательные проверки соответствия
```

Расхождение этих трёх представлений считается дефектом. Текущее поведение кода не используется как автоматический способ разрешить расхождение.

Отрицательные векторы являются частью границы выпуска наравне с положительными примерами.

### Проверка на опровержение

Обычный модульный тест чаще подтверждает известное требование реализации. Проверка на опровержение целенаправленно ищет способ сломать кандидатную семантику.

Проверяются, где применимо:

- контрпримеры и малые конечные модели;
- циклы и самоссылки;
- атаки на тождество и псевдонимы;
- некорректные входные данные;
- утечка из чтения в изменение;
- эквивалентные написания и переименования;
- неоднозначности между языками и реализациями.

## Жизненный цикл фундаментального решения

```text
Research
→ Problem
→ Candidate
→ Challenged
→ Modeled
→ Accepted
→ Released
```

В русском тексте это этапы исследования, постановки проблемы, кандидата, проверки, моделирования, принятия и выпуска.

До явного принятия кандидат остаётся экспериментальным, даже если для него уже существует код или тестовая модель.

### Критерии принятия

Для фундаментального кандидата проверяется:

- [ ] проблема сформулирована независимо от реализации;
- [ ] нормативная семантика определена;
- [ ] кандидатный контракт минимален и не зависит от устройства реализации;
- [ ] положительный и отрицательный корпуса достаточны;
- [ ] циклы и самоссылки проверены там, где это существенно;
- [ ] техническое тождество не просочилось в семантику;
- [ ] граница чтения и эффекта задана явно;
- [ ] некорректные входные данные отклоняются предсказуемо;
- [ ] существует исполнимая эталонная модель;
- [ ] независимая или дифференциальная проверка существует там, где она нужна;
- [ ] документация, контракт и корпус соответствия согласованы;
- [ ] известен план миграции потребителей;
- [ ] выполнено явное принятие владельцем теории;
- [ ] устаревшая активная семантика удаляется без режима совместимости.

## Версионирование контрактов

Версия принятой машинной границы меняется, когда меняется наблюдаемая принятая семантика либо состав текущего выпуска так, что потребитель должен перепривязаться к новой версии.

Автоматическая смена версии не требуется для:

- внутреннего рефакторинга;
- оптимизации производительности;
- нового индекса или кэша;
- уточнения документации без наблюдаемого изменения;
- новых отрицательных тестов, которые только выявляют уже действующее требование.

Если старый принятый контракт оказался неоднозначным, нельзя молча переписать его так, чтобы менялся наблюдаемый результат.

## Межъязыковое соответствие

Во время миграции Python → `TypeScript` переносимый корпус исполнялся двумя независимыми реализациями. После принятого перехода Python удалён из активного дерева, а доказательная история сохранена Git.

Будущая независимая реализация должна сравниваться по нормализованным наблюдаемым результатам, а не по техническим адресам объектов.

## Доверенное ядро и внешние инструменты

Предпочтительная схема:

```text
поиск / эвристики / интерфейс / оптимизация
        = недоверенный производитель

переносимое свидетельство
        ↓
маленькая проверка / replay
        = доверенный потребитель
```

## Принятие без копий совместимости

После принятия фундаментального кандидата:

1. потребители переводятся на новый канонический путь;
2. машинный контракт обновляется, если изменилась принятая граница;
3. устаревшая активная реализация удаляется после перехода последнего потребителя;
4. CI запрещает возвращение параллельной активной реализации;
5. история остаётся в Git, задачах и запросах на слияние.

## Ограничения

Изменение существующей теории, нотации, формата, эталонной модели или корневой формулы должно выполняться отдельной задачей. Рефакторинг не должен вводить новую семантику скрыто.

Зелёные тесты подтверждают реализацию текущих требований, но не принимают новую фундаментальную семантику автоматически.

Защищённый файл `docs/research/Исходные мысли МТС.md` изменяется только владельцем репозитория.

## Проверка

```bash
cd ts
npm ci
npm run typecheck
npm test
npm run browser:check
```

Полный CI дополнительно выполняет структурные и документационные проверки и отдельный запрет на возвращение Python. Кодировка текстовых файлов — UTF-8.
