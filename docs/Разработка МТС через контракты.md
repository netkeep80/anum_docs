# Разработка МТС через контракты

Этот документ — практическое руководство по contract-driven разработке МТС.

Его цель — сделать процесс воспроизводимым вручную: если автоматизация, ИИ-помощник или часть tooling недоступны, разработку можно продолжить, последовательно проверяя теорию, контракт, корпус соответствия, TypeScript-реализацию и evidence.

Документ **не определяет семантику МТС**. Нормативный смысл находится в `docs/theory/**` и `docs/specs/**`; принятая машинная граница определяется текущей accepted-парой contract/conformance, указанной в `repo-policy.json` и cutover evidence.

---

## 1. Главная идея

МТС нельзя определять через текущее поведение программы.

Неверное направление:

```text
код делает X
=> значит МТС означает X
```

Правильное направление:

```text
теоретический смысл
        ↓
явное семантическое решение
        ↓
candidate contract
        ↓
conformance + negative vectors
        ↓
TypeScript implementation
        ↓
executable evidence
        ↓
explicit acceptance
        ↓
accepted contract
```

Код является **реализацией смысла**, а не его источником.

Это позволяет:

- менять внутреннюю архитектуру без изменения теории;
- обнаруживать semantic drift;
- безопасно разрабатывать будущую версию рядом с accepted-версией;
- проверять разные реализации одной и той же семантики;
- отделять исследование от принятого машинного поведения;
- делать фундаментальные изменения пошагово, а не big-bang rewrite.

## 2. Какие сущности участвуют в процессе

### 2.1. Нормативная теория

Находится прежде всего в:

```text
docs/theory/**
docs/specs/**
```

Отвечает на вопрос:

> Что означает конструкция МТС?

Теория не должна зависеть от названий TypeScript-классов, runtime handle, storage ID, порядка allocation или конкретного parser API.

### 2.2. Contract

Contract — машиночитаемая проекция принятой или кандидатной теории на наблюдаемую машинную границу.

Он отвечает на вопрос:

> Что обязана соблюдать любая корректная реализация?

Contract фиксирует только существенные observables:

- смысловые роли входов;
- допустимые и недопустимые формы;
- семантический результат;
- инварианты тождества;
- canonicalization;
- read/write boundary;
- versioned surfaces;
- обязательные veto.

Contract **не должен без необходимости фиксировать implementation details**.

Например, плохо:

```json
{
  "rootRuntimeId": 17,
  "sequenceClass": "ExactSequenceImpl",
  "cacheSlot": 4
}
```

Потому что `17`, имя класса и cache slot не являются смыслом МТС.

Лучше:

```json
{
  "root": "R = R ⟼ R",
  "runtimeHandleIsSemanticIdentity": false,
  "readMayMaterialize": false
}
```

### 2.3. Conformance

Conformance — набор требований, по которым можно проверить реализацию contract.

Он отвечает на вопрос:

> Как доказать, что реализация действительно соблюдает contract?

Обычно в нём есть:

```text
positive vectors
negative vectors
carrier vectors
sequence vectors
semantic rule vectors
required executable gates
```

### 2.4. Executable evidence

Executable evidence — реальные тесты, differential checks, replay/checker или другие исполняемые доказательства, которые реализуют заявленные conformance requirements.

Важно различать:

```text
"vector записан в JSON"
```

и

```text
"vector реально проверяется blocking CI"
```

Первое — декларация. Второе — evidence.

### 2.5. Implementation

Текущая implementation МТС находится в TypeScript.

Она должна:

```text
реализовывать contract
```

но не должна:

```text
тайно расширять contract собственным поведением
```

Если в коде появляется новое наблюдаемое правило, сначала надо решить: это implementation detail или semantic delta.

### 2.6. Acceptance

Acceptance — отдельное явное действие.

Green CI **не означает**, что candidate автоматически стал accepted.

Правило:

```text
implemented == true
```

не означает:

```text
accepted == true
```

Candidate может быть полностью исполним и всё ещё оставаться candidate, пока не выполнены все semantic и governance gates.

## 3. Иерархия источников истины

При конфликте источников нельзя выбирать тот, который удобнее.

Используется следующий порядок рассуждения:

```text
нормативная теория / explicit semantic decision
        ↓
accepted contract
        ↓
accepted conformance
        ↓
executable evidence
        ↓
implementation
```

GitHub issues, PR и research notes могут содержать будущие candidates, гипотезы и rejected alternatives. Они не меняют accepted semantics сами по себе.

Если:

```text
код != accepted contract
```

то сначала предполагается defect реализации.

Если:

```text
теория != accepted contract
```

нужно определить, это:

- clarification без observable delta;
- ошибка accepted boundary;
- новая semantic version.

Нельзя просто переписать contract под текущее поведение кода.

## 4. Минимальный observable contract

Хороший contract маленький.

Он фиксирует не всё, что делает программа, а только то, что обязана воспроизводить независимая реализация.

### В contract обычно стоит включать

```text
semantic inputs
canonical result
identity rules
rejection/error category
read/write effect
normalization
version relation
negative vetoes
```

### В contract обычно не стоит включать

```text
runtime pointer identity
storage row ID
allocation order
TypeScript object shape
private helper names
cache/index layout
stack trace text
incidental iteration order
UI representation
```

### Пример

Пусть две связи имеют одинаковые semantic poles:

```text
A ⟼ B
A ⟼ B
```

Смысловой invariant:

```text
same ordered semantic poles
=> same semantic Link
```

Нельзя добавить в contract:

```text
link #41 != link #72
```

только потому, что storage выдал разные номера.

## 5. Contract и conformance всегда рассматриваются вместе

Contract отвечает:

```text
что является нормой
```

Conformance отвечает:

```text
как эту норму проверять
```

Для фундаментального инварианта желательно иметь три уровня:

```text
1. русское нормативное определение
2. machine-readable contract field
3. executable positive/negative evidence
```

Пример:

### Теория

```text
R — единственная полностью самозамкнутая semantic Link.
```

### Contract

```json
{
  "root": "R = R ⟼ R",
  "secondFullySelfClosedRootAllowed": false
}
```

### Positive evidence

```text
ensure(R, R) возвращает R
```

### Negative evidence

```text
попытка представить второй независимый fully-selfclosed root
не должна создавать вторую semantic Link
```

Positive tests показывают ожидаемое поведение.
Negative tests защищают границы смысла.

В фундаментальной части МТС negative vectors часто важнее happy path.

## 6. Проверка на опровержение

Обычный unit test спрашивает:

> Работает ли написанная функция?

Challenge спрашивает:

> Каким способом эта модель может быть неправильной?

Для фундаментальных candidates следует специально искать:

- collision;
- alias ambiguity;
- второй root;
- runtime-ID identity leakage;
- source-position identity leakage;
- malformed forms;
- cycles;
- ambiguous recursive forms;
- read → write leakage;
- hidden parser state;
- callback/opcode semantics;
- equivalent spellings с разным результатом;
- разные spellings, ошибочно схлопнутые в один результат;
- ошибки cross-language normalization.

### Пример

Предположим, предложена sequence encoding:

```text
Seq([]) = R
Seq([x]) = R ⟼ x
```

Сразу надо проверить:

```text
Seq([])
Seq([R])
```

Если обе формы дают `R`, encoding потерял позицию корня.

Такой counterexample полезнее десятка happy-path тестов с `L`, `U`, `O`, `C`.

После обнаружения collision сначала исправляется модель, а не тест.

## 7. Жизненный цикл semantic change

Рекомендуемая последовательность:

```text
Research
  ↓
Problem
  ↓
Semantic decision
  ↓
Candidate contract/conformance
  ↓
Challenge
  ↓
Implementation
  ↓
Evidence binding
  ↓
Readiness
  ↓
Explicit acceptance
  ↓
Release cleanup
```

### 7.1. Research

Есть идея, но ещё неизвестно, должна ли она менять accepted semantics.

Разрешены альтернативы и counterexamples.

На этом этапе не надо создавать version bump только потому, что появилась гипотеза.

### 7.2. Problem

Нужно сформулировать проблему **без ссылки на желаемую реализацию**.

Плохо:

```text
Нам нужен новый класс ByteCarrier.
```

Лучше:

```text
Текущий source boundary получает 256 opaque byte refs извне,
поэтому происхождение semantic Byte(p) не выражено через Q structure.
```

### 7.3. Semantic decision

До implementation должно быть понятно, какой смысл выбран.

Например:

```text
Rep_SQ(bytes)
= одна [8 bits] Q-группа на каждый exact byte

Byte(p)
:= Denote_Q([p])
```

После этого уже можно писать candidate contract.

### 7.4. Candidate contract/conformance

Candidate должен быть явно не accepted:

```text
status = candidate
accepted = false
acceptanceReady = false
```

Нельзя делать incomplete candidate видимо complete с помощью invented evidence.

Если slice ещё не реализован, статус должен честно говорить:

```text
planned
```

а не:

```text
green
```

### 7.5. Challenge

До или вместе с implementation создаются vectors, которые должны сломать плохие варианты модели.

### 7.6. Implementation

Implementation пишется под уже выбранный смысл.

Если во время кодирования обнаружилось, что contract невозможно реализовать без нового semantic assumption, надо остановить semantic drift и вернуть вопрос на уровень theory/decision.

### 7.7. Evidence binding

После появления реально зелёного теста candidate contract/conformance связывается с ним.

Правильный порядок:

```text
реальный test появился и green
        ↓
contract/conformance заявляет этот evidence
```

Неправильный:

```text
contract заранее объявил несуществующий evidence green
        ↓
когда-нибудь потом напишем test
```

### 7.8. Readiness

`acceptanceReady=true` разрешено только когда выполнены все обязательные slices и нет известного veto.

### 7.9. Explicit acceptance

Acceptance выполняется отдельным lifecycle step.

Типичная ротация:

```text
до:
previous = vN-1
current  = vN
candidate = vN+1

после:
previous = vN
current  = vN+1
```

Старый live runtime не сохраняется как compatibility island без отдельной причины.

Git уже хранит историю.

## 8. Когда нужна новая contract version

Новая версия нужна, если меняется accepted observable machine boundary.

### Обычно требует version bump

- меняется canonical representation;
- один и тот же вход теперь имеет другой semantic result;
- меняется identity invariant;
- ранее допустимая форма становится недопустимой или наоборот;
- меняется read/write effect;
- появляется новая обязательная semantic role;
- меняется внешний versioned surface, требующий repin consumer-а.

### Обычно не требует version bump

- refactoring;
- переименование private helper;
- новый cache;
- новый index;
- performance optimization;
- замена алгоритма при одинаковых observables;
- усиление тестов, которое только доказывает уже существующее правило;
- docs clarification без изменения смысла.

### Простая таблица решения

| Изменение | Contract | Conformance | Version |
|---|---|---|---|
| internal refactor | без изменения | старые tests должны пройти | та же |
| новый negative test уже принятого правила | обычно без изменения | усилить | та же |
| уточнение текста без observable delta | возможно docs only | без изменения | та же |
| новый observable semantic result | новый candidate | новый corpus | новая |
| новый representation boundary | новый candidate | новые carrier vectors | новая |

## 9. Пример 1: обычный refactoring

Допустим, `Memory` внутри заменяет один индекс на два более быстрых индекса.

До и после:

```text
ensure(A, B) -> та же semantic Link
find(A, B)   -> тот же результат
read         -> не пишет
```

Это implementation-only change.

Нужно:

```text
изменить TypeScript
запустить весь accepted conformance
добавить regression tests при необходимости
```

Не нужно:

```text
новый contract version
candidate lifecycle
acceptance rotation
```

---

## 10. Пример 2: semantic delta

Предположим, старое tooling кодирует Unicode code point одной Q-группой, содержащей все UTF-8 bytes.

Новая theory decision:

```text
каждый exact byte имеет собственную [8 bits] Q-группу
```

Для ASCII `A` различия может не быть:

```text
A = 0x41
=> [01000001]
```

Но для многобайтового UTF-8 символа representation меняется.

Значит это нельзя тихо переписать в accepted contract.

Правильная работа:

```text
1. записать semantic decision
2. завести candidate version
3. добавить carrier vectors
4. добавить malformed UTF-8 vectors
5. реализовать canonical per-byte carrier
6. доказать Byte(p) через Q structure
7. связать executable evidence
8. только после полной готовности принять новую версию
```

Хороший negative vector:

```text
256 произвольных runtime IDs не должны считаться semantic byte vocabulary
```

## 11. Пример 3: read не должен становиться write

В МТС принципиально различаются:

```text
find / read / replay / verify
```

и

```text
materialize / ensure / write
```

Допустим verifier проверяет evidence.

Плохая реализация:

```text
не нашёл нужную Link
=> создал её
=> verification прошёл
```

Так verifier сам создаёт доказательство, которое должен был только проверить.

Contract должен явно задавать:

```text
readMayMaterialize = false
replayMayMaterialize = false
```

Test должен измерить состояние до и после:

```text
before = linkCount
replay(...)
after = linkCount

assert(before == after)
```

Это пример observable effect, который обязательно входит в contract.

---

## 12. Пример 4: host code не должен быть скрытой теорией

Плохо, если смысл определяется выбором callback:

```text
if kind == "RELATION": replayRelation()
if kind == "COLON":    replayColon()
```

а сам `kind` существует только как TypeScript enum.

Тогда реальная теория находится в host program control flow.

Предпочтительное направление:

```text
I    = D ⟼ (G ⟼ T)
DR   = DR ⟼ RoleSequence
Rule = DR ⟼ Body
T ⟼ Rule
Act  содержит role bindings
```

а generic replay читает structural Rule и evidence.

TypeScript может иметь удобные wrappers, но wrapper не должен становиться semantic authority.

Проверочный вопрос:

> Может ли независимая реализация понять, какое правило применить, читая только semantic structure и contract, без знания имени TypeScript-функции?

Если нет — часть semantics, вероятно, всё ещё скрыта в host code.

## 13. Как работать вручную: полный алгоритм

Ниже минимальный порядок действий, который можно выполнять без ИИ.

### Шаг 1. Зафиксировать актуальный `main`

Перед работой определить exact current commit SHA.

Не начинать новый semantic slice от старой ветки, если `main` уже изменился.

### Шаг 2. Найти accepted boundary

Открыть:

```text
repo-policy.json
contracts/
cutover/
```

Проверить:

```text
какой contract = current
какой conformance = current
какой = previous
есть ли candidate
accepted/status fields
```

Никогда не определять current version по памяти.

### Шаг 3. Прочитать соответствующую theory/spec

До изменения runtime выписать смысл простыми словами.

Если смысла ещё нет — это research task, а не implementation task.

### Шаг 4. Классифицировать изменение

Выбрать ровно один основной класс:

```text
THEORY CLARIFICATION
IMPLEMENTATION REFACTOR
CONFORMANCE HARDENING
PACKAGING/CUTOVER
SEMANTIC DELTA
```

Если это `SEMANTIC DELTA`, accepted contract нельзя менять in-place.

### Шаг 5. Сформулировать problem statement

Формулировка должна быть независима от будущего кода.

Минимум ответить:

```text
что сейчас не выражено/неверно?
какие observables должны различаться?
какой counterexample показывает проблему?
```

### Шаг 6. Принять semantic decision

До implementation записать выбранное правило.

Для фундаментальной конструкции желательно иметь equation/form.

### Шаг 7. Составить vectors

Минимум:

```text
happy path
empty/root boundary
repeated values
malformed input
identity attack
read/write attack
```

Добавить domain-specific counterexamples.

### Шаг 8. Создать или дополнить candidate

Только при реальном semantic delta.

Candidate должен оставаться:

```text
accepted=false
acceptanceReady=false
```

до полного завершения lifecycle.

### Шаг 9. Реализовать маленький slice

Не делать сразу весь будущий runtime.

Предпочтительно:

```text
один semantic invariant
+ один implementation owner
+ один focused executable gate
```

### Шаг 10. Проверить read/write boundary

Каждый verifier/replay/read path проверить на отсутствие скрытой материализации.

### Шаг 11. Запустить полный TypeScript check

Из `ts/` используется проектный `npm run check`, который должен включать typecheck, tests и browser checks согласно текущему `package.json`.

Нельзя считать focused test заменой полного project CI.

### Шаг 12. Связать evidence с candidate

Только после появления real green evidence.

Contract/conformance должны указывать реальные owner paths и реальные executable gates.

### Шаг 13. Провести PR через repo-guard

PR должен быть узким и объяснять expected effects.

Не обходить repo-guard изменением low-level Git objects или альтернативным write path.

### Шаг 14. Проверить merge gates

Перед merge:

```text
full CI green
blocking repo-guard green
branch behind_by = 0
PR mergeable
head SHA стабилен
```

Merge выполнять с expected head SHA, если tooling это поддерживает.

### Шаг 15. Проверить post-merge main

После merge работа не закончена.

Нужно проверить:

```text
exact new main SHA
post-merge CI именно на этом состоянии
```

### Шаг 16. Не принимать candidate раньше времени

Implementation slice может стать:

```text
candidate-green
```

но весь release остаётся:

```text
accepted=false
acceptanceReady=false
```

пока не завершены остальные обязательные slices.

## 15. Минимальный шаблон implementation PR

Пример структуры PR description:

```markdown
Implementation slice для #NNN.

Что реализовано:
- ...
- ...

Что намеренно не меняется:
- accepted current contract
- unrelated public API
- cutover pointers

Semantic invariants:
- ...

Executable evidence:
- ...

```repo-guard-yaml
change_type: feature
scope:
  - ts/src/example.ts
  - ts/test/example.test.ts
budgets:
  max_new_files: 2
  max_new_docs: 0
  max_net_added_lines: 500
must_touch:
  - ts/src/example.ts
  - ts/test/example.test.ts
must_not_touch:
  - contracts/**
  - cutover/**
expected_effects:
  - implement one candidate invariant
  - preserve accepted semantics
```
```

Точные допустимые поля repo-guard нужно сверять с текущей policy/tooling, а не копировать старый PR вслепую.

## 16. Почему implementation и governance evidence полезно разделять

Для фундаментального slice часто безопаснее два PR.

### PR A — implementation

```text
TypeScript code
focused tests
accepted boundary не меняется
```

После merge evidence реально существует в `main`.

### PR B — governance projection

```text
candidate contract
candidate conformance
repo-policy evidence binding
```

Теперь contract связывается с уже существующим green evidence.

Преимущества:

- нельзя заявить несуществующий test как доказательство;
- проще review;
- меньше governance scope;
- repo-guard получает понятный diff;
- semantic acceptance не смешивается с implementation merge.

Это не абсолютное правило для любого маленького изменения, но хороший default для фундаментальной candidate semantics.

## 17. Repo-guard как проверка связности процесса

Repo-guard должен проверять не саму теорию МТС, а governance invariants репозитория.

Предпочтительно использовать generic constraints:

```text
document relations
cochange rules
referenced paths exist
evidence bindings
workflow path coverage
anchors
budgets
```

Не надо добавлять MTS-specific validator, если invariant уже выражается существующей generic Constraint Program.

Новая возможность repo-guard оправдана, когда можно показать конкретный invariant, который принципиально нельзя выразить текущими generic primitives.

### Пример

Если candidate conformance содержит:

```text
requiredExecutableGates = ["ts/test/x.test.ts"]
```

repo-guard должен уметь проверить хотя бы:

```text
путь существует
project CI покрывает ts/test/**
```

Для negative vectors желательно также иметь evidence binding, которая доказывает, что каждый declared vector связан с реальным test anchor до acceptance.

## 18. Как не превратить contracts в бюрократию

Contract-driven development не означает:

```text
JSON на каждую функцию
JSON на каждый класс
новый contract на каждый refactor
```

Плохой результат — когда contract повторяет структуру implementation.

Хороший результат — когда contract остаётся маленькой независимой границей.

Перед добавлением поля спросить:

> Если завтра TypeScript будет полностью переписан, должна ли независимая корректная реализация знать это поле?

Если ответ «нет», вероятно, поле не относится к contract.

---

## 19. Как понять, что slice закончен

Slice можно считать machine-complete, когда одновременно верны условия:

```text
semantic decision существует
contract projection не врёт
positive vectors исполнимы
negative vectors исполнимы
implementation owner существует
focused test green
full project CI green
repo-guard green
evidence реально связано с candidate
read/write boundary доказана
accepted current не изменён случайно
```

Но это всё ещё не обязательно означает release acceptance.

## 20. Как понять, что release можно принимать

Перед `acceptanceReady=true` пройти checklist:

- [ ] все обязательные semantic decisions закрыты;
- [ ] candidate contract согласован с theory;
- [ ] candidate conformance согласован с contract;
- [ ] все required implementation slices green;
- [ ] каждый required executable gate существует и запускается blocking CI;
- [ ] required negative vectors имеют реальное evidence;
- [ ] malformed cases fail-closed;
- [ ] technical identity не просочилась в semantics;
- [ ] read/replay не материализуют;
- [ ] нет hidden parser/callback/opcode semantic authority;
- [ ] public/tooling deltas классифицированы;
- [ ] migration/cutover plan известен;
- [ ] governance debt имеет план погашения;
- [ ] full CI green;
- [ ] blocking repo-guard green;
- [ ] explicit owner acceptance выполняется отдельным действием.

Если хотя бы один обязательный пункт неизвестен, правильное значение:

```text
acceptanceReady=false
```

## 21. Частые ошибки

### Ошибка: «тесты зелёные, значит версия принята»

Нет. Tests доказывают implementation state; acceptance — отдельное semantic/governance решение.

### Ошибка: менять accepted JSON in-place

Если observable semantics изменилась, нужен candidate version.

### Ошибка: сначала написать код, потом объявить его теорией

Implementation может обнаружить проблему, но не имеет права автоматически решать её смысл.

### Ошибка: сохранять старый runtime «на всякий случай»

После explicit cutover история уже находится в Git. Compatibility layer требует самостоятельного обоснования.

### Ошибка: считать runtime ID смысловым тождеством

Technical storage identity не создаёт semantic Link identity.

### Ошибка: verifier создаёт недостающие данные

`not found != does not exist`, но verification также не имеет права превращать отсутствие evidence в собственную materialization.

### Ошибка: contract описывает private TypeScript architecture

Это связывает теорию с одной реализацией и уничтожает главное преимущество подхода.

### Ошибка: candidate contract перечисляет будущие tests как уже green

Evidence разрешено утверждать только после появления evidence.

## 22. Что смотреть в репозитории при ручном продолжении

В начале каждой сессии полезно пройти этот порядок:

```text
1. latest main SHA
2. open PR
3. open owner/gate issues
4. repo-policy.json
5. contracts/current + previous + candidate
6. cutover evidence
7. relevant docs/theory/**
8. relevant docs/specs/**
9. TypeScript owner files
10. tests, на которые ссылается conformance
11. latest CI/repo-guard result
```

Не опираться на старый checkpoint, если GitHub показывает другое состояние.

## 23. Короткая памятка

Если нужно продолжить разработку МТС вручную и времени мало, держать перед глазами следующий алгоритм:

```text
1. Что сейчас accepted?
2. Что именно в теории я хочу изменить?
3. Это observable semantic delta?
4. Какой counterexample показывает необходимость изменения?
5. Как выглядит минимальный candidate contract?
6. Какие positive и negative vectors его опровергают/подтверждают?
7. Какой самый маленький TypeScript slice это реализует?
8. Проверяет ли replay/read отсутствие write?
9. Реально ли test запускается full CI?
10. Связан ли evidence с candidate?
11. Остался ли accepted current неизменным?
12. Выполнены ли merge gates?
13. Проверен ли exact post-merge main?
14. Только после полной readiness — explicit acceptance.
```

Главный принцип можно свести к одной строке:

```text
Смысл → контракт → проверка → реализация → доказательство → принятие.
```

Никогда не наоборот.
