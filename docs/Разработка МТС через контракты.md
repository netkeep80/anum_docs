# Разработка МТС через контракты

Это практическое руководство по разработке МТС через контракты (`contract-driven development`).

Его цель — сделать процесс воспроизводимым вручную. Если ИИ-помощник или часть автоматизации недоступны, разработку можно продолжить, последовательно проверяя теорию, контракт, корпус соответствия, реализацию на `TypeScript` и исполнимые свидетельства.

Документ **не определяет семантику МТС**. Нормативный смысл находится в `docs/theory/**` и `docs/specs/**`. Принятая машинная граница определяется текущей парой контракт/корпус соответствия, на которую указывает `repo-policy.json` и свидетельство переключения выпуска в `cutover/`.

---

## 1. Главная идея

МТС нельзя определять через текущее поведение программы.

Неверно:

```text
код делает X
=> значит МТС означает X
```

Правильно:

```text
теоретический смысл
        ↓
явное смысловое решение
        ↓
кандидатный контракт
        ↓
корпус соответствия
        ↓
реализация
        ↓
исполняемые проверки
        ↓
явное принятие
        ↓
принятый контракт
```

Код является реализацией смысла, а не его источником.

Такой порядок позволяет:

- менять внутреннюю архитектуру без изменения теории;
- обнаруживать скрытое изменение семантики;
- безопасно разрабатывать будущую версию рядом с принятой;
- проверять разные реализации одной и той же семантики;
- отделять исследование от принятого машинного поведения;
- делать фундаментальные изменения небольшими проверяемыми шагами.

## 2. Пять основных частей процесса

### 2.1. Нормативная теория

Основные места:

```text
docs/theory/**
docs/specs/**
```

Теория отвечает на вопрос:

> Что означает конструкция МТС?

Теория не должна зависеть от названий классов, технических идентификаторов, порядка выделения памяти или конкретного программного интерфейса.

### 2.2. Контракт

Контракт — машиночитаемая проекция принятой или кандидатной теории на наблюдаемую машинную границу.

Он отвечает на вопрос:

> Что обязана соблюдать любая корректная реализация?

Контракт обычно фиксирует:

- смысловые роли входов;
- допустимые и недопустимые формы;
- смысловой результат;
- инварианты тождества;
- требования канонизации;
- границу чтения и изменения;
- отношение версий;
- обязательные запреты.

Контракт не должен без причины фиксировать детали одной реализации.

Плохо:

```json
{
  "rootRuntimeId": 17,
  "sequenceClass": "ExactSequenceImpl",
  "cacheSlot": 4
}
```

Хорошо:

```json
{
  "root": "R = R ⟼ R",
  "runtimeHandleIsSemanticIdentity": false,
  "readMayMaterialize": false
}
```

В первом примере числа и имена программных сущностей случайны. Во втором примере записаны наблюдаемые требования.

### 2.3. Корпус соответствия

Корпус соответствия отвечает на вопрос:

> Как проверить, что реализация действительно соблюдает контракт?

В нём могут находиться:

```text
requiredPositiveVectors
requiredNegativeVectors
requiredCarrierVectors
requiredSequenceVectors
requiredSemanticRuleVectors
requiredExecutableGates
```

Особенно важны отрицательные векторы. Они показывают не только правильный результат, но и то, какие неправильные модели должны быть отвергнуты.

### 2.4. Исполнимое свидетельство

Запись требования в файле ещё не доказывает его выполнение.

Нужно различать:

```text
требование перечислено
```

и

```text
требование реально проверяется тестом,
а тест входит в блокирующую проверку проекта
```

Второе является исполнимым свидетельством.

### 2.5. Реализация

Текущая реализация МТС написана на `TypeScript`.

Она должна реализовывать контракт, но не должна незаметно расширять его собственным поведением.

Если в коде появляется новое наблюдаемое правило, необходимо определить:

```text
это внутренняя деталь реализации?
или это изменение семантики?
```

## 3. Принятие — отдельное действие

Зелёные тесты не означают, что кандидат автоматически стал принятой версией.

```text
реализовано
!=
принято
```

Кандидат может быть полностью исполним и оставаться кандидатом:

```text
status = candidate
accepted = false
acceptanceReady = false
```

Явное принятие выполняется только после завершения всех обязательных смысловых и машинных проверок.

Это защищает МТС от ситуации:

```text
мы написали код
=> код прошёл тесты
=> теперь считаем его новой теорией
```

## 4. Иерархия источников истины

При конфликте источников используется направление:

```text
нормативная теория / явное смысловое решение
        ↓
принятый контракт
        ↓
принятый корпус соответствия
        ↓
исполняемые проверки
        ↓
реализация
```

Задачи GitHub, запросы на слияние и исследовательские заметки могут содержать будущие варианты и отклонённые гипотезы. Они сами по себе не меняют принятую семантику.

Если:

```text
код != принятый контракт
```

сначала предполагается ошибка реализации.

Если:

```text
теория != принятый контракт
```

нужно определить, что произошло:

- уточнение текста без изменения наблюдаемого поведения;
- обнаружение ошибки в принятой границе;
- новое смысловое изменение, требующее новой версии.

Нельзя просто переписать контракт под текущее поведение кода.

## 5. Минимальная наблюдаемая граница

Хороший контракт маленький.

Он фиксирует только то, что должна воспроизвести независимая корректная реализация.

Обычно стоит фиксировать:

```text
смысловые входы
канонический результат
правила тождества
категорию отказа
границу чтения/изменения
канонизацию
отношение версий
обязательные запреты
```

Обычно не стоит фиксировать:

```text
технический номер объекта
номер строки хранилища
порядок выделения памяти
имя внутреннего класса
внутренний кэш
текст трассировки исключения
случайный порядок обхода
представление интерфейса пользователя
```

### Простой пример

Пусть имеются две записи:

```text
A ⟼ B
A ⟼ B
```

Если смысловое тождество связи определяется упорядоченными полюсами, то две технические записи не должны создавать две смысловые связи.

Контракт должен защищать правило:

```text
same ordered semantic poles
=> same semantic Link
```

но не должен закреплять случайные номера записей в памяти.

## 6. Контракт и корпус соответствия образуют пару

Контракт отвечает:

```text
что является нормой
```

Корпус соответствия отвечает:

```text
как эту норму проверить
```

Для важного инварианта желательно иметь три формы:

```text
1. русское нормативное определение
2. машиночитаемое поле контракта
3. исполнимую положительную и отрицательную проверку
```

### Пример с корнем

Нормативное утверждение:

```text
R — единственная полностью самозамкнутая смысловая связь.
```

Контракт:

```json
{
  "root": "R = R ⟼ R",
  "secondFullySelfClosedRootAllowed": false
}
```

Положительная проверка:

```text
ensure(R, R) возвращает R
```

Отрицательная проверка:

```text
нельзя получить второй независимый полностью самозамкнутый смысловой корень
```

Положительный пример показывает ожидаемое поведение.
Отрицательный пример защищает границу смысла.

## 7. Проверка на опровержение

Обычный модульный тест часто спрашивает:

> Работает ли написанная функция?

Проверка на опровержение спрашивает:

> Каким способом предложенная модель может быть неправильной?

Для фундаментальных конструкций полезно специально искать:

- столкновения разных форм в один результат;
- ложное различие по техническим идентификаторам;
- второй корень;
- потерю позиции корня в последовательности;
- циклические и самоссылочные контрпримеры;
- некорректные формы;
- скрытое изменение памяти при чтении;
- скрытое значение режима анализатора;
- зависимость смысла от имени программной функции;
- неоднозначность разных представлений одного носителя.

### Пример: плохая последовательность

Предположим:

```text
Seq([]) = R
Seq([x]) = R ⟼ x
```

Нужно немедленно сравнить:

```text
Seq([])
Seq([R])
```

Если обе формы дают `R`, модель потеряла позицию корня.

Такой контрпример важнее большого числа обычных примеров с `L`, `U`, `O`, `C`.

После обнаружения столкновения исправляется модель, а не тест.

## 8. Жизненный цикл смыслового изменения

Рекомендуемый порядок:

```text
исследование
  ↓
точная проблема
  ↓
смысловое решение
  ↓
кандидатный контракт + корпус
  ↓
проверка на опровержение
  ↓
реализация
  ↓
привязка исполнимых свидетельств
  ↓
готовность к принятию
  ↓
явное принятие
  ↓
очистка выпуска
```

### 8.1. Исследование

Есть идея, но ещё неизвестно, должна ли она менять принятую семантику.

На этом этапе допустимы альтернативы и контрпримеры. Не нужно создавать новую версию только потому, что появилась гипотеза.

### 8.2. Точная проблема

Проблема должна быть сформулирована без ссылки на желаемый класс или функцию.

Плохо:

```text
Нужен новый класс ByteCarrier.
```

Лучше:

```text
Текущая граница source получает 256 непрозрачных ссылок на байты извне,
поэтому происхождение Byte(p) не выражено через структуру Q.
```

### 8.3. Смысловое решение

До реализации должно быть понятно, какое правило выбрано.

Например:

```text
Rep_SQ(bytes)
= одна [8 bits] Q-группа на каждый точный байт

Byte(p)
:= Denote_Q([p])
```

После этого можно писать кандидатный контракт.

### 8.4. Кандидатный контракт

Кандидат должен честно показывать незавершённость:

```text
status = candidate
accepted = false
acceptanceReady = false
```

Если шаг ещё не реализован:

```text
status = planned
```

Нельзя объявлять будущий тест уже зелёным.

### 8.5. Реализация

Реализация пишется под уже выбранный смысл.

Если во время программирования выяснилось, что контракт невозможно реализовать без нового смыслового предположения, вопрос нужно вернуть на уровень теории и решения.

### 8.6. Привязка свидетельств

Правильный порядок:

```text
реальный тест появился
↓
тест прошёл
↓
кандидатный контракт/корпус ссылается на этот тест
```

Неправильный порядок:

```text
сначала объявить свидетельство существующим
↓
потом когда-нибудь написать тест
```

### 8.7. Готовность и принятие

`acceptanceReady=true` разрешено только после выполнения всех обязательных шагов и устранения известных запретов.

Принятие выполняется отдельным действием.

Типичная ротация:

```text
до:
previous = vN-1
current  = vN
candidate = vN+1

после:
previous = vN
current  = vN+1
```

Старая действующая реализация не сохраняется «на всякий случай», если отдельный режим совместимости не нужен по реальному требованию. История уже находится в Git.

## 9. Когда нужна новая версия контракта

Новая версия нужна, если меняется принятая наблюдаемая машинная граница.

Обычно требует новой версии:

- другое каноническое представление;
- другой смысловой результат для того же входа;
- другое правило тождества;
- изменение допустимости формы;
- изменение границы чтения и изменения;
- новая обязательная смысловая роль;
- изменение внешней границы, требующее переключения потребителя.

Обычно не требует новой версии:

- рефакторинг;
- новый кэш;
- новый индекс;
- ускорение алгоритма;
- замена внутреннего алгоритма при тех же результатах;
- усиление тестов уже принятого правила;
- уточнение документации без изменения наблюдаемого смысла.

### Таблица решения

| Изменение | Контракт | Корпус | Версия |
|---|---|---|---|
| внутренний рефакторинг | без изменения | старые проверки проходят | та же |
| новый отрицательный тест принятого правила | обычно без изменения | усилить | та же |
| уточнение текста | без изменения | без изменения | та же |
| новый смысловой результат | новый кандидат | новый корпус | новая |
| новое каноническое представление | новый кандидат | новые проверки носителя | новая |

## 10. Пример 1: обычный рефакторинг

Допустим, `Memory` заменяет один внутренний индекс на другой.

До и после:

```text
ensure(A, B) -> та же смысловая связь
find(A, B)   -> тот же результат
чтение       -> не изменяет память
```

Это изменение реализации.

Нужно:

```text
изменить TypeScript
запустить полный набор проверок
добавить регрессионный тест при необходимости
```

Не нужно:

```text
новая версия контракта
кандидатный выпуск
ротация accepted/current
```

---

## 11. Пример 2: настоящее смысловое изменение

Предположим, старый преобразователь помещает все байты одного символа Юникода в одну Q-группу.

Новое решение:

```text
каждый точный байт имеет собственную [8 bits] Q-группу
```

Для ASCII `A` различия может не быть:

```text
A = 0x41
=> [01000001]
```

Но для многобайтового UTF-8 символа представление меняется.

Значит нельзя тихо переписать принятый контракт.

Правильная работа:

```text
1. записать смысловое решение
2. завести кандидатную версию
3. добавить проверки носителей
4. добавить проверки неправильного UTF-8
5. реализовать канонический побайтовый носитель
6. доказать Byte(p) через структуру Q
7. связать реальные исполнимые проверки
8. принять новую версию только после полной готовности
```

Хороший отрицательный пример:

```text
256 произвольных runtime ID
не являются смысловым словарём байтов
```

## 12. Пример 3: чтение не должно становиться изменением

В МТС принципиально различаются:

```text
find / read / replay / verify
```

и

```text
materialize / ensure / write
```

Плохая проверка:

```text
не нашла нужную связь
=> создала её
=> после этого объявила доказательство корректным
```

Так проверяющая функция сама создаёт то, что обязана только проверять.

Контракт должен явно защищать, например:

```text
readMayMaterialize = false
replayMayMaterialize = false
```

Исполнимая проверка может сравнить состояние памяти:

```text
before = linkCount
replay(...)
after = linkCount

assert(before == after)
```

Граница эффекта — часть наблюдаемой семантики.

---

## 13. Пример 4: программная функция не должна быть скрытой теорией

Плохо, если смысл определяется только тем, какую функцию вызвала программа:

```text
if kind == "RELATION": replayRelation()
if kind == "COLON":    replayColon()
```

Если `kind` существует только как перечисление в `TypeScript`, часть теории находится в управляющем коде.

Предпочтительное направление:

```text
I    = D ⟼ (G ⟼ T)
DR   = DR ⟼ RoleSequence
Rule = DR ⟼ Body
T ⟼ Rule
Act  содержит role bindings
```

а общий механизм воспроизведения читает структурное правило и его свидетельства.

Контрольный вопрос:

> Может ли независимая реализация понять, какое правило применить, читая только смысловую структуру и контракт, не зная имени функции `TypeScript`?

Если нет, часть семантики, вероятно, всё ещё скрыта в коде среды.

## 14. Полный ручной алгоритм

Ниже порядок, который можно выполнять без ИИ.

### Шаг 1. Зафиксировать актуальный `main`

Определить точный текущий SHA.

Не начинать новый смысловой шаг от старого состояния, если `main` изменился.

### Шаг 2. Найти принятую машинную границу

Открыть:

```text
repo-policy.json
contracts/
cutover/
```

Проверить:

```text
какой contract = current
какой conformance = current
какой = previous
есть ли candidate
какие значения status/accepted
```

Не определять текущую версию по памяти.

### Шаг 3. Прочитать нужную теорию

Открыть соответствующие файлы:

```text
docs/theory/**
docs/specs/**
```

Если смысл ещё не определён, это исследовательская задача, а не задача реализации.

### Шаг 4. Классифицировать изменение

Выбрать основной класс:

```text
THEORY_CLARIFICATION
IMPLEMENTATION_REFACTOR
CONFORMANCE_HARDENING
PACKAGING_CUTOVER
SEMANTIC_DELTA
```

Если это `SEMANTIC_DELTA`, принятый контракт нельзя изменять на месте.

### Шаг 5. Сформулировать проблему

Ответить минимум на три вопроса:

```text
что сейчас не выражено или противоречиво?
какие наблюдаемые случаи должны различаться?
какой контрпример показывает проблему?
```

### Шаг 6. Записать смысловое решение

До реализации сформулировать правило простыми словами и, где возможно, формулой МТС.

### Шаг 7. Составить проверки

Минимальный набор:

```text
обычный случай
пустое значение / корень
повтор значения
некорректный вход
атака на тождество
проверка границы чтения/изменения
```

Добавить специальные контрпримеры конкретной задачи.

### Шаг 8. Создать или дополнить кандидата

Только при настоящем смысловом изменении.

До полной готовности:

```text
accepted=false
acceptanceReady=false
```

### Шаг 9. Реализовать маленький шаг

Предпочтительно:

```text
один смысловой инвариант
+ один узкий владелец реализации
+ одна сфокусированная исполнимая проверка
```

Не переписывать сразу весь будущий исполнитель.

### Шаг 10. Проверить отсутствие скрытой записи

Каждый путь чтения, проверки и воспроизведения проверить на отсутствие создания недостающих связей.

### Шаг 11. Запустить полный проектный набор проверок

Сверить актуальный `ts/package.json`.

В текущей структуре основной набор запускается через:

```text
npm --prefix ts run check
```

Сфокусированный тест не заменяет полную проверку проекта.

### Шаг 12. Связать свидетельство с кандидатом

Только после появления реально зелёного теста.

Контракт и корпус должны указывать существующие пути владельцев и существующие исполнимые проверки.

### Шаг 13. Создать запрос на слияние

Запрос должен быть узким и описывать ожидаемый эффект.

Нельзя обходить `repo-guard` низкоуровневыми операциями Git или альтернативным путём записи.

### Шаг 14. Проверить условия слияния

Перед слиянием:

```text
полный CI зелёный
blocking repo-guard зелёный
behind_by = 0
PR mergeable
head SHA не изменился после проверок
```

Если инструмент поддерживает это, слияние выполнять с ожидаемым SHA головы запроса.

### Шаг 15. Проверить состояние после слияния

Работа не закончена в момент нажатия Merge.

Проверить:

```text
точный новый main SHA
CI именно на новом состоянии main
```

### Шаг 16. Не принимать кандидата раньше времени

Отдельный шаг может получить статус:

```text
candidate-green
```

но весь выпуск остаётся:

```text
accepted=false
acceptanceReady=false
```

пока не завершены остальные обязательные шаги.

## 15. Шаблон задачи на смысловое изменение

```markdown
# Проблема

Что не выражено или противоречиво в текущей модели?

# Принятая граница

Какие текущие инварианты нельзя случайно изменить?

# Смысловое решение

Какое правило выбрано?

# Положительные проверки

- ...
- ...

# Отрицательные проверки

- ...
- ...

# Граница чтения и изменения

Что обязано быть только чтением?

# Владелец реализации

Какой узкий TypeScript-файл реализует решение?

# Передача в контракт

Какие поля кандидатного contract/conformance должны появиться после зелёного evidence?

# Запреты

Что нельзя вводить для удобства реализации?

# Готово, когда

Как выглядит проверяемый результат?
```

Англоязычные машинные имена в таком шаблоне допустимы только как буквальные имена файлов, полей и сущностей.

## 16. Шаблон запроса на слияние реализации

```markdown
Implementation slice для #NNN.

Что реализовано:
- ...

Что намеренно не меняется:
- accepted current contract
- unrelated public API
- cutover pointers

Semantic invariants:
- ...

Executable evidence:
- ...

```repo-guard-yaml
change_type: feature
scope:
  - ts/src/example.ts
  - ts/test/example.test.ts
budgets:
  max_new_files: 2
  max_new_docs: 0
  max_net_added_lines: 500
must_touch:
  - ts/src/example.ts
  - ts/test/example.test.ts
must_not_touch:
  - contracts/**
  - cutover/**
expected_effects:
  - implement one candidate invariant
  - preserve accepted semantics
```
```

Точные допустимые поля нужно всегда сверять с текущей политикой `repo-guard`, а не копировать старый запрос вслепую.

## 17. Почему реализацию и привязку свидетельств полезно разделять

Для фундаментального шага часто безопаснее два запроса на слияние.

Первый:

```text
код TypeScript
сфокусированные тесты
принятая граница не меняется
```

После его слияния свидетельство уже реально существует в `main`.

Второй:

```text
кандидатный контракт
кандидатный корпус
привязка свидетельств в repo-policy
```

Преимущества:

- нельзя заявить несуществующий тест;
- проще проверять изменение;
- меньше область изменения политики;
- принятие не смешивается с обычным слиянием реализации.

Это не обязательное правило для каждого маленького изменения, но хороший исходный вариант для фундаментальной семантики.

---

## 18. Роль `repo-guard`

`repo-guard` должен проверять не саму теорию МТС, а связность и дисциплину репозитория.

Предпочтительно использовать общие ограничения:

```text
document_relations
cochange_rules
referenced_paths_exist
evidence_bindings
workflow_path_coverage
anchors
budgets
```

Не следует добавлять специальный валидатор МТС, если требуемый инвариант уже выражается существующей общей моделью ограничений.

Новая возможность `repo-guard` оправдана, когда есть конкретный инвариант, который действительно нельзя выразить текущими общими средствами.

### Пример

Если кандидатный корпус содержит:

```text
requiredExecutableGates = ["ts/test/x.test.ts"]
```

политика должна уметь проверить хотя бы:

```text
путь существует
проектный CI действительно покрывает ts/test/**
```

До принятия полезно также требовать, чтобы каждый обязательный отрицательный вектор имел реальную привязку к тесту.

---

## 19. Как не превратить подход в бюрократию

Разработка через контракты не означает:

```text
JSON на каждую функцию
JSON на каждый класс
новый контракт на каждый рефакторинг
```

Перед добавлением поля в контракт нужно спросить:

> Если завтра реализация на `TypeScript` будет полностью переписана, должна ли независимая корректная реализация знать это поле?

Если ответ «нет», поле, вероятно, не относится к контракту.

Контракт должен упрощать архитектуру, а не копировать её.

## 20. Когда отдельный шаг закончен

Шаг можно считать машинно завершённым, когда одновременно верно:

- смысловое решение существует;
- контрактная проекция не врёт;
- положительные проверки исполнимы;
- отрицательные проверки исполнимы;
- владелец реализации существует;
- сфокусированный тест зелёный;
- полный проектный набор проверок зелёный;
- `repo-guard` зелёный;
- свидетельство реально связано с кандидатом;
- граница чтения и изменения доказана;
- принятая текущая версия не изменена случайно.

Но это ещё не обязательно означает принятие всего выпуска.

---

## 21. Когда выпуск можно принимать

Перед `acceptanceReady=true` проверить:

- [ ] все обязательные смысловые решения закрыты;
- [ ] кандидатный контракт согласован с теорией;
- [ ] кандидатный корпус согласован с контрактом;
- [ ] все обязательные шаги реализации зелёные;
- [ ] каждая обязательная исполнимая проверка существует и входит в блокирующий CI;
- [ ] обязательные отрицательные векторы имеют реальное свидетельство;
- [ ] некорректные случаи отвергаются закрыто и предсказуемо;
- [ ] техническое тождество не просочилось в семантику;
- [ ] чтение и воспроизведение не материализуют данные;
- [ ] смысл не определяется скрытым режимом анализатора или именем функции;
- [ ] изменения публичной границы классифицированы;
- [ ] план переключения версии известен;
- [ ] временный долг политики имеет план погашения;
- [ ] полный CI зелёный;
- [ ] блокирующий `repo-guard` зелёный;
- [ ] явное принятие выполняется отдельным действием.

Если хотя бы один обязательный пункт неизвестен:

```text
acceptanceReady=false
```

## 22. Частые ошибки

### «Тесты зелёные — значит версия принята»

Нет. Тесты показывают состояние реализации. Принятие — отдельное решение.

### Изменение принятого контракта на месте

Если наблюдаемая семантика изменилась, нужен кандидат новой версии.

### Сначала написать код, потом объявить его теорией

Код может обнаружить проблему, но не должен автоматически определять новый смысл.

### Хранить старую реализацию «на всякий случай»

После явного переключения история уже находится в Git. Режим совместимости требует отдельной причины.

### Считать технический идентификатор смысловым тождеством

Номер объекта или записи не создаёт новую смысловую связь.

### Проверяющая функция создаёт недостающие данные

Проверка должна проверять свидетельство, а не создавать его.

### Контракт описывает внутреннюю архитектуру

Так теория привязывается к одной реализации и теряет независимость.

### Кандидат заранее объявляет будущие тесты зелёными

Свидетельство можно указывать только после его реального появления.

## 23. Что смотреть в начале ручной сессии

Полезный порядок:

```text
1. latest main SHA
2. открытые PR
3. открытые owner/gate issues
4. repo-policy.json
5. contracts/current + previous + candidate
6. cutover evidence
7. нужные docs/theory/**
8. нужные docs/specs/**
9. файлы TypeScript, владеющие реализацией
10. тесты, на которые ссылается conformance
11. последние CI/repo-guard результаты
```

Не опираться на старый текстовый checkpoint, если GitHub показывает другое состояние.

## 24. Короткая памятка

Если нужно быстро продолжить разработку вручную, последовательно ответить:

```text
1. Что сейчас принято?
2. Какой именно смысл я хочу изменить?
3. Меняется ли наблюдаемая машинная граница?
4. Какой контрпример показывает необходимость изменения?
5. Как выглядит минимальный кандидатный контракт?
6. Какие положительные и отрицательные проверки нужны?
7. Какой самый маленький шаг TypeScript это реализует?
8. Не превращает ли чтение отсутствие данных в запись?
9. Реально ли тест запускается полным CI?
10. Связано ли свидетельство с кандидатом?
11. Осталась ли принятая текущая версия неизменной?
12. Выполнены ли условия слияния?
13. Проверен ли точный main после слияния?
14. Только после полной готовности — явное принятие.
```

Главный принцип:

```text
Смысл → контракт → проверка → реализация → свидетельство → принятие.
```

Никогда не наоборот.
