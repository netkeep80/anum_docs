# Разработка МТС через контракты

Этот документ описывает процесс выпуска версий МТС.
Он не определяет семантику МТС.

Нормативный смысл исследуется и фиксируется в теории и спецификациях.
Версионный контракт при этом не должен опережать рабочее ядро.

## Главный принцип

Бумажная версия МТС является следствием проверенного ядра.

Правильное направление:

```text
теория и исследование
        ↓
смысловое решение
        ↓
изменение рабочего ядра
        ↓
исполняемые проверки
        ↓
реальные тестовые данные
        ↓
корпус соответствия
        ↓
версионный контракт
        ↓
человекочитаемая документация
        ↓
явное принятие версии
```

Неправильное направление:

```text
сначала написать новую бумажную версию
        ↓
объявить желаемое поведение контрактом
        ↓
потом подгонять под него ядро
```

Контракт версии не является проектом будущей реализации.
Он является машиночитаемой проекцией уже полученного и проверенного поведения.

## Теория и ядро не меняются местами

Из принципа выше не следует, что программа определяет онтологию МТС.

Теория отвечает на вопрос:

> Какой смысл мы исследуем и хотим проверить?

Ядро отвечает на вопрос:

> Удалось ли этот смысл выразить работающим механизмом?

Исполняемые проверки отвечают на вопрос:

> Действительно ли механизм обладает заявленными свойствами?

Контракт отвечает только после этого:

> Какое уже доказанное наблюдаемое поведение принадлежит данной версии?

Поэтому неверны обе крайности:

```text
текущий код делает X
=> X автоматически является МТС
```

и

```text
в JSON написано X
=> ядро обязано считаться реализующим X
```

Между теоретическим решением и версионным контрактом обязательно стоит
рабочее ядро с исполняемым свидетельством.

## Неизменный инвариант версий

Семантика разных версий может меняться.
Способ доказательства готовности версии меняться не должен.

Для версии `V` требуется:

```text
Kernel(V) существует
Conformance(V) выполняется на Kernel(V)
все обязательные проверки существуют и проходят
обязательные тестовые файлы проходят через реальное ядро
Contract(V) не утверждает неподтверждённое поведение
```

Версия не может стать готовой к принятию, если хотя бы одно из этих
условий нарушено.

## Исполняемое свидетельство

Запись требования в `JSON` ещё не является свидетельством.

Нужно различать:

```text
требование записано
```

и

```text
требование проверяется на @mts/core
```

Второе имеет приоритет при выпуске версии.

Обязательная проверка версии должна использовать реальное ядро,
а не отдельную тестовую модель, повторяющую ожидаемый ответ.

Если проверка требует нового поведения, применяется цикл:

```text
RED
↓
минимальное изменение ядра
↓
GREEN
↓
только затем обновление корпуса соответствия
```

## Реальные тестовые файлы ачисел

Для сериализации особенно важны переносимые тестовые данные.

Основной сценарий:

```text
тестовый файл ачисла
        ↓
апамять A
        ↓
рабочий сериализатор
        ↓
передаваемое ачисло
        ↓
апамять B
        ↓
структурное сравнение A и B
```

Такой тест проверяет сразу несколько границ:

- десериализацию;
- работу реальной апамяти;
- сериализацию;
- перенос между независимыми апамятями;
- независимость от технических идентификаторов;
- каноничность повторной сериализации.

Для строковых и четверичных ачисел используется тот же принцип.
Если для некоторого вида ачисла такой путь ещё невозможно выполнить,
это считается обнаруженным пробелом, а не поводом написать фиктивный тест.

## Обязательные свидетельства версии

Тест, который должен стать постоянным условием начиная с некоторой версии,
помечается в исходном тестовом файле:

```text
// mts-version-evidence: required-from=0.12
```

Проверка согласованности версий читает такие метки непосредственно из
`ts/test/**`.

Если версия достигла указанной границы, но её корпус соответствия ещё не
содержит обязательное свидетельство, она может оставаться исследуемым
кандидатом, однако не может стать готовой или принятой.

Это позволяет соблюдать естественный порядок:

```text
сначала появился рабочий GREEN факт
потом бумажная версия зафиксировала этот факт
```

а не наоборот.

## Кандидат не равен версии

Исследование будущего поведения может существовать в задачах GitHub.
Допустимы RED проверки и временные экспериментальные ветки.

Но наличие файла с пометкой `candidate` не даёт новой семантике статуса
принятой версии.

Кандидат обязан оставаться:

```text
accepted = false
acceptanceReady = false
```

пока его бумажная проекция отстаёт от обязательного исполняемого evidence
или само ядро ещё не прошло необходимые проверки.

## Принятие версии

Перед принятием выполняется проверка всей цепочки:

```text
теоретическое решение
        ↓
рабочее ядро
        ↓
обязательные GREEN проверки
        ↓
корпус соответствия
        ↓
контракт
        ↓
документация
```

Только после этого выполняется отдельное явное действие принятия.

```text
GREEN != принято
```

Но также:

```text
нет GREEN => принять невозможно
```

## Что хранит историю

Текущий каталог репозитория должен описывать текущее состояние.

История исследований хранится в:

```text
Git
закрытых задачах GitHub
закрытых запросах на слияние
```

Не нужно сохранять в активном дереве несколько документов,
повторяющих одну и ту же стадию рассуждений.

## Короткая формула процесса

```text
ИССЛЕДУЕМ
→ РЕАЛИЗУЕМ
→ ОПРОВЕРГАЕМ ТЕСТАМИ
→ ПОДТВЕРЖДАЕМ НА РЕАЛЬНЫХ ДАННЫХ
→ ФИКСИРУЕМ КОРПУС
→ ВЫВОДИМ КОНТРАКТ
→ ДОКУМЕНТИРУЕМ
→ ПРИНИМАЕМ
```

Версионные документы следуют за работающей МТС.
Они не создают её работоспособность своим существованием.
