# Пучки значений МТС v0.2

> **Статус:** нормативная спецификация принятого контракта `mts-value-bundle/v0.2`.
>
> Теоретический смысл изложен в [«Пучки связей МТС»](../theory/Пучки%20связей%20МТС.md). Машинным источником истины являются `contracts/mts-value-bundle-v0.2.json` и `contracts/mts-value-bundle-conformance-v0.2.json`.

## 1. Область версии

v0.2 принимает только **плоский пучок значений**.

В машинном интерфейсе две роли фигурной записи обозначены как `ConstraintBundle` и `ValueBundle`; в тексте МТС им соответствуют **пучок условий** и **пучок значений**.

Принято:

- статическое различение пучка условий и пучка значений для одной записи `{...}`;
- независимое разрешение каждого вхождения исходной записи;
- экстенсиональное равенство по множеству уже разрешённых связей;
- отсутствие автоматического отождествления одноэлементного пучка и одиночной связи;
- раскрытие пучка как запрос чтения через соположение двух выражений, если хотя бы одно из них является пучком значений;
- пустой пучок как отсутствие ограничения только в позиции полюса раскрытия.

Не принято:

- вложенный пучок значений;
- непустой пучок значений в правой части `:`;
- автоматическое распространение `⟼`, `♀`, `♂`, `¬` на пучок;
- пучок как явный полюс формы связи `⟼`;
- неявное создание или удаление связей;
- синтетическое значение для отсутствующей связи.

## 2. Фигурная запись и статическое уточнение роли

Синтаксический анализатор сохраняет фигурную форму и отдельные вхождения исходной записи. Семантическая роль выбирается **до интерпретации**.

```text
фигурная запись
  ├─ пучок условий
  └─ пучок значений
```

Содержимое памяти не участвует в выборе роли.

### 2.1. Основания для выбора роли

Для непустого пучка:

- непосредственные элементы-суждения дают основание для роли пучка условий;
- непосредственные элементы-формы дают основание для роли пучка значений;
- смешение двух видов элементов является статической ошибкой `mixed-bundle-role-evidence`.

Названия кодов ошибок являются машинными идентификаторами контракта и не вводят отдельных понятий МТС.

### 2.2. Пустой `{}`

Пустой пучок не содержит внутреннего основания для выбора роли, поэтому его роль задаётся статическим внешним контекстом.

| Контекст | Роль |
|---|---|
| вход интерпретации условий | пучок условий |
| операнд `=` или `!=` | пучок значений |
| полюс раскрытия | пучок значений |
| правая часть `x : {}` | пучок условий |
| без достаточного статического контекста | ошибка неоднозначной роли |

### 2.3. Области допустимых операций

| Позиция | v0.2 |
|---|---|
| пучок условий на входе интерпретации условий | принят |
| плоский пучок значений в позиции значения/равенства | принят |
| последовательность с хотя бы одним пучком значений | запрос раскрытия |
| пучок значений как явный полюс `⟼` | отложено |
| `♀{...}`, `{...}♂`, `¬{...}` | отложено |
| `name : {a,b}` | отложено |
| вложенный `{{a,b}}` как значение | отложено |

## 3. Виды исполняемых значений

На уровне машинного ядра различаются два вида значения:

```text
одиночная связь
пучок связей
```

В API они представлены типами `LinkValue` и `BundleValue`.

Между ними нет автоматического приведения:

```text
{a} != a
```

даже если `a` разрешилось в единственную связь.

## 4. Разрешение вхождений и сохранение происхождения

Каждый непосредственный элемент плоского пучка значений разрешается независимо.

Для записи:

```text
{[], []}
```

два вхождения имеют разные структурные пути. Их нельзя объединить до разрешения.

Наблюдаемая последовательность такова:

```text
исходные вхождения
      ↓ независимое разрешение
вхождение → разрешённая связь
      ↓ экстенсиональная свёртка
множество различных разрешённых связей
```

Именно последнее множество образует семантическое значение пучка.

Порядок и число повторных вхождений сохраняются как сведения о происхождении результата, но после разрешения не входят в экстенсиональное равенство.

## 5. Равенство

Для двух пучков значений:

```text
равны(левый, правый)
⇔
множество_разрешённых(левый) = множество_разрешённых(правый)
```

Следствия:

```text
{a,b} = {b,a}
{a,a} = {a}
```

только после разрешения соответствующих вхождений.

Для безымянных форм:

```text
{[],[]} = {[]}
```

не является тождеством исходной записи. Результат зависит от того, в какие связи разрешились отдельные вхождения.

Сравнение разных видов значения остаётся различающим:

```text
одиночная_связь(x) != пучок({x})
```

## 6. Раскрытие пучка

Если последовательность содержит ровно два полюса и хотя бы один из них статически определён как пучок значений, последовательность трактуется как запрос раскрытия.

Область допустимых значений полюса:

- одиночная форма → одна разрешённая связь;
- непустой пучок → множество разрешённых связей;
- пустой пучок → отсутствие ограничения только в позиции полюса раскрытия.

### 6.1. Основной смысл

```text
a{b,c}
```

выбирает уже существующие связи `(a,b)` и `(a,c)`, если они существуют.

```text
{a,b}c
```

выбирает существующие `(a,c)` и `(b,c)`.

```text
{a,b}{c,d}
```

выбирает существующие упорядоченные пары из декартова произведения допустимых начал и концов.

### 6.2. Пустой пучок как отсутствие ограничения

```text
a{}   → все существующие исходящие связи из a
{}b   → все существующие входящие связи в b
{}{}  → все существующие связи выбранной памяти
```

Этот смысл действует только в статически известной позиции раскрытия.

### 6.3. Отсутствующая связь

Если точной пары полюсов в памяти нет, она просто не попадает в результат:

```text
нет связи → нет элемента результата
```

Связь при этом не создаётся.

## 7. Побочные действия

Принятый инвариант:

```text
интерпретация пучка может читать память
интерпретация пучка не может создавать связь
интерпретация пучка не может удалять связь
```

Раскрытие — запрос, а не команда изменения памяти.

## 8. Каноническое эталонное ядро

Единственная эталонная реализация принятой семантики:

```text
core/mtc_value_bundle.py
```

Основные операции машинного API:

```text
elaborate_bundles
evaluate_flat_value_bundle
values_equal
expand_bundle_query
```

Исполнение пучка условий остаётся в существующем `interpret_constraints()`. Это две разные семантические роли одной фигурной записи, а не две совместимые версии одного интерпретатора.

## 9. Корпус соответствия

Нормативный машинный корпус:

```text
contracts/mts-value-bundle-conformance-v0.2.json
```

Он фиксирует:

- статическое определение роли;
- статические отказы;
- экстенсиональное равенство после разрешения;
- независимость отдельных `[]`;
- сравнение пучка с одиночной связью;
- раскрытие только по существующим связям;
- запрет неявного создания и удаления.

Исследовательские файлы решения и проверок остаются доказательной историей принятого решения, но не являются альтернативными исполняемыми реализациями.

## 10. Неизменность корневой системы

Десять корневых определений МТС не меняются. Фигурные формы внутри `∞` и `(=)` статически определяются только как пучки условий.

Это обязательное условие v0.2.
