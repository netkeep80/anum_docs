# Пучки значений МТС v0.2

Этот документ описывает принятую историческую семантику `mts-value-bundle/v0.2`.

Машинные источники истины:

```text
contracts/mts-value-bundle-v0.2.json
contracts/mts-value-bundle-conformance-v0.2.json
core/mtc_value_bundle.py
```

Пучок нужен, когда требуется говорить не об одной связи, а о совокупности уже разрешённых связей. Версия 0.2 принимает только **плоские пучки значений**.

Важно: эта historical семантика не становится автоматически универсальной семантикой пучков Foundation v2. Точное вхождение связи и множественность должны учитываться отдельно при будущем переосмыслении.

## 1. Две роли фигурной записи

Одна запись:

```text
{...}
```

в версии 0.2 может иметь две статически различимые роли:

```text
пучок условий
пучок значений
```

В машинном интерфейсе им соответствуют `ConstraintBundle` и `ValueBundle`.

Роль определяется **до интерпретации**, а не по содержимому памяти.

Для непустого пучка:

- элементы-суждения задают пучок условий;
- элементы-формы в допустимой позиции значения задают пучок значений;
- смешение этих двух случаев является статической ошибкой.

## 2. Пустой пучок

Пустая запись:

```text
{}
```

сама не содержит достаточного основания для выбора роли. Роль определяется внешней синтаксической позицией.

Принятые случаи:

| Позиция | Роль |
|---|---|
| вход интерпретации условий | пучок условий |
| операнд `=` или `!=` | пучок значений |
| полюс раскрытия | пучок значений |
| правая часть `x : {}` | пучок условий |
| недостаточный внешний контекст | ошибка неоднозначности |

Как самостоятельное значение `{}` является пустым пучком. Особое значение «нет ограничения» появляется только в позиции полюса раскрытия.

## 3. Разрешение отдельных вхождений

Каждый непосредственный элемент пучка разрешается независимо.

Например:

```text
{[], []}
```

содержит два разных вхождения исходной записи. Их нельзя объединять только потому, что они записаны одинаково.

Сначала происходит:

```text
исходное вхождение
→ разрешённая связь
```

и только затем плоский пучок сворачивается в множество различных разрешённых связей.

Поэтому одинаковая запись не означает одинаковое значение.

## 4. Экстенсиональное равенство версии 0.2

После разрешения значением плоского пучка является множество различных разрешённых связей.

Отсюда:

```text
{a,b} = {b,a}
{a,a} = {a}
```

если соответствующие вхождения действительно разрешились в те же связи.

Но:

```text
{[],[]} = {[]}
```

не является тождеством исходной записи. Результат зависит от конкретного разрешения отдельных вхождений.

Порядок и количество исходных повторов могут сохраняться как сведения о происхождении, но не входят в экстенсиональное равенство v0.2.

## 5. Пучок и одиночная связь различаются

Версия 0.2 не вводит автоматического приведения:

```text
{a} = a
```

Даже одноэлементный пучок остаётся отдельным видом исполняемого значения.

В машинной реализации различаются:

```text
LinkValue
BundleValue
```

Это различие относится к интерфейсу исторической реализации и не добавляет скрытый тип в примитивную связь Foundation v2.

## 6. Раскрытие пучка

Если последовательность имеет два полюса и хотя бы один из них является пучком значений, версия 0.2 рассматривает её как **запрос чтения существующих связей**.

Примеры:

```text
a{b,c}
```

выбирает существующие:

```text
a ⟼ b
a ⟼ c
```

Запись:

```text
{a,b}c
```

выбирает существующие:

```text
a ⟼ c
b ⟼ c
```

А:

```text
{a,b}{c,d}
```

проверяет существующие пары из декартова произведения допустимых начал и концов.

## 7. Пустой пучок как отсутствие ограничения

Только в позиции раскрытия:

```text
a{}   → все существующие исходящие связи из a
{}b   → все существующие входящие связи в b
{}{}  → все существующие связи выбранного представления памяти
```

Вне раскрытия `{}` не является универсальным знаком «любой объект».

## 8. Отсутствующая связь не создаётся

Раскрытие является чтением.

Если подходящей пары нет:

```text
не найдено
```

означает только отсутствие элемента результата.

Не допускается скрытый переход:

```text
не найдено
→ создать связь
```

Поэтому:

```text
раскрытие ≠ материализация
раскрытие ≠ удаление
```

Эта граница согласуется с общим правилом апамяти:

```text
поиск / чтение / проверка
≠
явное изменение
```

## 9. Что версия 0.2 не принимает

Не определяются как принятая семантика:

- вложенные пучки значений;
- непустой пучок значений в правой части `:`;
- пучок как явный полюс `⟼`;
- автоматическое распространение `♀`, `♂`, `¬` на пучок;
- неявное создание отсутствующих связей;
- удаление связей через пустой пучок;
- синтетические значения для отсутствующих пар;
- глобальное переписывание через равенство пучков.

## 10. Корневая программа не меняется

Принятие пучков значений не изменяет десять исторических корневых определений МТС v0.2.

Фигурные формы внутри определений `∞` и `(=)` трактуются как пучки условий, а не как пучки значений.

Это сохраняется как часть воспроизводимой исторической версии.

## 11. Граница с Foundation v2

Foundation v2 допускает два разных точных вхождения одной пары:

```text
P1 = A ⟼ B
P2 = A ⟼ B
P1 ≠ P2
```

Поэтому будущая версия пучков не должна молча использовать экстенсиональное множество как способ уничтожить множественность точных вхождений.

Перед переносом пучков в следующее основание нужно отдельно определить:

```text
что является тождеством пучка?
сохраняется ли множественность?
что считается равенством при разных exact occurrences?
как выражается wildcard через связи/evidence?
как разделены поиск и материализация?
```

До такого решения этот документ остаётся спецификацией именно принятой historical v0.2 семантики.
