# Ачисла и сериализация
<!-- версия документа МТС; mts-doc-version: v0.13 -->
> **Версия МТС: v0.13**

Этот документ задаёт текущую спецификацию ачисел, точных последовательностей и переносимых представлений Связей в МТС v0.13.

Ачисло — **роль Связи или связевой структуры**, используемая для точного укоренённого представления. Оно не является отдельным видом сущности.

Связанные владельцы:

- [Система аксиом МТС](../theory/Система%20аксиом%20МТС.md) — онтология, корневой базис и тождество Связи;
- [Основания МТС](../theory/Основания%20МТС.md) — объяснение структурного фундамента;
- [Формальная нотация МТС](Формальная%20нотация%20МТС.md) — интерпретация, `FORMAL` и смысловые полномочия;
- [Апамять и управление сетью связей](Апамять%20и%20управление%20сетью%20связей.md) — чтение, запись и материализация.

## 1. Два четверичных слоя v0.13

В МТС v0.13 одновременно существуют две четверичные роли, которые нельзя смешивать.

### 1.1. Структурное описание Связи

Канонический структурный алфавит описывает локальный класс самой Связи:

```text
8 = ROOT
9 = START
6 = END
1 = PAIR
```

Эти четыре значения соответствуют четырём возможным сочетаниям локального самовхождения:

```text
start(X)=X  end(X)=X  -> ROOT
start(X)=X  end(X)!=X -> START
start(X)!=X end(X)=X  -> END
start(X)!=X end(X)!=X -> PAIR
```

### 1.2. Четверичный контекст Q

Отдельный текущий алфавит `Q`:

```text
[ ] 1 0
```

используется в собственной интерпретационной роли:

```text
[ -> O
] -> C
1 -> L
0 -> U
```

`∞/R` не является пятым абитом `Q`.

Одинаковое начертание не создаёт одинаковый смысл автоматически. В частности:

```text
структурный знак 1 = PAIR
Q-знак 1          = L
строковый знак 1  = байт UTF-8 для символа "1"
```

Роль задаётся выбранным контекстом интерпретации.

<a id="mts-law-rootBasisBoundary"></a> <!-- служебный якорь -->
Объявленный `RootBasis` перед смысловой записью проверяется структурно как `R/O/C/L/U`. Чужой, схлопнутый или поддельный базис не получает полномочия материализации.

## 2. Каноническое структурное ачисло

<a id="mts-law-L4"></a> <!-- нормативный владелец -->
<!-- mts:req:L4:begin -->
> **MTS `L4`** · `semantic-law` · `representation/recursive-alphabet/prefix-codec` · источник `contracts/mts-contract-v0.13.json#/requiredSemanticLaws/L4` · digest `f740e98eade6204d` · evidence +7/-1 · gates 2 · `traceability/mts-v0.13.json`.
<!-- mts:req:L4:end -->
### L4. Канонический структурный алфавит

Структурное ачисло имеет самодостаточную префиксную грамматику:

```text
Anum ::= 8
       | 9 Anum
       | 6 Anum
       | 1 Anum Anum
```

Арность определяется текущим знаком:

```text
8  ROOT   0 дочерних описаний
9  START  1 дочернее описание
6  END    1 дочернее описание
1  PAIR   2 дочерних описания
```

Поэтому поток читается без внешнего дерева разбора или дополнительной таблицы арности.

Корневые примеры:

```text
R = 8
O = 98
C = 68
L = 19868
U = 16898
```

Здесь важно различать **Связь-знак** и **описание самой Связи-знака**. Например:

```text
O                    = связевый знак START
физическая запись O  = 9
описание самой O      = 98
```

`U=C⟼O` — обычный `PAIR`, поэтому его описание начинается с `1`.

<a id="mts-law-L5"></a> <!-- нормативный владелец -->
<!-- mts:req:L5:begin -->
> **MTS `L5`** · `semantic-law` · `representation/recursive-alphabet/canonicality` · источник `contracts/mts-contract-v0.13.json#/requiredSemanticLaws/L5` · digest `c7cc23abd9ce2fe7` · evidence +1/-3 · gates 2 · `traceability/mts-v0.13.json`.
<!-- mts:req:L5:end -->
### L5. Знак обязан соответствовать фактическому классу

Структурный знак каноничен только тогда, когда совпадает с реальным локальным классом описываемой Связи.

Для `PAIR(left,right)` целевая Связь должна отличаться от обоих полюсов. Поэтому:

```text
188  -> 8
1988 -> 98
1868 -> 68
```

не являются каноническими описаниями через `1`: соответствующая структура схлопывается в `ROOT`, `START` или `END`.

При этом обычная Связь

```text
P = X ⟼ X
P != X
```

остаётся `PAIR`: равенство двух полюсов само по себе не является самовхождением целой Связи.

## 3. Описание не является целью

<a id="mts-law-L6"></a> <!-- нормативный владелец -->
<!-- mts:req:L6:begin -->
> **MTS `L6`** · `semantic-law` · `representation/carrier/description-target-boundary` · источник `contracts/mts-contract-v0.13.json#/requiredSemanticLaws/L6` · digest `e4541a6a3c0aad6a` · evidence +1/-1 · gates 3 · `traceability/mts-v0.13.json`.
<!-- mts:req:L6:end -->
### L6. Описание не является целью

Нужно различать как минимум четыре уровня:

```text
смысловая Связь
каноническое структурное описание
связевой носитель описания
физический поток
```

Даже если каждый уровень представлен Связями:

```text
description(S) != S
```

Из существования корректного описания не следует:

- что смысловая цель уже материализована;
- что её разрешено создать;
- что технический адрес носителя является адресом цели.

Описание позволяет **сказать, какую структуру мы имеем в виду**, не создавая её автоматически.

## 4. Межпамятное тождество

<a id="mts-law-L7"></a> <!-- нормативный владелец -->
<!-- mts:req:L7:begin -->
> **MTS `L7`** · `semantic-law` · `representation/transport/structural-identity` · источник `contracts/mts-contract-v0.13.json#/requiredSemanticLaws/L7` · digest `05a70ed1abb45c10` · evidence +3/-0 · gates 3 · `traceability/mts-v0.13.json`.
<!-- mts:req:L7:end -->
### L7. Переносимое тождество структурно

Технический идентификатор Связи локален своей апамяти.

```text
Memory A
  S_A
   ↓
каноническое описание
   ↓
физический поток
   ↓
Memory B
  S_B
```

`S_A` и `S_B` могут иметь разные локальные handles. Переносимым свидетельством тождества является одинаковая каноническая рекурсивная структура, а не числовой адрес или слот.

Один и тот же допустимый Link при независимой истории выделения памяти должен сериализоваться одинаково.

## 5. Точные последовательности и локальное укоренение

<a id="mts-law-exactAnumRooting"></a> <!-- служебный якорь -->
<a id="mts-law-L10"></a> <!-- нормативный владелец -->
<!-- mts:req:L10:begin -->
> **MTS `L10`** · `semantic-law` · `representation/anum/root-origin` · источник `contracts/mts-contract-v0.13.json#/requiredSemanticLaws/L10` · digest `ec379037cdff248d` · evidence +1/-2 · gates 1 · `traceability/mts-v0.13.json`.
<!-- mts:req:L10:end -->
### L10. Каждый локальный контекст ачисла начинается от R

Точная последовательность хранит явные позиции, поэтому не тождественна своему результату свёртки.

Для уже разрешённых значений удобно писать:

```text
des(ε)       = R
des(a)       = a
des(a,b)     = a ⟼ b
des(a,b,c)   = (a ⟼ b) ⟼ c
```

Но:

```text
точная последовательность
!=
результат свёртки
!=
адресуемая цель
```

Это видно уже на корне:

```text
des(ε)   = R
des([R]) = R
```

Результат одинаков, а последовательности различны.

Точный связевой носитель последовательности строится от локального `R`:

```text
Seq([]) = R
Cell(prev,value) = START(prev ⟼ value)
Seq(xs + [x]) = Cell(Seq(xs),x)
```

Поэтому:

```text
Seq([]) != Seq([R])
```

Повтор позиции не создаёт новую смысловую копию значения.

## 6. Контекст Q

Алфавит `Q` — отдельная текущая четверичная роль:

```text
[ ] 1 0
```

с корневыми значениями `O/C/L/U`.

Пустой `Q` разрешается к корню:

```text
des_Q(ε)  = R
des_Q([]) = R
```

Состояние носителя задаётся структурой:

```text
QEmpty = R
QNonEmpty(inner) = START(inner)
```

<a id="mts-law-quaternaryNestedContext"></a> <!-- служебный якорь -->
Вложенный `Q [...]` открывает собственный локальный контекст от `R`, возвращает родителю ровно одно значение-Связь и не выбирается эвристикой среды исполнения.

Для объяснения переходов допустима техническая метанотация:

```text
Q_OPEN
Q_VALUE
Q_CLOSE
Q_FINALIZE
```

Она описывает этапы обработки, но не вводит скрытый стек как смысловой источник.

Обязательные свойства:

- каждый вложенный контекст начинается от `R`;
- `R` не является пятым абитом;
- явная позиция `R` не теряется;
- дочерний контекст возвращает одно значение;
- чтение и проверка не создают отсутствующие смысловые Связи.

Уже существующий связевой носитель `Q` читается от текущей ячейки к `R`; технический адрес ячейки не участвует в смысловом тождестве.

## 7. Resolve и материализация

<a id="mts-law-resolveMaterializeSeparation"></a> <!-- служебный якорь -->
`Resolve` и `MATERIALIZE_TARGET` имеют разные эффекты:

```text
Resolve            = чтение
MATERIALIZE_TARGET = разрешённая смысловая запись
```

`Resolve` не создаёт отсутствующую цель.

Состояния чтения:

```text
UNINTERPRETABLE
NOT_FOUND
FOUND(X)
```

принадлежат спецификации [апамяти](Апамять%20и%20управление%20сетью%20связей.md).

<a id="mts-law-targetMaterializationBound"></a> <!-- служебный якорь -->
Обе адресные операции применяют один корневой срез к точному адресу; оставшаяся косвенность сохраняется.

`MATERIALIZE_TARGET` получает право записи только после полной проверки адресного свидетельства. Ошибка не должна оставлять частично созданную смысловую цель.

Право на материализацию структурных `START`, `END` и `PAIR` дополнительно требует смысловой цепочки полномочий, определённой законами `FORMAL` и апамяти.

## 8. Строковое ачисло и точные байты

Строковое ачисло хранит **точные байты**, а не нормализованный текст.

Текущий байтовый конверт:

```text
[bbbbbbbb]
```

содержит ровно восемь бит, старший бит передаётся первым.

<a id="mts-law-stringByteIdentity"></a> <!-- служебный якорь -->
<a id="mts-law-L11"></a> <!-- нормативный владелец -->
<!-- mts:req:L11:begin -->
> **MTS `L11`** · `semantic-law` · `representation/anum/string-carrier` · источник `contracts/mts-contract-v0.13.json#/requiredSemanticLaws/L11` · digest `1880b94c436992b7` · evidence +1/-0 · gates 1 · `traceability/mts-v0.13.json`.
<!-- mts:req:L11:end -->
### L11. STRING сохраняет точное байтовое тождество

```text
bytes
-> укоренённое STRING-ачисло
-> перенос
-> независимая апамять
-> укоренённое STRING-ачисло
-> те же bytes
```

Неявно не выполняются:

```text
нормализация Unicode
изменение регистра
переписывание переводов строк
локализованное преобразование
потеря повреждённых байтов
```

<a id="mts-law-utf8CarrierBoundary"></a> <!-- служебный якорь -->
UTF-8 — слой строгого чтения поверх точных байтов. Последовательность может быть корректным точным байтовым носителем и одновременно быть некорректным текстом UTF-8.

<a id="mts-law-stringNestedAnum"></a> <!-- служебный якорь -->
В строковом контексте вложенное ачисло открывает дочерний локальный контекст от `R` и возвращает ровно одно значение-Связь.

<a id="mts-law-stringOneVsQOne"></a> <!-- служебный якорь -->
Одинаковое видимое `1` не смешивает роли:

```text
структурное 1 -> PAIR
Q-контекст 1  -> L
STRING "1"    -> точные байты символа
```

## 9. Физическая структурная граница

<a id="mts-law-L13"></a> <!-- нормативный владелец -->
<!-- mts:req:L13:begin -->
> **MTS `L13`** · `semantic-law` · `representation/physical-boundary/digital-alphabet` · источник `contracts/mts-contract-v0.13.json#/requiredSemanticLaws/L13` · digest `352e9ec75cd20f11` · evidence +1/-1 · gates 2 · `traceability/mts-v0.13.json`.
<!-- mts:req:L13:end -->
### L13. Обязательны четыре физических состояния

Минимальная цифровая физическая граница структурного описания различает:

```text
1
6
8
9
```

Иное значение не является знаком канонического структурного алфавита и отвергается до смысловой материализации.

Состояние линии `Z` может обозначать отсутствие сигнала или передачи, но не является пятым смысловым абитом.

Физическое кодирование может быть устроено иначе, если сохраняет различимость четырёх классов. Утверждение о четырёх значениях относится к прямому каноническому кодированию одного структурного узла, а не к глобальной невозможности иных кодов переменной длины.

## 10. Представление не выбирает интерпретацию

<a id="mts-law-representationNotInterpretation"></a> <!-- служебный якорь -->
Физический или связевой носитель сам по себе не выбирает интерпретатор.

Например, символ `[` имеет точное строковое байтовое представление. Наличие этих байтов не означает автоматического открытия `Q`.

```text
одни и те же bytes
+ строковый контекст
!=
те же bytes
+ Q-контекст
```

Аналогично физический `1` получает роль `PAIR` только в структурном контексте `8/9/6/1`.

Выбор смыслового действия принадлежит явному интерпретационному слою `FORMAL`, а не форме носителя.

## 11. Производное относительное продолжение

После того как явные словарь, грамматика и теория выбрали последовательность значений, её можно продолжить относительно выбранного контекста.

Для:

```text
F = (f1,...,fn)
P = parent ⟼ prefix
K = START(P)
```

допустима производная запись:

```text
rel_K(ε) = prefix
r0 = prefix
r(i+1) = r(i) ⟼ f(i+1)
rel_K(F) = rn
```

Нужно различать:

```text
относительное продолжение
!=
общая навигация
!=
технический путь
!=
обратная Связь
```

Пустое продолжение возвращает выбранный `prefix`, а не создаёт новый корневой контекст.

Если следующий элемент равен `R`, отдельные результаты свёртки могут совпасть из-за `R=R⟼R`; по одному результату нельзя восстанавливать историю точных позиций.

## 12. Рекурсивная инверсия структурного ачисла

**Статус: производный результат о принятой v0.13, не новый закон контракта.**

Рекурсивной инверсии Связи соответствует точное преобразование структурного ачисла:

```text
J(8)     = 8
J(9 x)   = 6 J(x)
J(6 x)   = 9 J(x)
J(1 x y) = 1 J(y) J(x)
```

Отсюда:

```text
J(J(q)) = q
```

для канонического структурного описания `q`.

На корневых примерах:

```text
8     -> 8
98    -> 68
68    -> 98
19868 -> 19868
16898 -> 16898
```

Это преобразование не меняет локальный технический адрес Связи «магически»: оно задаёт рекурсивный структурный образ.

## 13. Сводка

В МТС v0.13 одновременно выполняются следующие границы:

```text
онтология = Link

структурное описание Link:
  8 ROOT
  9 START
  6 END
  1 PAIR

отдельный Q-контекст:
  [ ] 1 0

R не является дополнительным абитом Q
U не является пятым структурным аспектом

точная последовательность != результат свёртки
описание != цель
handle != переносимое тождество
Resolve != materialize
bytes != интерпретация
STRING 1 != Q 1 != structural 1
```

Текущий структурный `carrier` переносит допустимые `ROOT`-декомпозируемые Связи; граница допустимой смысловой области определяется фундаментом и апамятью, а не самим физическим алфавитом.
