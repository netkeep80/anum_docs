# Reference model МТС v0.1

Статус: актуальное, нормативное для архитектурных границ версии v0.1.

Этот документ фиксирует **референсную инженерную модель**, относительно которой строятся parser, interpreter, протокол ачисел, апамять и будущий апрувер. Он не объявляет выбранное машинное представление окончательной «природой связи» и не заменяет [Основания МТС](../theory/Основания%20МТС.md).

Машинный контракт находится в [`core/reference_model.py`](../../core/reference_model.py).

## 1. Главный принцип

Развитие МТС/Anum разделяется на шесть уровней:

```text
L0  Онтология
    что существует в МТС

L1  Семантическая модель
    как существующее представляется в reference model v0.1

L2  Формальный язык
    как семантика записывается знаками и формами

L3  Сериализация
    как структуры кодируются ачислами и абитами

L4  Исполнение
    как raw-носители и denotation читаются, ищутся и изменяются в памяти

L5  Теория вывода
    как строятся и проверяются доказательства
```

Главное архитектурное правило:

```text
верхний уровень не имеет права тайно определять семантику нижнего;
совпадение написания на разных уровнях не означает тождества объектов.
```

В частности, квадратные знаки L2 и абиты `[ ]` L3 могут иметь одинаковые glyph, но принадлежат разным слоям до явного правила отображения.

## 2. L0 — онтология

L0 сохраняет только положения оснований МТС:

```text
всё есть связь;
связь — единственная форма существования;
смысл не существует отдельно от связи;
несвязь не существует как отдельная натуральная сущность;
смысл несвязи выражается связью.
```

L0 не зависит от Python-классов, графов, файлов `*.anum`, квадратных скобок или будущего алгоритма доказательства.

## 3. L1 — семантическая reference model

### 3.1 Связь

Для v0.1 связь моделируется как узел с двумя **упорядоченными** полюсами:

```text
Link(start, end)
```

`start` и `end` сами ссылаются на связи. Поэтому конечный носитель модели является ориентированным графом связей и может содержать циклы.

Это позволяет представлять рекурсивную форму конечной структурой вместо бесконечного текстового разворачивания.

### 3.2 Акорень

```text
∞ = Link(∞, ∞)
```

Акорень представлен одной полностью самозамкнутой связью.

### 3.3 Начало формы

Актуальная ориентация из нормативных документов сохраняется:

```text
♀F = Link(♀F, F)
```

То есть `♀F` имеет самозамкнутый start-полюс и конец `F`.

### 3.4 Конец формы

```text
F♂ = Link(F, F♂)
```

То есть `F♂` имеет начало `F` и самозамкнутый end-полюс.

### 3.5 Инверсия

Для одной связи:

```text
¬Link(a, b) = Link(b, a)
```

Инверсия меняет направление связи. Она не означает отсутствие связи и не обязана рекурсивно инвертировать связи `a` и `b`, если оператор `¬` не применён к ним отдельно.

### 3.6 Равенство

Равенство v0.1 является структурным, а не строковым и не основанным на identity объекта реализации.

Для конечных циклических форм используется коиндуктивное чтение:

```text
A = B
```

тогда и только тогда, когда корневые ориентированные графы `A` и `B` бисимилярны с сохранением различия позиций `start` и `end`.

Практическое следствие:

```text
рекурсивные формы сравниваются без бесконечного unfolding.
```

Конкретный алгоритм сравнения реализуется на этапе исполнимой семантики; этот документ фиксирует его обязательный смысл.

### 3.7 Пучок

Текущий fixture уже фиксирует экстенсиональные свойства:

```text
{A, A} = {A}
{A, B} = {B, A}
```

Поэтому reference model v0.1 читает пучок как конечный экстенсиональный набор форм: порядок несущественен, повтор элемента не создаёт новый элемент.

## 4. L2 — формальный язык

L2 описывает синтаксические формы. Typed AST будет отдельной реализацией, но его контракт уже должен различать формы, суждения и определения.

Минимальные сигнатуры v0.1:

| Знак | Вход | Результат | Чтение |
|---|---|---|---|
| `:` | `Form × Form` | `Definition` | вводит различие через локальную форму |
| `⟼` | `Form × Form` | `Form` | строит `Link(start, end)` |
| `=` | `Form × Form` | `Judgment` | суждение структурного равенства |
| `!=` | `Form × Form` | `Judgment` | суждение различимости |
| `¬` | `Form` | `Form` | инверсия направления |
| `♀` | `Form` | `Form` | начало формы; prefix |
| `♂` | `Form` | `Form` | конец формы; postfix |
| `(...)` | `Form` | `Form` | круглая формальная форма / группировка |
| `[...]` | `Form` | `Form` | квадратная форма L2 |
| `{...}` | `Form*` | `Bundle` | пучковая форма |

Приоритеты и ассоциативность зафиксированы машинным контрактом `core/reference_model.py` и должны использоваться будущим typed parser.

`⟼` в v0.1 читается левоассоциативно, что соответствует уже присутствующим формулам вида:

```text
[][][] = ([] ⟼ []) ⟼ []
[][][] = [] ⟼ [] ⟼ []
```

### Определение не является мутацией памяти

```text
X : F
```

создаёт определение/связывание в формальном окружении L2/L1. Оно само по себе не является командой L4 `realize` и не должно тайно изменять апамять.

## 5. L3 — сериализация

L3 содержит:

```text
[ ] 1 0
*.anum
quaternary mode
string mode
UTF-8 payload codec
raw carrier
```

Базовый четверичный алфавит содержит ровно четыре абита:

```text
[ ] 1 0
```

Имена типа `window`, `position`, `int` не являются пятым видом абита.

Рабочая проекция issue #61:

```text
[] → 0
][ → 1
```

остаётся **experimental**. Она описана в [Протоколе абитов ачисел](Протокол%20абитов%20ачисел.md), но не становится частью корневой системы только из-за наличия прототипа в коде.

## 6. L4 — исполнение

Операции памяти обязаны различать raw carrier и denotation.

```text
raw(A) — носитель ачисла
den(A) — описываемая связь/структура
```

Контракт операций:

| Операция | Изменяет память | Материализует `den(A)` | Смысл |
|---|---:|---:|---|
| `load` | да, raw storage | нет | сохраняет носитель |
| `decode` | нет | нет | разбирает носитель |
| `project` | нет | нет | применяет явный контекст чтения `K` |
| `find` | нет | нет | проверяет наличие denotation |
| `realize` | да | да | явно материализует denotation |
| `delete` | да | нет | явно удаляет материализованную структуру |

Главный инвариант:

```text
load(A) не создаёт den(A)
find(A) не создаёт den(A)
```

И ещё один принцип:

```text
описание состояния ≠ команда изменения состояния.
```

Формула пучка, пустая форма или равенство не должны сами по себе удалять или создавать связи в памяти.

## 7. L5 — теория вывода

В v0.1 reference model L5 пока не содержит набора trusted inference rules.

Апрувер должен строиться только после стабилизации L0–L4. До этого утверждения о proof search, подстановке, конгруэнтности и полноте имеют статус `experimental`, если они не зафиксированы отдельным принятым решением.

Будущий L5 обязан различать:

```text
proof search
proof object
proof checker / trusted kernel
```

и не может использовать строковое совпадение как доказательство семантического равенства.

## 8. Статусы утверждений

Каждому нормативному или экспериментальному элементу назначается один статус:

```text
primitive     — исходное различие уровня
definition    — принятое определение
derived       — выводимое утверждение
conformance   — пример ожидаемого поведения
experimental  — рабочая гипотеза без нормативной силы
```

Нахождение строки в одном файле рядом с аксиомами не меняет её статус автоматически.

Текущий `tests/mtc_formulas.mtc` остаётся корневым fixture текущей системы, но дальнейшие parser/interpreter/prover не должны предполагать, что все его строки имеют одну и ту же логическую категорию.

## 9. Жизненный цикл фундаментального решения

Новая идея, меняющая reference model, проходит минимальный путь:

```text
Research
→ Problem
→ Candidate
→ Challenged
→ Modeled
→ Accepted
→ Released
```

Дополнительные состояния:

```text
Rejected
Deferred
Superseded
```

Смысл стадий:

- `Research` — идея без нормативной силы;
- `Problem` — точно сформулированный дефект текущей версии;
- `Candidate` — предложены синтаксис/семантика и контрпримеры;
- `Challenged` — выполнена попытка разрушить решение;
- `Modeled` — есть изолированная исполнимая модель;
- `Accepted` — владелец теории явно принимает решение;
- `Released` — решение вошло в версию, документацию и conformance tests.

ИИ-агент может исследовать, моделировать и оспаривать кандидат, но фундаментальное изменение не должно незаметно переходить из `experimental` в `Accepted`.

## 10. Граница текущей версии

Reference model v0.1 **не реализует**:

```text
typed AST;
semantic evaluator;
полную context model *.anum;
настоящую апамять;
proof kernel;
proof search.
```

Она задаёт контракт для этих этапов.

Если будущая реализация вынуждена нарушить этот документ, это означает не «особый случай в коде», а необходимость отдельного теоретического решения и изменения версии reference model.
