# Формальная нотация МТС

Статус: **актуальное, нормативное**.

Уровень: **L2 — формальный язык**.

Reference model: [МТС v0.2](Reference%20model%20МТС%20v0.2.md).

Machine contract: [`contracts/mts-contract-v0.2.json`](../../contracts/mts-contract-v0.2.json).

## 1. Назначение

Формальная нотация МТС — исполняемый язык описания и сопоставления форм связей.

Она не является:

```text
форматом хранения апамяти;
Anum-сериализацией;
обычным языком переменных и присваиваний;
скрытой командой materialization.
```

Production pipeline:

```text
source
→ core/mtc_parser.py
→ core/mtc_ast.py typed AST
→ core/mtc_interpreter.py
→ local substitutions / aliases / trace
```

## 2. Типы AST

```text
Expression
├── Form
├── Judgment
└── Definition
```

Основные узлы:

```text
Symbol
Literal
ContextPronoun
RoundForm
SquareForm
BundleForm
Sequence
StartProjection
EndProjection
Inversion
LinkForm
Equality
Inequality
Definition
```

`Expression` — машинный supertype синтаксиса, не новая онтологическая сущность.

## 3. Бинарный контекст

Любой локальный запуск интерпретации имеет виртуальный бинарный контекст:

```text
ContextFrame(start, end, parent?)
```

Для двух ролей существуют ровно два атомарных односимвольных местоимения:

```text
◁  — start текущего ContextFrame
▷  — end текущего ContextFrame
```

Местоимение не является переменной и не содержит имя объекта. Оно дейктически указывает на роль текущего контекста.

### Вышестоящий контекст

Подъём к parent context — отдельный prefix `↑`:

```text
↑◁    parent.start
↑▷    parent.end
↑↑◁   grandparent.start
```

`↑` не является частью identity местоимения.

### Скобки не перегружаются

Жёсткий lexical invariant:

```text
atomicPronouns = true
bracketOverloading = false
```

`[` и `]` никогда не получают особое значение из-за соседнего context glyph.

Строка:

```text
◁[]▷
```

токенизируется как:

```text
◁   [   ]   ▷
```

Поэтому scanner квадратных скобок может вообще ничего не знать о `◁`, `▷` и `↑`.

## 4. `[]` — анонимное вхождение формы

Пустая квадратная форма:

```text
[]
```

не является одной глобальной Link-константой, общей для всех одинаковых glyph.

Каждое AST-вхождение `[]` создаёт отдельный anonymous `HoleId`.

Identity:

```text
HoleId := structural AST occurrence path
```

Не identity:

```text
display text;
SourceSpan;
адрес объекта AST в памяти.
```

Поэтому:

```text
{[] = ◁, [] = ▷}
```

содержит два независимых anonymous occurrences.

Это принципиально устраняет старый global-collapse: формула `[] = X` связывает только конкретное вхождение текущей интерпретации и не превращается в правило «все `[]` равны X».

## 5. Полюса формы

```text
♀F  — StartProjection
F♂  — EndProjection
```

Reference carrier:

```text
♀F = Link(♀F, F)
F♂ = Link(F, F♂)
```

Старая ориентация `F♀` / `♂F` не используется.

Контекстные местоимения являются обычными `Form`, поэтому к ним применяются те же операторы:

```text
♀◁
◁♂
♀▷
▷♂
```

Никакого отдельного context-path language для этого не требуется.

## 6. Равенство

Нормативное определение:

```text
(=) : {♀◁ = ♀▷, ◁♂ = ▷♂}
```

При:

```text
ContextFrame(start=A, end=B)
```

проверяются соответствующие формы начала и конца `A` и `B`.

Оператор `=` строит `Judgment` и при `interpret` работает как **локальное identity/unification constraint**.

Он не означает:

```text
глобальное текстовое присваивание;
неограниченное rewrite-rule;
автоматическое слияние всех одинаково написанных occurrences.
```

## 7. `:` — определение, а не присваивание

```text
A : expression
```

создаёт:

```text
Definition(target=A, value=expression)
```

Правая часть имеет тип `Expression`, поскольку определение может содержать локальный пучок constraints:

```text
∞ : {◁ = ∞, ▷ = ∞}
(=) : {♀◁ = ♀▷, ◁♂ = ▷♂}
```

`:` сам по себе не изменяет апамять.

## 8. `⟼` — LinkForm и структурный pattern

```text
A ⟼ B
```

строит `LinkForm(A, B)`.

При интерпретации существуют два направления.

### Полностью заданная форма

```text
2 ⟼ 3
```

может найти существующий `LinkRef(2,3)`.

### Pattern против существующей связи

```text
10 = [] ⟼ []
```

при:

```text
poles(10) = (2, 3)
```

даёт:

```text
hole₀ → 2
hole₁ → 3
```

Вложенные forms декомпозируются рекурсивно:

```text
20 = ([] ⟼ []) ⟼ []
```

Так формальная нотация становится запросом к асети, а не только способом текстовой записи формулы.

`interpret` при этом не вызывает `realize`.

## 9. Скобочные формы

```text
(...)  — круглая форма
[...]  — квадратная форма L2
{...}  — пучковая форма
```

### Круглая форма

Сохраняется в typed AST и canonical printer. При structural matching grouping прозрачен.

### Квадратная форма

```text
[]   — anonymous link form occurrence
[1]  — квадратная форма абита связи
[0]  — квадратная форма абита несвязи
```

В `([)` и `(])` знаки `[`/`]` являются `Literal` внутри `RoundForm`.

### Пучок

`BundleForm` содержит ноль или более `Expression`.

Пучковые алгебраические свойства не включаются автоматически в root definitions; их место — отдельный semantic/conformance layer.

## 10. Граница L2 ↔ L3

Одинаковый glyph не означает один объект.

```text
L2: [...]  — квадратная форма formal notation
L3: [ ]    — два абита четверичного Anum-алфавита
```

Raw L3:

```text
][
```

может быть валидной последовательностью абитов, но strict L2 parser не обязан принимать её как L2 expression.

Рабочая L3-проекция issue #61 остаётся experimental.

## 11. Операторы и приоритеты

| Конструкция | Вход | Результат | Приоритет / fixity |
|---|---|---|---|
| `:` | `Form × Expression` | `Definition` | 10, right |
| `=` | `Form × Form` | `Judgment` | 20 |
| `!=` | `Form × Form` | `Judgment` | 20 |
| `⟼` | `Form × Form` | `Form` | 40, left |
| juxtaposition | `Form+` | `Sequence` | 50 |
| `¬` | `Form` | `Form` | 60, prefix |
| `♀` | `Form` | `Form` | 70, prefix |
| `♂` | `Form` | `Form` | 70, postfix |
| `(...)` | `Expression?` | `RoundForm` | container |
| `[...]` | `Form?` | `SquareForm` | container |
| `{...}` | `Expression*` | `BundleForm` | container |

Контекстные `◁` и `▷` являются atomic forms. `↑` относится только к context ascent.

`⟼` синтаксически левоассоциативен:

```text
A ⟼ B ⟼ C
```

читается parser-ом как:

```text
(A ⟼ B) ⟼ C
```

Это parser rule, а не утверждение algebraic associativity.

## 12. Parse, interpret и realize — разные функции

```text
parse(source)
    → typed AST

interpret(AST, ContextFrame, MemoryView)
    → success
    → local substitutions
    → local aliases
    → resolution trace

realize(...)
    → explicit memory effect
```

Главный invariant:

```text
interpret ≠ realize
```

`ContextFrame` тоже не обязан быть материализованной связью в апамяти.

## 13. SourceSpan и semantic identity

`SourceSpan(start,end)` нужен для diagnostics и подсветки исходника.

Он **не** определяет semantic identity anonymous occurrence.

Поэтому изменение пробелов:

```text
{[]=◁,[]=▷}
{  [] = ◁ , [] = ▷  }
```

не меняет structural `HoleId` и результат интерпретации.

Это необходимо и для будущего визуального апрувера: layout/formatting UI не должен менять смысл proof object.
