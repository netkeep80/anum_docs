# Формальная нотация МТС

Статус: актуальное, нормативное.

Уровень: **L2 — формальный язык**.

## Назначение

Формальная нотация МТС записывает формы, суждения и определения, чья L1-денотация задаётся [Reference model МТС v0.1](Reference%20model%20МТС%20v0.1.md).

Формальная нотация не вводит внешний источник смысла и не является форматом хранения апамяти.

Машинный front-end:

```text
source
→ core/mtc_parser.py tokenizer
→ Pratt parser
→ core/mtc_ast.py typed AST
→ static validation
```

## Источник формул

Текущая машинная поверхность формул находится в [корневом fixture](../../tests/mtc_formulas.mtc). Чтение принятых аксиом/определений дано в [Системе аксиом МТС](../theory/Система%20аксиом%20МТС.md).

Нахождение строки в fixture не определяет автоматически её логический статус. Статусы `definition`, `derived`, `conformance` и `experimental` различаются согласно reference model.

## Типы AST

L2 front-end различает три верхнеуровневые категории:

```text
Expression
├── Form
├── Judgment
└── Definition
```

Основные узлы:

```text
Symbol
Literal
RoundForm
SquareForm
BundleForm
Sequence
StartProjection
EndProjection
Inversion
LinkForm
Equality
Inequality
Definition
```

`Expression` нужен не как новая сущность МТС, а как машинный supertype синтаксиса. Например:

```text
∞ : [] = [] ⟼ []
```

имеет AST:

```text
Definition(
    target = Form(∞),
    value  = Equality(...)
)
```

Поэтому правая часть `:` не может быть искусственно ограничена только `Form`.

Аналогично:

```text
(=) : {♀[] = ♀[], []♂ = []♂}
```

содержит `BundleForm` из двух `Equality`-суждений. Пучковая форма удерживает выражения, а не только атомарные формы.

## Граница L2 ↔ L3

Совпадение видимого знака не означает совпадения объекта разных уровней.

```text
L2: [...]  — квадратная форма формального языка
L3: [ ]    — два glyph базового четверичного алфавита абитов
```

Любое тождество или проекция между ними должно задаваться явным правилом L3. Рабочая гипотеза issue #61 не считается частью L2 только потому, что использует те же квадратные знаки.

Строка:

```text
][
```

допустима как raw-последовательность L3, но strict L2 parser не обязан и не должен принимать её как формулу МТС без L2-конструкции.

## Скобочные нотации

```text
(...) — круглая формальная нотация
[...] — квадратная форма L2
{...} — пучковая нотация
```

```text
[] — минимальная завершённая форма одной связи
() — минимальная формальная форма смысла
{} — пустой пучок связей
```

Три пустые формы различимы:

```text
[] != ()
() != {}
{} != []
```

Скобки не взаимозаменяемы. В `([)` и `(])` квадратный знак является `Literal` внутри `RoundForm`, а не незакрытой границей квадратного контейнера. В `[1]` и `[0]` квадратные скобки являются границами `SquareForm`.

## Связь как оператор и как формальная форма смысла

Нужно различать два L2-вхождения одного видимого glyph:

```text
A ⟼ B
```

— `LinkForm`, бинарный конструктор формы связи. Его L1-денотация:

```text
Link(A, B)
```

А:

```text
(⟼)
```

— `RoundForm(Literal("⟼"))`, формальная форма **смысла связи**, введённая корневой системой.

Поэтому parser не подменяет `A ⟼ B` литералом `(⟼)` и не восстанавливает роль glyph строковыми эвристиками.

Аналогично `(↛)` является круглой формой символа смысла несвязи. Несвязь не существует в натуре; её смысл выражается связью.

## Полюса формы

Полюса записываются в актуальной ориентации:

```text
♀F — StartProjection, prefix
F♂ — EndProjection, postfix
```

Reference model v0.1 задаёт их циклическое чтение:

```text
♀F = Link(♀F, F)
F♂ = Link(F, F♂)
```

Старая ориентация `F♀` и `♂F` не используется в активной нотации.

## Операторы, типы и приоритеты

Текущая typed grammar использует:

| Конструкция | Вход | Результат | Приоритет / ассоциативность |
|---|---|---|---|
| `:` | `Form × Expression` | `Definition` | 10, справа |
| `=` | `Form × Form` | `Judgment` | 20, non-associative по смыслу |
| `!=` | `Form × Form` | `Judgment` | 20, non-associative по смыслу |
| `⟼` | `Form × Form` | `Form` | 40, слева |
| juxtaposition | `Form+` | `Sequence` | 50, слева |
| `¬` | `Form` | `Form` | 60, prefix |
| `♀` | `Form` | `Form` | 70, prefix |
| `♂` | `Form` | `Form` | 70, postfix |
| `(...)` | `Expression?` | `RoundForm` | container |
| `[...]` | `Form?` | `SquareForm` | container |
| `{...}` | `Expression*` | `BundleForm` | container |

`⟼` левоассоциативен, что проверяется существующей парой формул:

```text
[][][] = ([] ⟼ []) ⟼ []
[][][] = [] ⟼ [] ⟼ []
```

Juxtaposition является отдельным структурным правилом, поэтому:

```text
[][]
[][][]
[]([][])
[]{...}
{...}[]
```

строятся как `Sequence`, а не через post-hoc анализ исходной строки.

## Локальный контекст определения

Форма:

```text
A : expression
```

строит `Definition` и вводит различие `A` через локальное выражение.

Это L2-definition, а не L4-команда изменения памяти.

Повторные видимые знаки являются разными AST-вхождениями со своими `SourceSpan`. Они не превращаются автоматически в одну глобальную текстовую переменную.

```text
∞ : [] = [] ⟼ []
(=) : {♀[] = ♀[], []♂ = []♂}
```

Будущий prover должен вводить отдельную модель bindings/metavariables; parser не симулирует её совпадением строк.

## Роли вхождений

Видимый glyph не равен AST-вхождению glyph.

| Роль | Пример | AST-чтение |
|---|---|---|
| `container-boundary` | `[1]`, `{[]}`, `(A)` | граница typed container |
| `literal-abit` | `([)`, `(])` | `Literal` внутри `RoundForm` |
| `one-link-form` | `[]` | `SquareForm(None)` |
| `link-pole-form` | `♀[]`, `[]♂` | `StartProjection` / `EndProjection` |
| `abit-form` | `[1]`, `[0]` | `SquareForm(Symbol(...))` |
| `formal-form` | `(⟼)`, `(↛)` | `RoundForm` литерала/символа |
| `link-constructor` | `A ⟼ B` | `LinkForm` |
| `empty-formal-form` | `()` | `RoundForm(None)` |
| `grouped-form` | `(A)` | `RoundForm(A)` |
| `bundle-form` | `{}`, `{[]}` | `BundleForm` |

## Пучки

Пучок удерживает несколько выражений как одну пучковую форму. Текущий fixture фиксирует экстенсиональные свойства:

```text
{} != []
{[]} != []
{[], []} = {[]}
{[], [][]} = {[][], []}
```

Порядок элементов несущественен, повтор не создаёт новый элемент пучка на L1. Parser при этом сохраняет исходный порядок AST; экстенсиональная нормализация относится к semantic evaluator #70.

Пучковое раскрытие в fixture является описательной формой. Оно не является скрытой L4-командой создания или удаления связей.

## Source spans и ошибки

Каждый AST-узел хранит half-open `SourceSpan(start, end)`. Ошибка parser-а содержит диапазон исходной строки, поэтому diagnostics не зависят от повторного поиска текста.

Tokenizer сначала распознаёт многосимвольный `!=`, затем одиночные операторы и границы. Parser выдаёт ошибку на незакрытые контейнеры, dangling operators, недопустимые operands и L3-формы, которые не являются L2-выражениями.

## Canonical printer

`core/mtc_ast.py` предоставляет:

```text
format_expression(AST)
```

и структурный ключ без source spans:

```text
structural_key(AST)
```

Для актуального fixture проверяется инвариант:

```text
parse(source)
→ format
→ parse
```

сохраняет typed AST structure.

## Единственный production path

`core/mtc_parser.py` является единственным parser-ом L2.

`core/root_library.py` строит registry непосредственно из `Definition` AST nodes. Старые `core/mtc_reader.py` и `core/layers.py` удалены после миграции consumers; параллельный compatibility parser не сохраняется.
