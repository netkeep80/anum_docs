# Асеть доказательства МТС

Статус: архитектурная спецификация исчисления доказательств.

Связанные задачи: #999, #1019, #1040. Исполнимое основание: #1038 / #1039.

Принятая семантика МТС остаётся `v0.11`. Активного смыслового кандидата нет.

Эта спецификация не вводит новую версию МТС и не меняет принятый контракт. Она фиксирует архитектурную границу доказательств, необходимую для дальнейшего развития проверяющего механизма.

---

## 1. Главный закон

Доказательство в МТС является асетью.

```text
ДОКАЗАТЕЛЬСТВО = АСЕТЬ СВЯЗЕЙ
```

Массив узлов, объект языка реализации, ориентированный граф или сериализация сами по себе не являются доказательством. Они могут быть только проекциями одной и той же асети.

```text
асеть доказательства              <- authority
        |
        +-> массивы / индексы      <- обход
        +-> граф                   <- визуализация
        +-> JSON                   <- перенос
        +-> формальная нотация     <- текстовая проекция
```

Ни одна проекция не получает самостоятельного доказательного авторитета.

---

## 2. Асеть и история её построения — разные вещи

Нужно различать само доказательство и способ его получения.

Подстановка, специализация, перенос между областями ролей и композиция могут строить новую асеть доказательства, но не должны становиться обязательными типами узлов внутри неё.

Неверная модель:

```text
PrimitiveProof
SpecializedProof
CrossScopeProof
ClosureProof
...
```

Она создаёт второй язык доказательств поверх МТС.

Правильное направление:

```text
специализация / перенос / композиция
              ↓
строят или преобразуют асеть
              ↓
получившаяся асеть проверяется сама по себе
```

История построения может сохраняться как происхождение или диагностика, но не как источник доказательного авторитета.

---

## 3. Что уже подтверждено исполнимо

#1038 / #1039 установили четыре факта.

### 3.1. Повторное использование одной связи допустимо

Если правило требует одну и ту же доказанную связь в нескольких позициях, не нужно создавать искусственные копии.

```text
A
B
B
---
C
```

Один точный доказанный `B` может быть указан в двух позициях зависимостей.

```text
число позиций зависимостей != число различных доказанных связей
```

### 3.2. Производное правило не нужно превращать в примитивное

Сам факт наличия связи:

```text
DerivedDR -> Theory
```

не даёт производному правилу примитивного авторитета. Его авторитет должен идти от несомого доказательства.

### 3.3. Эти свойства совместимы

Повторное использование одного доказанного вхождения сохраняется при композиции производного доказательства.

### 3.4. Реальный L0 уже представим как асеть

Для цели:

```text
Nat0(A)
-------
Add(U,A,A)
```

все необходимые координаты уже собираются в одной асети МТС.

```text
проблема представления = отсутствует
```

Оставшийся барьер находится в доверенном чтении и проверке этой асети.

## 4. Минимальная конечная нормальная форма

Следующая топология — минимальный кандидат для отдельной проверки на опровержение. Она ещё не считается исполнимо подтверждённой.

### 4.1. Тождество производного доказательства

```text
I = TargetDR -> Theory
```

`TargetDR` задаёт утверждаемое производное правило. Связь `I` сама по себе не разрешает его применение.

Примитивное разрешение имеет противоположную форму:

```text
Theory -> PrimitiveDR
```

### 4.2. Внешняя посылка

```text
H = Claim -> I
```

Такое вхождение принадлежит выбранному доказательству и несёт точное утверждение `Claim`.

### 4.3. Применение примитивного правила

```text
A = PrimitiveDR -> ExactSequence(dependencies)
```

`dependencies` содержит ссылки на доказанные вхождения или внешние посылки. Одна ссылка может встречаться несколько раз.

### 4.4. Доказанное вхождение

```text
O = Claim -> A
```

`Claim` — фактически доказанная связь в текущей области доказательства.

Это принципиально отличается от модели, где результат узла считается буквально равным телу исходного правила.

### 4.5. Корень доказательства

Минимальный кандидат:

```text
P = I -> TargetOccurrence
```

Принадлежность конечной асети доказательства определяется достижимостью от `P` по доказательным зависимостям.

Посторонние связи памяти, не достижимые от корня, не входят в доказательство и не получают никакого авторитета.

Если переносная проекция отдельно заявляет список членов асети, она может проверять точное совпадение этого списка с достижимым замыканием. Но такой список остаётся проекцией, а не authority.

### 4.6. Обязательство проверить коллизии

Формы `H`, `A`, `O`, `I` и `P` построены из обычных связей МТС, поэтому нельзя заранее считать их различными «по типу».

Следующая проверка на опровержение обязана выяснить, не могут ли допустимые полюса привести к неоднозначному совпадению этих носителей.

Если топология не позволяет однозначно восстановить роль связи, её нужно усилить дополнительными связями МТС. Запрещено исправлять коллизию скрытым host-тегом.

## 5. Почему отдельный `Claim` у доказанного вхождения необходим

Общее правило сложения:

```text
Add(A,B,C)
S0(B,B1)
S0(C,C1)
------------
Add(A,B1,C1)
```

В L0 оно используется так:

```text
Add(U,N,N)
S0(N,N1)
S0(N,N1)
-------------
Add(U,N1,N1)
```

Примитивное правило остаётся тем же, но фактическое утверждение находится в другой области ролей.

Поэтому проверяется:

```text
PrimitiveDR
+ фактические посылки
+ фактический результат
----------------------
одна согласованная структурная подстановка
```

Не должно требоваться:

```text
actual Claim == source Rule body
```

Именно такое старое ограничение сейчас отделяет уже представимую асеть от доверенной повторной проверки.

---

## 6. Подстановка определяется по всему правилу

Недостаточно выводить подстановку только из заключения.

В правиле сложения роли `B` и `C` могут определяться посылками. Поэтому одна подстановка должна одновременно удовлетворять всей системе:

```text
source conclusion -> actual conclusion
source premise 1  -> actual premise 1
source premise 2  -> actual premise 2
...
```

Для каждой роли получается ровно одно согласованное значение. Повторное появление роли обязано давать ту же связь. Противоречие приводит к отказу.

---

## 7. Граница первого исполнимого шага

Для L0 достаточно двух форм значения роли источника:

```text
роль источника -> роль цели
роль источника -> точная заземлённая связь
```

Текущий пример:

```text
A  -> U
B  -> N
C  -> N
B1 -> N1
C1 -> N1
```

Неинъективная подстановка допустима: разные роли источника могут отображаться в одну целевую роль, если Теория не содержит явного запрета.

Произвольные составные выражения с несколькими целевыми ролями как значение одной исходной роли в первый шаг не входят.

---

## 8. Защита от захвата роли

Роль существует только потому, что она явно объявлена ролью выбранного словаря.

При переносе необходимо сохранять разделение:

```text
объявленная роль источника -> разрешённая подстановка
заземлённая часть источника -> точное тождество
```

Заземлённая связь не должна внезапно стать ролью другой области из-за совпадения тождества.

Если заземлённая часть попадает в роль целевой области там, где не было подстановки роли источника, проверка обязана отказать.

Общность доказывается структурой, а не именем переменной или соглашением языка реализации.

---

## 9. Нормализация конечных преобразований

Для специализации, переноса между областями и конечной композиции:

```text
исходная асеть доказательства
+ структурное преобразование
        ↓
недоверенное построение новой асети
        ↓
каноническая конечная асеть доказательства
        ↓
независимая доверенная проверка
```

Критический закон:

```text
успех преобразователя != доказательство
```

Доказательством является только результат, который независимо проверен.

После нормализации проверка не должна требовать метки:

```text
specialization
cross-scope
composed
```

---

## 10. Примитивный и производный авторитет

Примитивный авторитет задаётся выбранной Теорией:

```text
Theory -> Rule
Theory -> DR
```

Производное правило не получает такую связь автоматически.

Запрещено:

```text
проверили один раз
      ↓
добавили Theory -> DerivedDR
      ↓
считаем DerivedDR примитивным
```

Правильно:

```text
DerivedDR -> Theory
+ асеть доказательства
      ↓
доверенная проверка доказательства
```

Точная ревизия Теории остаётся неизменной.

---

## 11. Особая граница индукции и замыкания

Не каждое доказательное основание можно конечным образом развернуть в цепочку обычных правил.

Структурная индукция означает потенциально неограниченное семейство:

```text
P(U)
P(N) -> P(N1)
---------------
Nat0(N) -> P(N)
```

Нельзя материализовать бесконечную цепочку:

```text
P(U)
P(S(U))
P(S(S(U)))
...
```

Поэтому для индукции или наименьшего замыкания само доказательное основание должно быть явной асетью авторитета.

```text
асеть основания замыкания
+ асеть базы
+ асеть шага
+ структурные отображения
        ↓
асеть итогового доказательства
```

Доверенный механизм проверяет эти асети и их отношения. Специальный доверенный объект языка реализации не появляется.

Неверно:

```text
kind = induction
InductionProof = trusted
```

## 12. Что является авторитетом

Авторитет:

```text
точные связи МТС
точная топология асети
точная Theory
явные разрешения примитивных правил
явная асеть неприводимого доказательного основания
```

Не авторитет:

```text
boolean verified
hash без повторной проверки содержания
имя функции
класс TypeScript
тип JSON
порядок массива
указатель на ранее проверенный объект
метка specialized / cross-scope / induction
```

---

## 13. Требования к доверенной проверке

Доверенная проверка должна:

1. начинаться от явного корня асети;
2. восстанавливать целевое производное правило и точную Теорию;
3. определять доказательное замыкание только достижимостью от корня;
4. читать зависимости из связей МТС;
5. различать внешние посылки и доказанные вхождения по топологии;
6. разрешать повторные ссылки на одно вхождение;
7. для примитивного шага проверять точное разрешение правила в Теории;
8. находить одну согласованную подстановку по заключению и всем посылкам;
9. сохранять точное тождество заземлённых частей;
10. отвергать захват ролей;
11. отвергать циклические зависимости;
12. отвергать самопринятие производного правила;
13. не изменять память;
14. не изменять точную ревизию Теории.

Посторонние связи памяти не являются ошибкой доказательства: они просто не принадлежат достижимой асети.

Точное соответствие дополнительного массива или списка достижимому замыканию относится к проверке переносной проекции.

---

## 14. Отрицательная граница

Следующий исполнимый корпус должен отвергать:

```text
DerivedDR -> Theory без доказательной асети
поддельное Theory -> DerivedDR
отсутствующую или лишнюю зависимость шага
неверное число позиций посылок
противоречивую подстановку одной роли
частичную подстановку
захват заземлённой связи ролью цели
использование неразрешённого примитивного DR
чужую Theory
цикл зависимостей
подмену Claim
подмену последовательности зависимостей
запись в память во время проверки
неоднозначную коллизию носителей H/A/O/I/P
```

Если переносная проекция заявляет лишний недостижимый элемент, отклоняется проекция. Сам посторонний Link в общей памяти не становится частью proof authority.

Положительный случай обязательно сохраняется:

```text
одно доказанное вхождение используется двумя позициями одного правила
```

## 15. Связь с L0 и коммутативностью сложения

Текущее состояние:

```text
N2a  = COMPLETE
N2b  = COMPLETE
IND  = COMPLETE
L0   = BLOCKED
L1   = NOT STARTED
COMM = NOT STARTED
```

После #1039:

```text
L0 representation = SUPPORTED
L0 trusted proof-Aset replay = GAP
```

Следующий шаг не должен добавлять специальный проверяющий механизм для L0.

Нужно проверить универсальный закон конечной асети доказательства. Если он проходит на общем корпусе и реальном L0, только тогда можно закрыть L0 и переходить к L1.

## 16. Следующий обязательный шаг

После принятия этой спецификации нужна отдельная проверка на опровержение только в тестах, без изменений production-кода.

Минимальные положительные случаи:

```text
простая цепочка двух примитивных DR
ветвящееся доказательство
повторное использование одного вхождения
производный TargetDR без Theory -> TargetDR
специализированная асеть без метки specialization
cross-scope асеть без метки cross-scope
реальный L0
```

Ключевой тест:

```text
одна rho выводится согласованно
из conclusion + всех premise slots
```

Также обязательно проверяется отсутствие коллизий кандидатной топологии раздела 4.

Если тестовый наблюдатель независимо принимает асеть, а текущая production-проверка её отвергает, получена точная граница минимального production delta.

Если кандидатная топология недостаточна, исправляется топология МТС, а не вводится host-only тип доказательства.

## 18. Критерий архитектурной завершённости

Архитектура считается правильной, если достаточно сказать:

```text
покажи корень асети доказательства и точную Теорию
```

и доверенный механизм способен восстановить и проверить весь доказательный авторитет без знания алгоритма, которым асеть была построена.

Целевая граница:

```text
всё доказательство выражено связями
```
