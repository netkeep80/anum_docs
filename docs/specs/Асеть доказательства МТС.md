# Асеть доказательства МТС

Статус: архитектурная спецификация исчисления доказательств.

Связанные задачи: #999, #1019, #1040.

Исполнимое основание решения: #1038 / #1039.

Принятая семантика МТС остаётся `v0.11`.

Активного смыслового кандидата нет.

Эта спецификация не вводит новую версию МТС и не меняет принятый контракт. Она фиксирует архитектурную границу доказательств, необходимую для дальнейшего развития проверяющего механизма.

---

## 1. Главный закон

Доказательство в МТС является асетью.

```text
ДОКАЗАТЕЛЬСТВО = АСЕТЬ СВЯЗЕЙ
```

Ни массив узлов, ни объект языка реализации, ни ориентированный граф, ни сериализация сами по себе не являются доказательством.

Они могут быть только проекциями одной и той же асети.

```text
асеть доказательства              <- authority
        |
        +-> массивы / индексы      <- обход
        +-> граф                   <- визуализация
        +-> JSON                   <- перенос
        +-> формальная нотация     <- текстовая проекция
```

Ни одна проекция не получает самостоятельного доказательного авторитета.

---

## 2. Асеть доказательства и история её построения — разные вещи

Нужно различать:

```text
что является доказательством
```

и:

```text
каким способом это доказательство было построено
```

Подстановка, специализация, перенос между областями ролей и композиция могут строить новую асеть доказательства.

Но они не должны становиться обязательными типами узлов внутри доказательства.

Неверная модель:

```text
PrimitiveProof
SpecializedProof
CrossScopeProof
ClosureProof
...
```

Такая модель создаёт второй язык доказательств поверх МТС.

Правильное направление:

```text
специализация
      ↓
строит или преобразует асеть
      ↓
получившаяся асеть проверяется сама по себе
```

После построения конечной асети проверяющему механизму не обязательно знать, какой функцией или алгоритмом она была получена.

История построения может сохраняться как происхождение или диагностическая информация, но не как источник доказательного авторитета.

## 3. Что уже подтверждено исполнимо

#1038 / #1039 установили четыре важных факта.

### 3.1. Повторное использование одной связи допустимо

Если правило требует одну и ту же доказанную связь в нескольких позициях, не нужно создавать искусственные копии.

Например:

```text
A
B
B
---
C
```

может зависеть от одного точного доказанного вхождения `B`, на которое ссылаются две позиции зависимостей.

То есть:

```text
число позиций зависимостей != число различных доказанных связей
```

### 3.2. Производное правило можно не превращать в примитивное

Если правило выведено из уже разрешённых правил, сам факт наличия связи вида:

```text
DerivedDR -> Theory
```

не даёт ему примитивного авторитета.

Авторитет производного правила должен идти от несомого доказательства.

### 3.3. Эти два свойства совместимы

Повторное использование одной доказанной связи сохраняется и при композиции производного доказательства.

### 3.4. Реальный L0 уже представим как асеть

Для цели:

```text
Nat0(A)
-------
Add(U,A,A)
```

все необходимые координаты уже можно собрать в одной асети МТС.

Следовательно:

```text
проблема представления = отсутствует
```

Оставшийся барьер находится в доверенном чтении и проверке такой асети.

## 4. Минимальная конечная нормальная форма

Следующая топология является целевой минимальной формой для проверки на опровержение.

Она ещё должна быть подтверждена отдельным исполнимым тестом.

### 4.1. Тождество производного доказательства

```text
I = TargetDR -> Theory
```

`TargetDR` задаёт утверждаемое производное правило.

Связь `I` сама по себе не является разрешением правила.

Примитивное разрешение по-прежнему имеет противоположную форму:

```text
Theory -> PrimitiveDR
```

Это различие принципиально.

### 4.2. Внешняя посылка

Посылка доказательства может быть представлена как:

```text
H = Claim -> I
```

Тем самым связь принадлежит выбранному доказательству и несёт точное утверждение `Claim`.

### 4.3. Применение примитивного правила

Для уже разрешённого примитивного правила:

```text
A = PrimitiveDR -> ExactSequence(dependencies)
```

`dependencies` содержит ссылки на доказанные вхождения или внешние посылки.

Одна и та же ссылка может встречаться в последовательности несколько раз.

### 4.4. Доказанное вхождение

Результат применения правила:

```text
O = Claim -> A
```

Здесь `Claim` — фактически доказанная связь в текущей области доказательства.

Это важное отличие от старой модели, где результат узла фактически считался равным телу исходного правила.

### 4.5. Корень доказательства

Минимальный кандидат:

```text
P = I -> TargetOccurrence
```

где `TargetOccurrence` — конечное доказанное вхождение.

От корня должен восстанавливаться весь используемый замкнутый набор зависимостей.

Неиспользуемые узлы не должны давать доказательного авторитета.

---

## 5. Почему отдельный `Claim` у доказанного вхождения необходим

Рассмотрим общее правило сложения:

```text
Add(A,B,C)
S0(B,B1)
S0(C,C1)
------------
Add(A,B1,C1)
```

Для L0 оно используется в форме:

```text
Add(U,N,N)
S0(N,N1)
S0(N,N1)
-------------
Add(U,N1,N1)
```

Примитивное правило остаётся тем же самым.

Но фактическое утверждение узла уже находится в другой области ролей.

Поэтому проверяющий механизм должен проверять:

```text
PrimitiveDR
+ фактические посылки
+ фактический результат
----------------------
существует одна согласованная структурная подстановка
```

Он не должен требовать:

```text
actual Claim == source Rule body
```

Такое требование и создаёт нынешний барьер между уже представимой асетью и доверенным replay.

---

## 6. Подстановка должна определяться по всему правилу

Недостаточно определять подстановку только по заключению.

В правиле сложения роли `B` и `C` могут встречаться в посылках, но не давать достаточной информации в заключении.

Поэтому одна подстановка должна одновременно удовлетворять всей системе:

```text
source conclusion -> actual conclusion
source premise 1  -> actual premise 1
source premise 2  -> actual premise 2
...
```

То есть проверяется не отдельный шаблон, а всё правило вывода как единая система структурных ограничений.

Для каждой роли должно получиться ровно одно согласованное значение.

Повторное появление роли обязано давать ту же самую связь.

Противоречивые значения должны приводить к отказу.

---

## 7. Граница первой реализации подстановки

Для первого исполнимого шага достаточно уже существующей границы:

```text
роль источника -> роль цели
```

или:

```text
роль источника -> точная заземлённая связь
```

Это покрывает текущий L0:

```text
A  -> U
B  -> N
C  -> N
B1 -> N1
C1 -> N1
```

Не нужно сразу разрешать произвольное выражение с несколькими целевыми ролями в качестве значения одной роли источника.

Такое расширение можно исследовать отдельно, если оно реально понадобится математике.

---

## 8. Защита от захвата роли

Роль существует только потому, что она явно объявлена ролью в выбранном словаре.

Заземлённая связь не должна внезапно стать ролью только потому, что её тождество совпало с ролью другой области.

При переносе между областями необходимо сохранять разделение:

```text
объявленная роль источника -> разрешённая подстановка
заземлённая часть источника -> точное тождество
```

Если заземлённая часть неожиданно попадает в роль целевой области, проверка должна отказать.

Таким образом общность доказывается структурой, а не именем переменной и не соглашением языка реализации.

---

## 9. Нормализация конечных преобразований

Для специализации, переноса между областями и обычной конечной композиции целевой процесс выглядит так:

```text
исходная асеть доказательства
+ структурное преобразование
        ↓
недоверенное построение новой асети
        ↓
каноническая конечная асеть доказательства
        ↓
независимый доверенный replay
```

Критический закон:

```text
успех преобразователя != доказательство
```

Доказательством является только результат, который независимо прошёл доверенную проверку.

После нормализации проверка конечной асети не должна требовать метку:

```text
specialization
cross-scope
composed
```

---

## 10. Примитивный и производный авторитет

Примитивный авторитет задаётся выбранной Теорией:

```text
Theory -> Rule
Theory -> DR
```

Производное правило не должно автоматически получать такую связь.

Запрещённая схема:

```text
проверили один раз
      ↓
добавили Theory -> DerivedDR
      ↓
дальше считаем DerivedDR примитивным
```

Правильная схема:

```text
DerivedDR -> Theory
+ асеть доказательства
      ↓
доверенная проверка доказательства
```

Точная ревизия Теории при этом остаётся неизменной.

---

## 11. Особая граница индукции и замыкания

Не каждое доказательное основание можно конечным образом развернуть в цепочку обычных применений правил.

Например структурная индукция означает потенциально неограниченное семейство:

```text
P(U)
P(N) -> P(N1)
---------------
Nat0(N) -> P(N)
```

Нельзя материализовать бесконечную цепочку:

```text
P(U)
P(S(U))
P(S(S(U)))
...
```

Поэтому для индукции или наименьшего замыкания само основание должно быть явной асетью доказательного авторитета.

Но это всё равно не создаёт специальный объект языка реализации.

Правильная граница:

```text
асеть основания замыкания
+ асеть базы
+ асеть шага
+ структурные отображения
        ↓
асеть итогового доказательства
```

Доверенный механизм обязан проверить все эти асети и их структурные отношения.

Неверно:

```text
kind = induction
```

или:

```text
InductionProof = trusted
```

---

## 12. Что является авторитетом, а что нет

Авторитет:

```text
точные связи МТС
точная топология асети
точная Theory
явные разрешения примитивных правил
явная асеть неприводимого доказательного основания
```

Не авторитет:

```text
boolean verified
hash без повторной проверки содержания
имя функции
класс TypeScript
тип JSON
порядок массива
указатель на ранее проверенный объект
метка specialized / cross-scope / induction
```

---

## 13. Требования к доверенному replay

Доверенная проверка асети должна:

1. начинаться от явного корня доказательства;
2. восстанавливать тождество целевого производного правила и точную Теорию;
3. читать все зависимости из связей МТС;
4. различать внешние посылки и доказанные вхождения по их топологии;
5. разрешать повторные ссылки на одно вхождение;
6. для каждого примитивного шага проверять точное разрешение правила в Теории;
7. находить одну согласованную структурную подстановку по заключению и всем посылкам шага;
8. сохранять точное тождество заземлённых частей;
9. отвергать захват ролей;
10. отвергать циклические доказательные зависимости;
11. отвергать недостижимые лишние узлы;
12. отвергать самопринятие производного правила;
13. не изменять память;
14. не изменять точную ревизию Теории.

---

## 14. Отрицательная граница

Следующий исполнимый корпус должен специально отвергать:

```text
DerivedDR -> Theory без доказательной асети
поддельное Theory -> DerivedDR
отсутствующую зависимость
лишнюю зависимость
неверное число позиций посылок
противоречивую подстановку одной роли
частичную подстановку
захват заземлённой связи ролью цели
использование неразрешённого примитивного DR
чужую Theory
цикл зависимостей
недостижимый узел
подмену Claim после построения
подмену последовательности зависимостей
запись в память во время replay
```

Отдельно должен сохраняться положительный случай:

```text
одна доказанная связь используется двумя позициями одного правила
```

## 15. Связь с L0 и коммутативностью сложения

Текущее состояние арифметического пути:

```text
N2a  = COMPLETE
N2b  = COMPLETE
IND  = COMPLETE
L0   = BLOCKED
L1   = NOT STARTED
COMM = NOT STARTED
```

После #1039 блокировка L0 уточнена:

```text
L0 representation = SUPPORTED
L0 trusted proof-Aset replay = GAP
```

Поэтому следующий шаг не должен добавлять специальный проверяющий механизм для L0.

Он должен проверить универсальный закон конечной асети доказательства.

Если этот закон проходит на общем корпусе и затем на реальном L0, только после этого можно считать L0 закрытым и переходить к L1.

---

## 16. Следующий обязательный шаг

После принятия этой спецификации нужен отдельный test-only falsifier.

Он должен проверить минимальную кандидатную нормальную форму из раздела 4 без изменений production-кода.

Минимальные положительные случаи:

```text
простая цепочка двух примитивных DR
ветвящееся доказательство
повторное использование одного вхождения
производный TargetDR без Theory -> TargetDR
специализированная асеть без метки specialization
cross-scope асеть без метки cross-scope
реальный L0
```

Обязательный ключевой тест:

```text
одна rho выводится согласованно
из conclusion + всех premise slots
```

Если test-only наблюдатель может независимо принять такую асеть, а текущий production replay её отвергает, получаем точную границу для минимального production delta.

Если сама кандидатная топология оказывается недостаточной, исправляется топология, а не вводится host-only тип доказательства.

## 18. Критерий архитектурной завершённости

Архитектура считается правильной, если можно сказать:

```text
покажи мне корень асети доказательства и точную Теорию
```

и этого достаточно, чтобы доверенный механизм восстановил и проверил весь доказательный авторитет без знания того, каким алгоритмом асеть была построена.

Именно это является целевой границей:

```text
всё доказательство выражено связями
```
