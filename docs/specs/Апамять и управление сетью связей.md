# Апамять и управление сетью связей

Этот документ задаёт текущую границу апамяти, материализации и заземлённого исполнения МТС v0.13.

Документ является нормативным владельцем законов `L1`, `L8` и `L9`.

Связанные владельцы:

- [Система аксиом МТС](../theory/Система%20аксиом%20МТС.md) — тождество Связи, акорень и граница фундаментальных положений;
- [Основания МТС](../theory/Основания%20МТС.md) — объяснение укоренения, хиральности и области теории;
- [Ачисла и сериализация](Ачисла%20и%20сериализация.md) — `Resolve`, структурный перенос и целевая материализация;
- [Формальная нотация МТС](Формальная%20нотация%20МТС.md) — `Context`, `Dictionary / Grammar / Theory / Rule` и полномочия `FORMAL`.

## 1. Что такое апамять

Апамять — конкретная материализованная асеть Связей и доступные над ней возможности чтения и изменения.

Она не является универсумом всех Связей, допускаемых МТС.

Смысловая запись:

```text
X = A ⟼ B
```

и технический доступ к ней различаются:

```text
semantic Link
!= local handle
!= storage slot
!= source occurrence
!= path coordinate
```

Тождество Связи задаётся структурой МТС, а не номером записи в конкретной памяти.

<a id="mts-law-L1"></a> <!-- нормативный владелец -->

### L1. Корневое основание остаётся системой Связей

Онтологическая сущность одна:

```text
Link
```

Единственный акорень:

```text
R = R ⟼ R
```

Корневой базис:

```text
O = O ⟼ R
C = R ⟼ C
L = O ⟼ C
U = C ⟼ O
```

Апамять не вводит второй корень, отдельную пустую сущность или глобальный технический идентификатор Связи.

## 2. Состояния знания при чтении

<a id="mts-law-knowledgeStateSeparation"></a> <!-- служебный якорь -->

Для чтения и разрешения различаются три результата:

```text
UNINTERPRETABLE
NOT_FOUND
FOUND(X)
```

`UNINTERPRETABLE` означает: предъявленного структурного основания недостаточно, чтобы корректно интерпретировать запрос.

`NOT_FOUND` означает: запрос интерпретируем, но соответствующая материализованная Связь не найдена в выбранной памяти.

`FOUND(X)` означает: найдена конкретная Связь `X`.

Поэтому:

```text
NOT_FOUND
!= доказательство несуществования

UNINTERPRETABLE
!= NOT_FOUND
```

Конкретная апамять сообщает о своём текущем состоянии, а не о полном универсуме МТС.

## 3. Чтение и изменение — разные возможности

```text
читать
искать
разрешать
проверять
воспроизводить
!=
создавать
удалять
изменять
материализовать
```

В частности:

- `Resolve` является чтением;
- отсутствие цели при `Resolve` не даёт права её создать;
- построение носителя адреса и построение адресуемой смысловой цели — разные действия;
- целевая материализация требует отдельного полномочия.

Точные адресные правила принадлежат [спецификации ачисел](Ачисла%20и%20сериализация.md#mts-law-resolveMaterializeSeparation).

## 4. Каноническая материализация

Если материализация `A ⟼ B` разрешена, повторный запрос той же смысловой пары должен сходиться к той же Связи:

```text
X = A ⟼ B

ensure(A,B) -> X
ensure(A,B) -> X
```

Технически разные акты записи не создают разные смысловые экземпляры одной пары.

Отдельные формы самовхождения канонизируются по своей структуре:

```text
ROOT
START(X)
END(X)
PAIR(A,B)
```

Материализация не может использовать технический handle как дополнительный смысловой полюс.

## 5. Полномочие смысловой записи

<a id="mts-law-L8"></a> <!-- нормативный владелец -->

### L8. Смысловая материализация требует явного полномочия

Для записи смысловых `START`, `END` или `PAIR` требуется согласованная цепочка:

```text
точный source
+ выбранный Dictionary Use
+ Grammar
+ фиксированная Theory
+ допущенный StructuralRule
+ проверенный запрос построения
```

Наличие представления или структурного описания само по себе не даёт права создавать смысловую цель.

До прохождения этой границы могут существовать Связи представления и доказательства, но не новая авторизованная смысловая цель.

Неуспешная авторизация должна завершаться до смысловой записи.

## 6. Область допустимых Связей и циклы

<a id="mts-law-L9"></a> <!-- нормативный владелец -->

### L9. Тождество требует конечного ROOT-заземления

Принятая смысловая область v0.13 требует конечной рекурсивной декомпозиции до `ROOT`.

Прямые собственные самовхождения:

```text
ROOT
START
END
```

не считаются новой внешней зависимостью.

Но цикл зависимостей между **разными** предполагаемыми Связями не входит в текущую принятую смысловую область:

```text
A depends on B
B depends on A
->
cyclic-grounding
```

Поэтому для v0.13 одновременно верны два утверждения:

```text
accepted semantic domain:
  distinct-node dependency cycles = not admitted

ontology:
  any conceivable rooted cyclic structure is not declared impossible
```

Циклическая структура может существовать как данные описания, однако текущие доказательство тождества, канонический древовидный носитель, перенос и рабочая материализация не устанавливают для неё смысловую Связь.

Это **не** превращает граф в основание МТС: основанием остаётся Связь. Упоминание циклического графа относится только к возможной форме данных представления вне текущего доказанного носителя.

## 7. Позиции, вхождения и техническая история

Одна смысловая Связь может участвовать во многих местах:

```text
[L, L, L]
```

Отсюда не возникают три смысловые `L`.

Необходимо различать:

```text
смысловая Связь
позиция
вхождение
акт доступа
техническая история
```

Если происхождение или временной порядок важны, они должны быть представлены отдельной структурой, а не скрыты в техническом идентификаторе самой Связи.

## 8. Сохранение и технические адреса

При переносе или долговременном восстановлении смысл должен сохраняться с точностью до переименования локальных технических handles.

```text
same semantic structure
may use
different local handles
```

Текущая v0.13 не включает доказательство восстановления нефундированных взаимных циклов только по техническим идентификаторам.

Поэтому persistence-механизм не может расширять принятую смысловую область лишь потому, что умеет хранить произвольные идентификаторы.

## 9. Атомарная граница изменений

Сложная операция может внутренне подготавливать несколько Связей, но публикация смыслового изменения должна иметь одну явную границу:

```text
успех
-> виден согласованный новый результат

ошибка
-> смысловая цель не опубликована частично
```

Для целевой материализации действует более сильное требование fail-closed: неверное точное свидетельство должно быть отклонено до записи смысловой цели.

## 10. Контекст и область исполнения — разные конструкции

`Context` задаёт структурное отношение:

```text
Context(parent,current)
=
START(parent ⟼ current)
```

Его владельцем является [формальная нотация](Формальная%20нотация%20МТС.md#mts-law-explicitKContext).

`Scope` заземлённого исполнения — другая конструкция. Он задаёт текущий рабочий набор истин относительно выбранной `Theory`:

```text
Scope = START(seed ⟼ Theory)

Scope ⟼ truth_1
Scope ⟼ truth_2
...
```

Следовательно:

```text
Context
!=
Scope
```

Обе конструкции имеют `START)-форму в текущей конвенции, но выполняют разные роли.

<a id="amemory-theory-admission"></a> <!-- допуск теории -->
## 11. Контекстная истина и заземлённая Theory

Текущая истина имеет форму:

```text
truth = K ⟼ A
```

где `K` — явный контекст, а `A` — текущее утверждаемое значение.

Исполнимое заземлённое отношение:

```text
relation = A ⟼ ExactSequence(B...)
```

получает полномочие только через:

```text
admission = Theory ⟼ relation
```

Текущая `Theory` является полным фронтиром исполнимых заземлённых отношений: отдельно скрытый список opcodes или функций не требуется.

Отношение другой `Theory` для текущего `Scope` инертно.

<a id="amemory-elementary-transition"></a> <!-- реакция и переход -->
## 12. Обобщённая реакция

Текущий закон заземлённого исполнения:

```text
K ⟼ A
Theory ⟼ (A ⟼ ExactSequence(B...))
------------------------------------
K ⟼ B...
```

Контекст `K` сохраняется, а значение заменяется всеми выходами всех допущенных отношений для `A`.

Исполнение не использует отдельное смысловое ветвление по имени функции, `opcode`, типу правила или конкретному терму.

## 13. Нет отношения, `ZERO`, `ONE` и `MANY`

Это различие принципиально.

### Нет допущенного отношения

Если для текущего `A` под выбранной `Theory` нет ни одного допущенного отношения:

```text
K ⟼ A
->
K ⟼ A
```

Текущая истина сохраняется.

Это ветвь «нет продолжения», а не явное нулевое отображение.

### Нулевой образ (`ZERO`)

Если допущено отношение с пустой точной последовательностью:

```text
Theory ⟼ (A ⟼ ExactSequence())
```

то:

```text
K ⟼ A
->
<нет этой истины в successor Scope>
```

То есть явный пустой образ удаляет текущую истину из следующего `Scope`.

### Один выход (`ONE`)

```text
A -> [B]
```

даёт:

```text
K ⟼ A
->
K ⟼ B
```

### Много выходов (`MANY`)

```text
A -> [B,C,...]
```

или несколько одновременно допущенных отношений для `A` порождают все их выходы.

Если разные ветви сходятся к одной и той же `K ⟼ E`, каноническое тождество Связи схлопывает дубль.

### E2/W2/W3. Полный элементарный переход

> **Статус:** производный результат исследования #1558 после принятия MTS v0.13. Он уточняет уже реализованный закон заземлённой реакции и не изменяет принятую семантику v0.13.

Для текущей истины `K ⟼ A` обозначим через `R_T(A)` все отношения, которые одновременно:

```text
допущены выбранной Theory
и
имеют A своим antecedent
```

Тогда элементарный переход полностью задаётся одним законом:

```text
если R_T(A) пусто:
  successor contribution = { K ⟼ A }

иначе:
  successor contribution =
    объединение всех { K ⟼ B_j }
    по всем выходам всех отношений из R_T(A)
```

Отсюда без дополнительных ветвей следуют:

```text
нет допущенного отношения
  -> сохранить K ⟼ A

все допущенные образы пусты
  -> не переносить K ⟼ A в следующий Scope

ровно один канонический выход
  -> K ⟼ B

несколько канонических выходов
  -> K ⟼ B, K ⟼ C, ...
```

Если для одного `A` одновременно допущены пустой и непустой образы, пустой образ просто не добавляет выходов, а непустые образы продолжают участвовать в общем объединении. `ZERO` не является запретом для других одновременно допущенных отношений.

#### `NOT_FOUND` не является условием сохранения само по себе

Состояние чтения `NOT_FOUND` относится к **конкретному запросу** на материализованную Связь. Из того, что один кандидат `A ⟼ X` не найден, не следует, что под текущей `Theory` отсутствует другое допущенное отношение для того же `A`.

Поэтому:

```text
specific relation lookup = NOT_FOUND
!=
R_T(A) is empty
```

Сохранение `K ⟼ A` разрешено только после установления более сильного факта:

```text
NO_ADMITTED_RELATION(A, Theory)
```

то есть после исчерпывающего просмотра релевантного фронтира допущений выбранной `Theory`. Реализация может получать отдельные `NOT_FOUND` во время такого поиска, но они не являются самостоятельным семантическим исходом реакции.

#### W3. Семантическое удаление без физического удаления

Когда `K ⟼ A` не входит в следующий `Scope`, это означает только:

```text
K ⟼ A не является членом опубликованного successor Scope
```

Из этого не следует удаление самой Связи `K ⟼ A`, старого `Scope` или их физического носителя. Они могут оставаться канонически доступными как техническая история, пока текущесть определяется опубликованным корнем апамяти.

W2/W3 проверены одним исполняемым свидетелем после принятия v0.13 для:

```text
NO_ADMITTED_RELATION
ZERO
ONE
MANY
ZERO + непустой образ одновременно
конвергенция дублей
specific NOT_FOUND при наличии другого допущенного отношения
сохранение старой физической топологии
```

Для E2 принятой v0.13 достаточно: принятый заземлённый исполнитель уже реализует этот закон. Это **локальный вывод E2**; итоговая классификация всей #1558 остаётся открытой.

## 14. Следующая область исполнения и текущесть

Реакция строит новый полный `Scope`, не изменяя текущий рабочий набор поэлементно в процессе вычисления.

После успешного построения выполняется один атомарный handoff:

```text
old current Scope
-> successor Scope
```

До handoff текущим остаётся старый `Scope`.

Сам выбор «какой `Scope` сейчас текущий» остаётся непрозрачной изменяемой границей апамяти. Он не выводится из порядка добавления Связей в техническую историю.

Это важная граница substrate:

```text
Link-carried program state
!=
mechanism selecting current Scope
```

<a id="amemory-currentness"></a> <!-- текущесть -->
### E1/W1. Точное полномочие текущести

> **Статус:** производный результат исследования #1558 после принятия MTS v0.13. Он уточняет уже принятую границу апамяти и не добавляет новый семантический закон v0.13.

Текущесть не является внутренним свойством самого `Scope` и не выводится из физического возраста Связей. Смысловое состояние исполняемой апамяти задаётся относительно **единственного опубликованного текущего корня** этой апамяти:

```text
publishedRoot(M) = S_t
semanticState(M,t) = members(S_t)
```

Структура `S_t` и его членство выражены Связями. Механизм хранения опубликованного корня остаётся технической границей апамяти.

Минимальный контракт публикации:

```text
до построения successor:
  publishedRoot = S_t

во время построения successor:
  publishedRoot = S_t

атомарная публикация:
  expected current = S_t
  publish S_t -> S_(t+1)

после публикации:
  publishedRoot = S_(t+1)
```

Поэтому существование старого `S_t` или его членов в физической памяти после публикации не делает их текущими. Текущим является только `Scope`, выбранный опубликованным корнем.

Это полномочие нельзя подменять локальной переменной конкретной реализации. Такая переменная, ячейка базы или регистр ускорителя может быть лишь реализацией одного и того же контракта апамяти: наблюдаемым смысловым фактом остаётся выбранная структурная Связь `Scope` и атомарная смена выбора.

Простой append-only кандидат:

```text
CURRENT ⟼ S_t
CURRENT ⟼ S_(t+1)
```

недостаточен: обе Связи остаются одинаково доступными, и сама топология не указывает, какая из них новее. Это уже зафиксировано falsifier-свидетелем A72n. Для чисто связевого выбора потребовалась бы дополнительная семантика жизненного цикла или порядка; E1 её не вводит.

Минимальный W1 имеет вид:

```text
до реакции:
  publishedRoot = S0
  S0 ⟼ (K ⟼ A)
  Theory ⟼ (A ⟼ [B])

кандидат:
  S1 ⟼ (K ⟼ B)
  publishedRoot всё ещё S0

handoff:
  publish S0 -> S1

после реакции:
  publishedRoot = S1
  semantic state = { K ⟼ B }

физически могут сохраниться:
  S0
  K ⟼ A
```

Таким образом, для E1 принятой v0.13 достаточно: структурное состояние уже задаётся `Scope`, а текущесть уже принадлежит явно оставленной границе current-root апамяти. Это **локальный вывод E1**; итоговая классификация всей #1558 остаётся открытой до E2–E7.

### E3/W4/W5. Логическая реакция и физический планировщик

> **Статус:** производный результат исследования #1558 после принятия MTS v0.13. W4 подтверждает инвариантный класс, W5 обнаруживает границу принятого исполнителя. Нового семантического закона этот шаг не вводит.

Для параллельного исполнения нужно строго развести четыре слоя:

```text
1. logical pre-state
2. physical scheduling
3. candidate generation
4. semantic publication
```

Физический порядок потоков, рабочих групп, ядер или обхода массива не может определять смысловой `state(t+1)`.

#### W4. Инвариантный класс

Если во время одной логической реакции:

```text
Theory frontier не изменяется
и
применимость реакции одного текущего члена
не изменяется действиями другого текущего члена
```

то перестановка порядка обработки текущих членов даёт один и тот же экстенсиональный successor `Scope`.

Для этого класса принятая v0.13 уже достаточна: результаты всех независимых реакций можно вычислять в любом физическом порядке, канонически объединить и опубликовать одним handoff.

#### W5. Взаимодействующая реакция с живой `Theory`

Принятый заземлённый исполнитель читает фронтир `Theory` из живой памяти. Поэтому текущий член может в ходе реакции материализовать новую:

```text
Theory ⟼ relation
```

и другой член той же реакции увидит её только в том случае, если физически обрабатывается позже.

Исполняемый свидетель воспроизводит два порядка одного исходного состояния:

```text
generator first:
  matches = 2
  generated relation действует на target в той же реакции

target first:
  matches = 1
  target сохраняется до следующей реакции
```

Следовательно:

```text
same semantic pre-state
+
different physical schedule
->
different immediate successor Scope
```

Сохранённый A73k дополнительно показывает, что в этом конкретном монотонном примере обе траектории затем сходятся к одной экстенсиональной неподвижной точке. Но:

```text
same final fixed point
!=
same semantic trajectory
```

и потому равенства конечного результата недостаточно для определения `state(t) -> state(t+1)`.

### Граница E3

Для общей конкурентной апамяти принятой v0.13 **недостаточно как полного определения одного логического шага**, пока не определена видимость изменений `Theory` внутри реакции.

Это само по себе не доказывает необходимость нового семантического закона. E4 ниже проверяет, достаточно ли отдельного профиля исполнения с явной границей снимка/публикации.

До этого запрещено считать порядок:

```text
thread
work-group
GPU lane
array iteration
allocation
```

семантическим законом.
<a id="amemory-theory-snapshot"></a> <!-- снимок теории -->
### E4. Видимость изменений `Theory` и граница снимка

> **Статус:** производный результат исследования #1558 после принятия `MTS v0.13`. Принятая `v0.13` не изменяется. `E4` классифицирует недостающую границу переносимого исполнения.

`W5` показал, что текущая рабочая реализация заземлённой реакции читает `Theory` из живой памяти повторно для каждого текущего члена. Поэтому новое допущение:

```text
Theory ⟼ relation
```

может стать видимым другому члену в той же реакции или не стать — в зависимости от физического порядка обхода.

Такое поведение допустимо как конкретная реализация принятого исполнителя, но оно не может быть полным переносимым определением одного логического шага: `thread / work-group / GPU lane / array order` не имеют смыслового полномочия.

#### Кандидат профиля: снимок `Theory` в начале реакции

Минимальная schedule-independent граница задаётся так:

```text
reaction t begins
  TheorySnapshot_t := admitted grounded relations
                      visible before candidate generation

for every member of current Scope:
  discover images only in TheorySnapshot_t
  generate candidate successor Links

writes during reaction:
  may materialize physically immediately
  but do not enter TheorySnapshot_t

publish successor Scope atomically

reaction t+1 begins
  TheorySnapshot_(t+1) := then-current admitted relations
```

Снимок — не новая сущность МТС и не обязательный массив или копия памяти. Это логическая граница наблюдаемости. Процессор, БД, браузер или ускоритель могут реализовать её любым способом, если все участники одного логического шага видят один и тот же фронтир полномочия.

#### Свидетель E4

Для исходного состояния, где один текущий член порождает новое допущение для другого:

```text
generator:
  Theory ⟼ BOOT
  BOOT ⟼ [candidateRelation]

target:
  K ⟼ A

candidateRelation:
  A ⟼ [B]
```

Профиль снимка даёт одну и ту же траекторию при обоих физических порядках:

```text
reaction 1:
  matches = 1
  new Theory ⟼ candidateRelation physically exists
  current target remains K ⟼ A

reaction 2:
  matches = 1
  target becomes K ⟼ B

reaction 3:
  matches = 0
  quiescent
```

То есть:

```text
generator-first trajectory
=
target-first trajectory
```

в отличие от поведения принятой реализации с видимостью `live same-reaction`, где первый непосредственный преемник различается.

#### Почему это профиль исполнения, а не новая семантика основания

E4 не вводит:

```text
новый вид Связи
новый структурный аспект
новое тождество
новое отношение Context / Theory
новую MTS-онтологию времени
```

Он выбирает **когда уже существующее структурное полномочие `Theory` наблюдается исполнителем** относительно границы одной реакции.

Принятая `v0.13` содержит необходимые структуры и операции, но её принятый контракт не выбирает между:

```text
same-reaction live visibility
и
reaction-start snapshot visibility
```

Поэтому для полной переносимой апамяти результат `E4`:

```text
E4_CLASSIFICATION = V013_PLUS_EXECUTION_PROFILE
V013_SUFFICIENT for complete #1558 = eliminated
SEMANTIC_EXTENSION_REQUIRED = not established
```

Это ещё не окончательный вердикт всей #1558: `E5–E7` могут обнаружить необходимость будущего смыслового закона. Но вариант `V013_SUFFICIENT` уже недостаточен, потому что независимая реализация не может вывести границу видимости `Theory` только из принятой `v0.13`.

Независимое от планировщика причинное замыкание внутри одного шага теоретически может быть другим профилем, но оно потребовало бы отдельного определения замыкания, его наблюдаемых границ и поведения при бесконечной активации. `E4` не добавляет такую более сильную механику: минимальным кандидатом остаётся снимок на входе реакции.

## 15. Покой и неподвижная точка

Текущая реакция считается `quiescent`, когда ни одна текущая истина не имеет допущенного отношения под выбранной `Theory`:

```text
matchedRelations = 0
```

Тогда:

```text
successor Scope не создаётся
atomic handoff не выполняется
current Scope остаётся прежним
```

Это точное понятие `fixed point` для принятого заземлённого исполнителя.

Оно не определяется техническим порядком обхода памяти и не означает автоматически равенство любых двух произвольно построенных снимков.

<a id="amemory-recurrence"></a> <!-- рекуррентность -->
### E5/W6. Рекуррентность и неограниченное исполнение

> **Статус:** производный результат исследования #1558 после принятия `MTS v0.13`. Принятая `v0.13` не изменяется. Для переносимого исполнения наблюдение относится к выбранной границе логической реакции из E4.

Покой устанавливается только после **полной смысловой проверки** текущего `Scope` относительно выбранного фронтира `Theory`:

```text
complete logical reaction
+ matchedRelations = 0
=> quiescent
=> successor Scope не публикуется
=> handoffCount = 0
```

Поэтому временно пустая очередь потока, рабочей группы или линии GPU не является свидетельством покоя: физический планировщик сначала должен завершить проверку всего текущего смыслового шага.

Рекуррентность — другой случай. Состояние рекуррентно, если после ненулевого числа **активных** переходов снова возникает то же нормализованное смысловое состояние:

```text
S_i ≡ S_j,  i < j
и между ними есть хотя бы один активный переход
```

Равенство здесь относится к смысловому содержимому текущего состояния, а не к локальному техническому адресу корня `Scope`. Исторические `Scope` могут быть разными физическими Связями.

#### W6 — конечная сеть без покоя

Для неизменной `Theory`:

```text
current:
  K ⟼ A

admitted:
  A ⟼ [B]
  B ⟼ [A]
```

получается:

```text
S0 = { K ⟼ A }
  -> S1 = { K ⟼ B }
  -> S2 = { K ⟼ A }
  -> S3 = { K ⟼ B }
  -> ...
```

Каждый шаг имеет:

```text
matchedRelations = 1
handoffCount = 1
quiescent = false
```

и при этом:

```text
semanticState(S0) = semanticState(S2)
ScopeHandle(S0) != ScopeHandle(S2) допустимо
```

Это конструктивный свидетель **неограниченного исполнения**: одна и та же смысловая конфигурация возвращается при неизменной `Theory`, поэтому тот же активный цикл может повторяться без достижения покоя.

Важно:

```text
recurrence != quiescence
nontermination != обязательно recurrence
```

Рекуррентный цикл достаточен, чтобы показать отсутствие глобальной гарантии завершения, но не всякое неограниченное исполнение обязано быть периодическим.

#### Структурный `END` не является глобальной остановкой

Канонический знак `C` имеет структурный класс `END`, но один этот класс не останавливает заземлённый исполнитель. Если выбранная `Theory` допускает продолжение из `C`, переход остаётся активным.

Свидетель E5 использует:

```text
A ⟼ [C]
C ⟼ [A]
```

и получает активный цикл через канонический `END`-знак. Следовательно:

```text
STRUCTURAL_END_ASPECT_IMPLIES_GLOBAL_HALT = FALSE
```

Если конкретная теория или будущий профиль вводит собственное явное условие завершения, оно должно быть сформулировано отдельно и не выводится автоматически из структурного аспекта `END`.

#### Классификация E5

```text
QUIESCENCE =
  complete reaction with matchedRelations = 0

RECURRENCE =
  repeated semantic state with active transitions

GLOBAL_TERMINATION_REQUIRED = FALSE
STRUCTURAL_END_ASPECT_IMPLIES_GLOBAL_HALT = FALSE

E5_CLASSIFICATION = V013_PLUS_EXECUTION_PROFILE
SEMANTIC_EXTENSION_REQUIRED = not established
E6/E7 = OPEN
```

E5 не вводит новой онтологии МТС. Он уточняет наблюдаемые состояния исполнения после выбора E4-границы реакции.

## 16. Живая Theory и самoактивация

Исполнимые отношения обнаруживаются непосредственно через текущие Связи:

```text
Theory ⟼ relation
```

Поэтому новое корректно материализованное допущение `Theory ⟼ relation` становится частью исполнимого фронтира той же живой апамяти без отдельной host-регистрации функции.

Это позволяет `Theory` изменять набор будущих реакций связевой структурой.

Принятая рабочая реализация `v0.13` читает этот фронтир из живой памяти и потому может увидеть новое допущение ещё внутри текущего вызова реакции. `E3/E4` показали, что точная **межреакционная граница видимости** этим фактом не определяется: для переносимого конкурентного исполнения #1558 требуется отдельно управляемый профиль исполнения. Минимальный кандидат `E4` фиксирует `Theory` на входе логической реакции и допускает новые допуски к исполнению со следующей реакции.

Но отсюда не следует, что произвольное высокоуровневое `StructuralRule` уже полностью самохостящимся образом компилируется в заземлённое отношение.

## 17. Граница self-hosting

Внутри Связей уже находятся:

```text
Theory
admitted grounded relations
Context / Scope structures
contextual truths
outputs
program-specific semantic selection
```

Заземлённый исполнитель использует один общий закон реакции и не содержит смыслового ветвления по функции или `opcode`.

Внешней substrate-границей остаются:

- сама апамять и операции доступа к её Связям;
- механизм выбора текущего `Scope`;
- атомарное переключение на следующий `Scope`;
- общий цикл исполнения;
- механика `ExactSequence`;
- ввод-вывод и долговременный технический носитель;
- отдельный слой заземления произвольных высокоуровневых правил.

Поэтому корректная формулировка:

```text
scoped self-hosted program semantics
!=
fully self-hosted MTS system
```

<a id="amemory-hierarchical-result"></a> <!-- иерархический результат -->
### E6. Иерархический результат и вложенный контекст

> **Статус:** производный результат исследования #1558 после принятия `MTS v0.13`. Принятая `v0.13` не изменяется.

Нужно различать две разные задачи:

```text
иерархическая Link-топология результата
!=
пошаговое построение иерархического Result
   деревом временных Context
```

Первая задача уже покрывается обычной структурой Связей. Результатом заземлённой реакции может быть одна Связь с произвольной допустимой вложенной топологией; исполнитель переносит её как обычный выход отношения и не обязан знать внутреннюю форму результата.

Минимальный свидетель E6 использует:

```text
H = X ⟼ (Y ⟼ Z)

current:
  K ⟼ A

admitted:
  A ⟼ [H]

next:
  K ⟼ H
```

Для этого не требуются:

```text
Result slots
дерево дочерних Context
версии Result
path-copy
merge / rebase
отдельный текущий корень Result
```

То есть внутренняя иерархия результата сама по себе не расширяет минимальный закон реакции.

#### Сохранённая линия A72u/A72v

Исследование A72u остаётся положительным ограниченным свидетелем другой задачи:

```text
Context tree = временный строительный каркас
Result tree  = отдельная сохраняемая структура
Context node -> ссылка на конкретную часть Result
```

Для одноразового заполнения заранее известных слотов было показано:

```text
разные Context могут заполнять разные части
листья могут завершаться в разном порядке
готовый слот сохраняется после ухода дочернего Context
корень Result остаётся тем же
```

При этом A72u явно оставил внешними проверку готовности слота и общий случай изменяемой текущести Result. A72v с неизменяемыми версиями, копированием пути и вопросом слияния соседних обновлений был закрыт без слияния и сохранён как отложенное исследование.

Следовательно, эти механизмы не нужны для уже установленной минимальной семантики E1–E5 и не должны автоматически становиться частью переносимого профиля исполнения.

Классификация E6:

```text
HIERARCHICAL_LINK_AS_RESULT = supported by minimal reaction

DYNAMIC_HIERARCHICAL_RESULT_CONSTRUCTION
NESTED_CONTEXT_RESULT_LIFECYCLE
PERSISTENT_RESULT_VERSIONS
  = INDEPENDENT_LATER_FEATURE

DEFERRED != REJECTED
SEMANTIC_EXTENSION_REQUIRED = not established
E7 = OPEN
```

Эта классификация не запрещает будущий профиль с двумя связанными деревьями контекста и результата. Она только фиксирует, что такой профиль не является условием полной **минимальной** семантики апамяти, исследуемой в #1558.

<a id="amemory-substrate-boundary"></a> <!-- субстрат апамяти -->
### E7/W7. Граница физического субстрата и независимость адресации

> **Статус:** итоговый производный результат семантической части исследования #1558 после принятия `MTS v0.13`. Принятая `v0.13` не изменяется.

Смысловой закон исполнения не задаёт конкретный интерфейс хранилища. Реализация обязана уметь физически поддержать требуемые наблюдаемые свойства Связей, но имена методов, таблицы индексов и локальные адреса не становятся сущностями МТС.

Удобно разделять три технических слоя.

#### 1. Субстрат носителя Связей

Текущая реализация и аудит A9 выделяют восемь возможностей:

```text
локальное техническое тождество Связи
корневой якорь
чтение полюсов
поиск канонической пары
создание или повторное получение обычной пары
создание или повторное получение START-самозамыкания
создание или повторное получение END-самозамыкания
перечисление инцидентных исходящих Связей
```

Это **возможности субстрата**, а не восемь новых примитивов МТС. Аудит A9 по-прежнему имеет:

```text
confirmedIndependentPrimitiveCount = 0
unknownPrimitiveStatusCount = 8
```

То есть их дальнейшая сводимость или физическая минимальность остаётся отдельным исследованием основания носителя. Конкретная реализация может выполнять поиск индексом, сканированием, Doublets-структурой, массивом, хеш-таблицей или другим способом.

#### 2. Субстрат публикации исполнения

Из E1 требуется одна внешняя техническая операция над исполняемой апамятью:

```text
прочитать опубликованный текущий корень
атомарно заменить S_t на уже построенный S_(t+1)
```

Сам локальный указатель, регистр, ячейка или дескриптор не является смысловым полномочием. Смысл задаётся тем, какая структурная область `Scope` опубликована как текущая.

#### 3. Субстрат представления

Точный перенос последовательностей выходов и описаний может использовать `ExactSequence`, Anum или иной согласованный носитель. Обход такого носителя — техническая механика. Порядок физических ячеек, локальные номера и способ хранения не определяют смысл результата.

#### W7 — две независимо адресованные памяти

Свидетель E7 строит одну и ту же смысловую сеть в двух независимых `Memory`, но намеренно:

```text
добавляет лишние физические Связи во вторую память
создаёт роли в другом порядке
добавляет отношения Theory в обратном порядке
получает разные локальные технические адреса
```

Для обеих памяти исполняется одна и та же реакция:

```text
current:
  K ⟼ A

admitted:
  A ⟼ [B]
  A ⟼ [C]

next:
  K ⟼ B
  K ⟼ C
```

Сравнение выполняется после рекурсивной структурной нормализации, а не по локальным адресам. Результат:

```text
normalized successor A = normalized successor B
local address vector A != local address vector B
foreign handle from A is rejected by B
```

Отсюда:

```text
local handle != semantic identity
allocation order != semantic authority
storage index != semantic authority
concrete Memory API != MTS ontology
Doublets / array / GPU layout != MTS ontology
```

#### Минимальный переносимый профиль исполнения

После E1–E7 минимальный профиль полной апамяти формулируется так:

```text
1.  Текущее смысловое состояние = члены единственного опубликованного Scope.
2.  Старые Scope и истины могут физически сохраняться; текущесть от этого не меняется.
3.  Выбранная Theory задаёт допустимые заземлённые отношения.
4.  На входе реакции фиксируется TheorySnapshot_t.
5.  Все члены реакции t используют один и тот же TheorySnapshot_t.
6.  Для каждого K ⟼ A исчерпываются все допущенные отношения с antecedent A.
7.  Ни одного допущенного отношения -> сохранить K ⟼ A.
8.  Допущенные отношения -> заменить вкладом всех K ⟼ B_j из всех образов.
9.  ZERO даёт ноль выходов и не запрещает выходы других одновременно допущенных отношений.
10. Совпавшие выходы сходятся по каноническому тождеству Связи.
11. Полный следующий Scope строится до публикации.
12. При matchedRelations > 0 выполняется один атомарный handoff текущего корня.
13. При matchedRelations = 0 handoff отсутствует и состояние является quiescent.
14. Новые допуски Theory, созданные во время реакции t, исполнимы начиная с t+1.
15. Физическое расписание, локальные адреса и размещение не могут менять нормализованный смысловой результат.
16. Рекуррентность и неограниченное исполнение допустимы; глобальное завершение не требуется.
17. Структурный END сам по себе не является командой глобальной остановки.
```

Иерархическое пошаговое построение результата деревом контекстов не входит в этот минимум по классификации E6.

#### Итоговая семантическая классификация #1558

```text
V013_SUFFICIENT = FALSE
V013_PLUS_EXECUTION_PROFILE = TRUE
SEMANTIC_EXTENSION_REQUIRED = FALSE for minimal complete A-memory
```

То есть принятой `MTS v0.13` достаточно как **основания**, но для независимых реализаций полной апамяти нужен отдельно управляемый переносимый профиль исполнения. Новый закон онтологии МТС для минимального профиля E1–E7 не потребовался.

Это ещё не означает административное завершение #1558: перед закрытием должны сойтись машинный профиль, текущая документация, словарь и документация потребителя `amemory`.

#### D1–D6. Сходимость профиля и документации

Каноническим смысловым владельцем исполнения апамяти остаётся **этот документ**. Машинная проекция находится в `profiles/amemory-execution-profile.json`; она предназначена для независимых реализаций и автоматических проверок, но не создаёт второго смыслового владельца.

Машинная проекция имеет собственную версию профиля и ссылается на принятое основание `MTS v0.13`. Это фиксирует границу:

```text
accepted MTS v0.13 foundation
+
separately governed A-memory execution profile
```

Принятые артефакты v0.13 при этом не изменяются. Результаты E1–E2 остаются производными уточнениями принятого основания; граница снимка `Theory`, наблюдаемые условия покоя и переносимая независимость от физического расписания принадлежат профилю исполнения.

Словарь обязан иметь один предпочтительный термин и ссылку **«Подробнее»** для текущести, реакции, допуска `Theory`, публикации, снимка `Theory`, покоя, рекуррентности, субстрата, самохостинга и классификации иерархического результата.

##### Матрица обязательных примеров D5

```text
A. минимальное преобразование
   K ⟼ A ; A ⟼ [B]  ->  K ⟼ B
   старая K ⟼ A может физически сохраниться

B. отсутствие отношения и ZERO
   NO_ADMITTED_RELATION -> сохранить K ⟼ A
   ZERO                 -> не включать K ⟼ A в следующий Scope

C. MANY
   A ⟼ [B,C] -> K ⟼ B, K ⟼ C
   совпавшие выходы сходятся канонически

D. независимые реакции
   разные физические порядки W4
   -> одинаковый нормализованный successor

E. взаимодействующие реакции
   новое допущение Theory во время реакции t
   -> исполнимо с t+1 по границе TheorySnapshot_t

F. рекуррентность
   K ⟼ A -> K ⟼ B -> K ⟼ A -> ...
   активность сохраняется, покой не достигается

G. граница субстрата
   две независимо адресованные памяти W7
   -> одинаковый нормализованный successor
```

Для D6 действует уже установленная классификация:

```text
HIERARCHICAL_LINK_AS_RESULT = supported by minimal reaction

DYNAMIC_HIERARCHICAL_RESULT_CONSTRUCTION
NESTED_CONTEXT_RESULT_LIFECYCLE
PERSISTENT_RESULT_VERSIONS
  = INDEPENDENT_LATER_FEATURE

DEFERRED != REJECTED
```

Таким образом, D1–D6 не вводят новую семантику МТС: они сводят уже полученный результат E1–E7 в одну человекочитаемую и одну машинно-проверяемую поверхность. D7 начинается на границе потребителя: реализация `amemory` должна объявить, какой профиль она реализует, и доказать эквивалентность своих вычислительных backend без превращения их технических деталей в семантику.

#### D8–D9. Проверки документации и приёмка внешнего читателя

Для текущей поверхности документации обязательны следующие исполняемые проверки:

```text
npm --prefix ts run docs:sync
npm --prefix ts run docs:check
npm --prefix ts run check
repo-guard
docs-current-surface
glossary-link
A-memory execution-profile convergence
external-reader acceptance
semantic-owner uniqueness
```

Одна успешная локальная проверка не заменяет проверку точной головы PR: изменение документации считается прошедшим D8 только после зелёных CI и `repo-guard` для того же commit.

Ниже приведена самодостаточная приёмка D9. Для ответов не требуется история исследовательских issue.

**`D9-Q01` — Что является смысловым состоянием апамяти?** Члены единственного опубликованного текущего `Scope`. Физически присутствующие Связи вне него не становятся текущим состоянием только из-за своего существования.

**`D9-Q02` — Что делает состояние текущим?** Единственный опубликованный текущий корень апамяти. Конкретная переменная, регистр или запись БД может реализовать это полномочие, но сама по себе не является семантикой МТС.

**`D9-Q03` — Нужно ли физически удалять старую истину?** Нет. После публикации следующего `Scope` старые `Scope` и `K ⟼ A` могут оставаться физически доступными; они просто больше не входят в текущее смысловое состояние.

**`D9-Q04` — Что такое один элементарный переход?** Для каждого текущего `K ⟼ A` исполнитель исчерпывает все отношения с antecedent `A`, допущенные выбранным снимком `Theory`, строит полный следующий `Scope` и затем публикует его одной атомарной сменой текущего корня.

**`D9-Q05` — Чем `NOT_FOUND` отличается от `ZERO`?** `NOT_FOUND` относится к конкретному запросу чтения и не доказывает отсутствия всех допущенных отношений. `ZERO` — реально допущенное отношение с пустым образом; оно даёт нулевой вклад в следующий `Scope`.

**`D9-Q06` — Что делают `ONE` и `MANY`?** `ONE` заменяет `K ⟼ A` одним каноническим `K ⟼ B`; `MANY` добавляет все канонические выходы всех одновременно допущенных образов, а совпавшие выходы сходятся по тождеству Связи.

**`D9-Q07` — Что означает конкурентное исполнение семантически?** Все участники одного логического шага читают одно исходное состояние и один снимок `Theory`; кандидаты могут вычисляться физически параллельно, но смысловым результатом является полный нормализованный successor `Scope`, опубликованный одной границей.

**`D9-Q08` — Какие различия расписания наблюдаемы?** В переносимом профиле перестановка потоков, рабочих групп, линий ускорителя, порядка обхода и локальных адресов не должна менять нормализованный смысловой результат. Такие различия остаются технически наблюдаемыми, но не имеют семантического полномочия.

**`D9-Q09` — Когда виден новый допуск `Theory`?** Допуск, материализованный во время реакции `t`, может физически существовать сразу, но не входит в `TheorySnapshot_t`; исполнимым он становится начиная с реакции `t+1`.

**`D9-Q10` — Что такое покой?** Покой устанавливается только после полного логического шага, в котором `matchedRelations = 0` и не выполняется handoff. Простое бездействие планировщика покоем не является.

**`D9-Q11` — Чем рекуррентность отличается от покоя?** При рекуррентности то же нормализованное смысловое состояние возвращается после одного или нескольких активных переходов. Поэтому рекуррентная сеть может оставаться активной бесконечно и не быть в покое.

**`D9-Q12` — Требуется ли глобальное завершение?** Нет. Минимальный профиль допускает рекуррентность и неограниченное исполнение; структурный аспект `END` сам по себе не является командой глобальной остановки.

**`D9-Q13` — Входят ли иерархический результат и вложенный контекст в минимальный закон?** Вложенная Link-топология может быть обычным результатом реакции, но динамическое построение иерархического результата, жизненный цикл дочерних контекстов и постоянные версии результата классифицированы как независимая более поздняя возможность.

**`D9-Q14` — Что остаётся физическим субстратом?** Техническое хранение и адресация Связей, чтение полюсов и инцидентности, каноническая материализация, механизм публикации текущего корня и конкретное представление последовательностей. Локальные `handles`, индексы, `Doublets`, массивы и размещение на ускорителе не являются онтологией МТС.

**`D9-Q15` — Что именно является самохостингом?** Смысловое полномочие программы уже может находиться в Link-структурах `Theory`, отношений, контекстных истин и выходов. Внешними остаются носитель, публикация текущего `Scope`, общий цикл исполнения, ввод-вывод и часть механики заземления; поэтому доказан ограниченный самохостинг семантики программы, а не полностью самохостящаяся система.

**`D9-Q16` — Где проходит граница между МТС, профилем исполнения и реализацией `amemory`?** Принятая MTS v0.13 задаёт основание; этот репозиторий отдельно управляет переносимым профилем исполнения апамяти; конкретные `CPU`, браузерные и ускорительные `backend`, `layout`, `scheduler` и механизм хранения принадлежат реализации `amemory` и обязаны доказывать эквивалентность профилю, не превращая свои технические решения в семантику.

#### D10. Итоговая сходимость

Переносимый профиль исполнения, текущая документация и документация потребителя сведены в одну непротиворечивую границу. Принятое основание MTS v0.13 при этом не изменялось.

Точный downstream-свидетель потребителя:

```text
amemory D7 issue 24 = COMPLETED
amemory PR 25 = MERGED
amemory main = 90a6a3a26ad14b8d00fca0ec6e66fa1fdd9a5203

accepted MTS v0.13 foundation pin =
  440caf09558d4ff5cfda11805cb3ef97b48d1ad5

execution profile pin =
  af4e3dadbb9857fba7239a58f79ed2da59bc5c42

execution profile blob =
  e2c614e1556f31f6230cb69d686d1f22ab2c97e8
```

Потребитель явно различает физическую реализацию и смысловой профиль. Для текущих Rust/WASM и WebGPU прототипов зафиксировано:

```text
implementedProfileId = minimal-portable-amemory-execution
implementedProfileVersion = 0.1.0
supportLevel = partial
fullProfileConformance = false
current reaction Scope = NOT_IMPLEMENTED_FOR_EXECUTION

P10 / P15 = supporting evidence only
P01-P09 / P11-P14 / P16-P17 = not-yet-executed
```

Поэтому завершение документационной и смысловой сходимости **не означает**, что потребитель уже реализовал все семнадцать законов реакции. Реализация полной реакции CPU/WASM ↔ WebGPU остаётся отдельной инженерной работой и не является условием завершённости самого профиля.

Финальная классификация:

```text
V013_SUFFICIENT = FALSE
V013_PLUS_EXECUTION_PROFILE = TRUE
SEMANTIC_EXTENSION_REQUIRED = FALSE
```

Финальный аудит текущей поверхности:

```text
A_MEMORY_DOCUMENTATION = COMPLETE
GLOSSARY = CONVERGED
AMEMORY_IMPLEMENTATION_DOCS = ALIGNED
BROKEN_CURRENT_LINKS = 0
COMPETING_A_MEMORY_SEMANTIC_OWNERS = 0
UNSCOPED_SELF_HOSTING_CLAIMS = 0
HOST_SCHEDULING_PRESENTED_AS_SEMANTICS = 0
D1_D10 = COMPLETE

FULL_REACTION_PROFILE_CONFORMANCE = FALSE
```

Эти результаты означают:

- один текущий человекочитаемый смысловой владелец апамяти;
- одну машинную проекцию переносимого профиля, не являющуюся вторым смысловым владельцем;
- согласованный словарь и рабочие ссылки текущей документации;
- явную границу ограниченного самохостинга без заявления о полностью самохостящейся системе;
- физическое расписание, локальная адресация и устройство ускорителя остаются техническими деталями;
- потребитель закрепляет точную версию профиля и не выдаёт частичные свидетельства хранения за полное исполнение реакции.

## 18. Производный результат: инверсия исполнения

**Статус: производный результат о принятой v0.13, а не принятая рабочая семантика исполнения.**

Для точной двойственной конвенции доказано:

```text
dualReact(J(state))
=
J(react(state))
```

Чтобы равенство выполнялось, одновременно инвертируются:

Ветви `MANY`, `ZERO` и отсутствие отношения сохраняют свою структурную двойственность.

Но текущий исполнитель остаётся в принятой ориентации. Двойственный исполнитель является доказательным свидетелем `THEORY_DUALIZATION`, а не второй production-конвенцией.

## 19. Инженерная поверхность

Текущая эталонная реализация разделяет читающую и изменяющую способности:

```text
ReadMemory:
  root
  linkCount
  poles
  find
  outgoing
  incoming

WriteMemory:
  ensureRoot
  ensureStartSelfClosed
  ensureEndSelfClosed
  ensure
```

Эти имена являются реализационным свидетельством, а не смысловым авторитетом.

Индексы `outgoing/incoming`, порядок выдачи handles и слот памяти могут ускорять исполнение, но не участвуют в тождестве Связи.

## Итог

Текущая динамика апамяти v0.13 имеет три чётко разделённых слоя:


Заземлённая реакция уже выражает программу через саму сеть Связей, но механизм текущести и физическое выполнение реакции остаются границей апамяти.
