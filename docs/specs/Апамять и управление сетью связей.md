# Апамять и управление сетью связей

Апамять — слой МТС, который хранит сеть связей, позволяет искать в ней существующие отношения, явно создавать новые и воспроизводить уже произошедшие действия.

Текущая реализация остаётся кандидатом следующего основания МТС. Этот документ описывает её понятийные границы, а не историю этапов разработки.

Связанные документы:

- [Основания МТС](../theory/Основания%20МТС.md)
- [Формальная нотация МТС](Формальная%20нотация%20МТС.md)
- [Ачисла и сериализация](Ачисла%20и%20сериализация.md)

## 1. Апамять хранит связи, а не объекты поверх связей

Базовая структура остаётся бинарной:

```text
Link(start, end)
```

Контекст, словарь, теория, исходная запись, акт интерпретации и доказательство не обязаны быть внешними объектами особого рода. Если различие существенно, оно может быть представлено дополнительными связями той же сети.

Поэтому апамять следует понимать как **контроллер точных вхождений связей**, а не как объектную базу данных с обязательной системой классов.

## 2. Точное вхождение важнее пары полюсов

Могут одновременно существовать:

```text
P1 = A ⟼ B
P2 = A ⟼ B
P1 ≠ P2
```

Одинаковая пара полюсов не делает два вхождения одной связью.

Это нужно, потому что одинаковая структурная пара может соответствовать разным:

- событиям;
- объявлениям;
- источникам;
- актам интерпретации;
- результатам материализации;
- свидетельствам происхождения.

Индекс по паре `(A,B)` полезен для поиска, но не является правилом тождества.

## 3. Наблюдение и изменение разделены

Критический инвариант:

```text
читать / искать / разрешать / проверять
                    ≠
создавать / удалять / изменять
```

Если связь `A ⟼ B` отсутствует:

```text
find(A,B) -> ()
```

не должно менять память.

Только явное действие:

```text
X = materialize(A,B)
```

создаёт новое вхождение:

```text
X = A ⟼ B
```

Повторная материализация создаёт ещё одно вхождение:

```text
Y = materialize(A,B)
X ≠ Y
```

После этого поиск вправе вернуть оба результата.

Это особенно важно для проверяющей части системы: проверка доказательства не должна создавать недостающие факты ради собственного успеха.

## 4. Циклы и совместное использование являются обычной структурой

Апамять должна хранить самозамыкание:

```text
R = R ⟼ R
```

взаимные циклы:

```text
A = B ⟼ X
B = A ⟼ Y
```

и совместное использование одного вхождения:

```text
P = A ⟼ X
Q = B ⟼ X
```

В последнем случае `X` остаётся одним точным вхождением, а не двумя копиями одинаковой формы.

Поэтому произвольная асеть не обязана быть деревом, а сравнение по форме не заменяет тождество связей.

## 5. Контекст хранится в самой сети

Текущий кандидат контекста:

```text
P = parent ⟼ current
K = K ⟼ P
```

`K` — точное вхождение состояния контекста.

После перехода создаётся новое состояние:

```text
P1 = Parent ⟼ Current1
K1 = K1 ⟼ P1
```

Старое состояние `K0` не переписывается.

Это позволяет позднее предъявить точные `K_before` и `K_after` и проверить произошедший переход без скрытого глобального стека среды исполнения.

## 6. Словарь также является сохраняемой сетью

Состояние словаря можно представить так:

```text
D = D ⟼ (parentScope ⟼ localHistory)
```

Определение связывает содержимое исходной записи с формой:

```text
Entry = sourceContent ⟼ Form
```

Конкретное объявление сохраняет точное состояние до изменения:

```text
Occurrence = D_before ⟼ Entry
```

История расширяется новым звеном:

```text
H_after = H_before ⟼ Occurrence
D_after = D_after ⟼ (sameParentScope ⟼ H_after)
```

`D_before` остаётся доступным. Таким образом область имён становится частью проверяемой сети, а не скрытым изменяемым словарём языка реализации.

## 7. Знак `:` обозначает явное изменение словаря

После разрешения исходной записи действие определения может создать:

```text
Entry
Occurrence
H_after
D_after
A
```

где `A` — конкретный акт.

Доверенная проверка уже выполненного определения только читает память и подтверждает, что:

- `Entry` связывает нужное содержимое с нужной формой;
- `Occurrence` относится именно к `D_before`;
- история расширена ровно предъявленным объявлением;
- родительская область не изменилась;
- новое объявление видно из `D_after`;
- `D_before` осталось неизменным;
- акт указывает на те же точные свидетельства.

Проверка не должна повторно выполнять определение.

## 8. Исходная запись и результирующая сеть — разные вещи

Пусть исходное описание содержит:

```text
∞ A B
```

Сам факт загрузки этого описания ещё не означает существование:

```text
A ⟼ B
```

в целевой сети.

Правильное разделение:

```text
исходная запись
→ разбор и разрешение
→ выбранное структурное описание
→ явная материализация
→ результирующая сеть
```

При операции чтения последний переход отсутствует:

```text
исходная запись
→ разбор и разрешение
→ поиск / сравнение / проверка
```

Это позволяет отличить ранее существовавший факт от результата только что выполненного действия.

## 9. Материализация последовательности ачисла

Для выбранной последовательности:

```text
∞ A B C
```

материализация выполняется как левая свёртка накопленного точного префикса:

```text
AB  = A ⟼ B
ABC = AB ⟼ C
```

поэтому:

```text
des(∞ A B C)
= (A ⟼ B) ⟼ C
= A ⟼ B ⟼ C
```

`∞` служит начальным значением контекста последовательности, но не становится дополнительным операндом свёртки. Первый разрешённый элемент становится текущим значением; каждый следующий элемент связывается с уже построенным точным префиксом.

Это соответствует связевой форме самого последовательного носителя: следующий элемент присоединяется не к предыдущему элементу отдельно, а ко всей накопленной истории слева.

Вложенная группа сначала строит внутреннее значение:

```text
[A]   -> A
[A B] -> X = A ⟼ B
```

поэтому:

```text
∞ [A B] C
```

даёт:

```text
X = A ⟼ B
Y = X ⟼ C
```

Каждый явно материализованный шаг левой свёртки создаёт новое точное вхождение, даже если связь с такими полюсами уже существует.

Подробнее о структуре ачисел: [Ачисла и сериализация](Ачисла%20и%20сериализация.md).

## 10. Ассоциативный поиск

Минимальный набор запросов может выглядеть так:

```text
find(start=A)
find(end=B)
find(start=A,end=B)
outgoing(A)
incoming(B)
```

Физический индекс может использовать хеш-таблицу, дерево, базу данных или специализированную структуру памяти.

Но индекс только ускоряет выбор кандидатов. Он не решает, какая найденная связь является нужным смыслом, и не превращает одинаковые пары в одну сущность.

## 11. Конкретный акт сохраняет происхождение результата

Акт интерпретации может связывать точные свидетельства:

```text
source
form
D
G
T
K_before
binding
result
K_after
```

Благодаря этому память хранит не только результат, но и ответ на вопросы:

```text
из какой исходной записи он получен?
в каком словаре?
в какой теории?
в каком контексте?
какое точное вхождение было результатом?
```

Поиск подходящего действия может быть эвристическим, но проверка выбранного действия должна быть детерминированной.

## 12. Последовательность актов

История выбранных действий может быть связана в последовательность:

```text
Run0 = R
Run1 = Run0 ⟼ A0
Run2 = Run1 ⟼ A1
```

Соседние действия должны предъявлять один и тот же точный переходный контекст:

```text
A_i.after is A_(i+1).before
```

Такая последовательность хранит порядок и происхождение. Она сама по себе не вводит логическую транзитивность и не создаёт краткую связь от первого состояния к последнему.

## 13. Поиск доказательства и проверка доказательства разделены

Архитектура допускает сложный недоверенный поиск:

```text
индексы
эвристики
параллельный перебор
ранжирование кандидатов
машинное обучение
```

но доверенная часть получает выбранные точные свидетельства и только воспроизводит их.

Схема:

```text
недоверенный поиск
       ↓
выбранное доказательство
       ↓
детерминированная проверка
       ↓
принять / отвергнуть
```

Это позволяет усложнять поиск, не увеличивая доверенную семантическую основу.

## 14. Правило вывода явно допускается теорией

Например правило разложения равных полных связей должно быть предъявлено как отдельная связь:

```text
T ⟼ Rule
```

Проверка применения правила может подтвердить связи между соответствующими полюсами, но не обязана изменять локальное равенство `K` и не получает скрытого права записи в память.

Любое последующее изменение должно быть отдельным актом.

## 15. Почему оперативного тождества недостаточно для долговременной памяти

Внутри одного запуска реализация может использовать `OccurrenceRef`.

После закрытия и повторного открытия процесса прежний объект среды исполнения уже не существует. Поэтому долговременная память различает как минимум четыре уровня:

```text
runtime OccurrenceRef
persistent dataset-local logical id
snapshot-local slot
backend physical address
```

Их нельзя отождествлять.

## 16. Логическое тождество внутри набора данных

Эталонная запись долговременного идентификатора:

```text
PersistentOccurrenceId(lineage, local)
```

`lineage` обозначает происхождение конкретного набора данных, а `local` — точное вхождение внутри него.

После закрытия и повторного открытия того же набора:

```text
(L1,42)
```

остаётся тем же долговременным вхождением, хотя новый `OccurrenceRef` может быть другим объектом программы.

## 17. Одинаковая структура в другом наборе данных не является тем же вхождением

Если ту же топологию импортировать в независимый набор с другим происхождением:

```text
(L1,42) ≠ (L2,42)
```

даже при полном совпадении полюсов и окружающей структуры.

Это продолжает общий принцип МТС:

```text
одинаковая форма ≠ одно и то же точное вхождение
```

## 18. Физический адрес не является тождеством МТС

Хранилище может перемещать данные при:

- уплотнении;
- восстановлении;
- копировании при записи;
- переносе страниц;
- изменении внутреннего формата.

Поэтому требуется граница:

```text
долговременный логический идентификатор
                ↓
        отображение хранилища
                ↓
          физический адрес
```

Физическое расположение может меняться без изменения тождества связи.

## 19. Повторяющиеся пары должны переживать повторное открытие

Пусть долговременная память содержит:

```text
P1 = A ⟼ B
```

Новое явное действие создаёт:

```text
P2 = A ⟼ B
P1 ≠ P2
```

После повторного открытия:

```text
find(A,B) -> (P1,P2)
```

Оба точных вхождения должны сохраниться.

Это принципиально отличает текущую модель от старой схемы, где пара полюсов автоматически интернировалась в одну связь.

## 20. Атомарное создание группы связей

Для циклов необходимо заранее ссылаться на связи, которые создаются в той же операции. Для этого реализация может использовать временные ссылки группы:

```text
BatchRef(0)
BatchRef(1)
```

Самозамыкание:

```text
BatchRef(0) ⟼ BatchRef(0)
```

Взаимный цикл:

```text
A = BatchRef(1) ⟼ X
B = BatchRef(0) ⟼ Y
```

Сначала выделяются логические идентификаторы всей группы, затем проверяются все полюса, после чего новое состояние публикуется целиком.

Наблюдаемая гарантия:

```text
успех  -> видна вся группа
ошибка -> видно исходное состояние
```

Половинчатая сеть не должна становиться сохранённым состоянием.

## 21. Формат эталонного хранилища не является частью теории

`JsonExactLinkStore` используется только как небольшое исполнимое доказательство требований к долговременной памяти.

Нормативны наблюдаемые свойства:

- множественность одинаковых пар переживает повторное открытие;
- циклы и совместное использование сохраняются;
- корень сохраняется по логическому тождеству;
- поиск не пишет;
- групповое изменение атомарно;
- свидетельство материализации можно проверить после повторного открытия.

Сам формат JSON нормативным не является.

## 22. Производственное хранилище может быть другим

В качестве будущего производственного слоя естественно рассматривать `PersistMemoryManager` или другое долговременное хранилище.

Направление зависимости должно оставаться таким:

```text
требования МТС к апамяти
          ↑
   адаптер хранилища
```

а не наоборот.

Внутренний адрес блока, строки базы данных или страницы памяти не должен становиться семантическим тождеством связи.

## 23. Воспроизведение материализации после повторного открытия

Долговременный слой не должен реализовывать второй раз семантику ачисел.

Правильная композиция:

```text
долговременное хранилище
→ восстановить точную сеть времени исполнения
→ применить существующую семантику последовательности
→ нормализовать новые полюса в долговременные идентификаторы
→ атомарно сохранить группу
```

Для проверки выполняется обратное сопоставление долговременных идентификаторов с новым набором оперативных ссылок и вызывается та же проверка последовательности.

Так меняется способ хранения, но семантика материализации остаётся одна.

## 24. Минимальный интерфейс контроллера

Понятийно достаточно небольшого набора операций:

```text
# чтение
poles(id)
find(start?,end?)
outgoing(start)
incoming(end)
snapshot()

# явное изменение
materialize(start,end) -> NEW exact id
materialize_batch(edges) -> NEW exact ids atomically

# проверка
replay(evidence) -> accept/reject
```

Критические свойства:

```text
множественность сохраняется
циклы сохраняются
совместное использование сохраняется
чтение не изменяет память
проверка не изменяет память
материализация всегда явна
долговременное тождество ограничено происхождением набора данных
физический адрес не является смыслом
```

## 25. Что ещё не определено окончательно

Текущий кандидат не устанавливает автоматически:

- семантику удаления;
- перенос тождества между независимыми наборами данных;
- конкретный производственный механизм восстановления после аварии;
- конкретный адаптер `PersistMemoryManager`;
- принятие следующей версии МТС.

Эти вопросы могут решаться отдельно, не меняя уже определённые границы чтения, точного вхождения и долговременного тождества.

## Итог

Апамять переносит постулат:

```text
всё есть связь
```

в вычислительную архитектуру, где одна сеть может хранить данные, состояния, словари, действия и свидетельства доказательств.

Главный набор ограничений остаётся компактным:

```text
одинаковая пара ≠ одно вхождение
одинаковая форма ≠ тождество
поиск ≠ создание
проверка ≠ изменение
логическое тождество ≠ физический адрес
```

Именно эти границы позволяют строить ассоциативную память, не превращая удобства конкретного хранилища в скрытую семантику МТС.
