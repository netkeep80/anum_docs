# Апамять и управление сетью связей

Апамять — слой МТС, который хранит конкретно материализованную асеть, позволяет искать в ней связи, явно материализовать недостающие записи и воспроизводить засвидетельствованные действия.

Связанные документы:

- [Система аксиом МТС](../theory/Система%20аксиом%20МТС.md)
- [Основания МТС](../theory/Основания%20МТС.md)
- [Формальная нотация МТС](Формальная%20нотация%20МТС.md)
- [Ачисла и сериализация](Ачисла%20и%20сериализация.md)

Этот документ описывает текущую принятую границу апамяти **MTS v0.9**. Единственный live semantic runtime — TypeScript `@mts/core`; previous immutable machine evidence — MTS v0.8.

## 1. Апамять хранит связи

Базовая структура МТС бинарна:

```text
Link(start, end)
```

Контекст, словарь, теория, исходная запись, акт интерпретации, история и доказательство могут быть представлены связями той же сети. Для их различения не требуется вводить отдельную онтологическую категорию объектов поверх связей.

## 2. Тождество связи определяется полюсами

Фундаментальный инвариант:

```text
(A ⟼ B) = (C ⟼ D)
⇔
A = C ∧ B = D
```

Следовательно:

```text
P1 = A ⟼ B
P2 = A ⟼ B
=> P1 = P2
```

В МТС не существует двух разных смысловых связей с одной и той же упорядоченной парой `(start,end)` уже структурно различённых полюсов.

Индекс, адрес записи, номер операции, позиция в последовательности или техническая ссылка времени исполнения могут различаться, но не создают второе смысловое тождество связи.

F2/F3 усиливают это no-instance result через grounded recursive normal forms: technical identity не используется как premise.

## 3. Апамять не равна универсуму МТС

Если конкретная память не содержит физической записи формы:

```text
A ⟼ B
```

из этого не следует, что такая связь «не существует» в семантическом смысле.

Поэтому:

```text
не найдено != не существует
```

Апамять — конкретно материализованная часть возможной связевой структуры, а не обязательное перечисление всех возможных связей.

## 4. Поиск и изменение строго разделены

Критический инженерный инвариант:

```text
читать / искать / разрешать / проверять / replay
                    !=
создавать / удалять / изменять
```

Текущий TypeScript `ReadMemory` предоставляет только чтение:

```text
root
linkCount
poles(link)
find(start,end)
outgoing(start)
incoming(end)
```

Эти операции не должны материализовать отсутствующие связи.

Явная операция materialization принадлежит `WriteMemory`:

```text
ensure(start,end)
```

и ведёт себя канонически:

```text
если A ⟼ B уже присутствует -> вернуть эту же semantic Link
иначе -> материализовать A ⟼ B и вернуть её
```

## 5. Повторная материализация не создаёт второй экземпляр

Если в памяти уже присутствует:

```text
X = A ⟼ B
```

повторная явная операция:

```text
ensure(A,B)
```

возвращает `X`.

Неверная для МТС модель:

```text
X = materialize(A,B)
Y = materialize(A,B)
X != Y
```

не допускается в accepted MTS v0.9.

Допустимо различать два **акта обращения к памяти**, но их общий результат остаётся одной semantic Link `A ⟼ B`.

## 6. История и акт не являются скрытым тождеством связи

Разные акты построения, чтения или наблюдения одной связи могут быть различены, если это существенно.

Но различие должно выражаться самой связевой структурой истории, например через разные позиции в последовательности актов, разные состояния контекста, источники или иные отношения.

Принцип:

```text
разные акты получения одной связи
!=
разные экземпляры самой связи
```

Если две предполагаемые записи акта имеют полностью одинаковую grounded form и ничем связево не различены, technical handle не может превратить их в две semantic Links.

## 7. Циклы и совместное использование допустимы

Апамять должна поддерживать самозамыкание:

```text
R = R ⟼ R
```

петли:

```text
Loop(a) = a ⟼ a
```

взаимные циклы и совместное использование одной связи несколькими структурами, если различимость укоренена относительно уже различённого основания.

Для данного `a` связь `a ⟼ a` единственна.

Если:

```text
a = a ⟼ a
```

то:

```text
Loop(a) = a = R
```

В частности:

```text
Loop(R) = R
```

## 8. Корень каноничен

Для акорня:

```text
R = R ⟼ R
```

поэтому отдельная semantic Link `X != R` с полюсами `(R,R)` невозможна.

Физическая реализация может использовать внутренний slot/handle для доступа, но это не создаёт второй root.

## 9. Позиционная множественность хранится структурой

Последовательность может несколько раз ссылаться на одну и ту же связь.

Например три вхождения `L`:

```text
[L, L, L]
```

не требуют трёх semantic объектов `L`.

Различие первого, второго и третьего употребления задаётся structural occurrence/position evidence.

Это особенно важно для ачисел: повтор абита означает повтор ссылки, а не materialization duplicate pair.

## 10. Fold result и exact sequence — разные роли

Для вычисления результата последовательности значений может использоваться левая свёртка:

```text
AB  = ensure(A,B)
ABC = ensure(AB,C)
```

Если требуемая пара уже присутствует, соответствующий шаг переиспользует существующую связь.

Но MTS v0.9 **не** использует такую свёртку как универсальное identity-представление последовательности, если значением позиции может быть `R`.

Потому что наивно:

```text
[]  -> R
[R] -> R
```

и позиции схлопываются.

Для identity-sensitive последовательностей используется root-safe `ExactSequence`:

```text
Seq([]) = R
Cell(prev,value) = start-self-closed(prev ⟼ value)
```

Поэтому:

```text
Seq([]) != Seq([R])
```

без создания второго `R`.

Подробнее: [Ачисла и сериализация](Ачисла%20и%20сериализация.md).

## 11. Импорт физического артефакта

Внешнее хранилище может содержать технические идентификаторы:

```text
row42 -> (A,B)
row77 -> (A,B)
```

Это не означает наличие двух semantic Links МТС.

Импорт обязан выбрать явную политику:

```text
reject duplicate physical representation
```

или:

```text
canonicalize row42,row77 -> one Link(A,B)
```

Молчаливо превращать разные идентификаторы хранения в разные смысловые связи запрещено.

## 12. Технический handle не является смыслом

Текущий TypeScript owner использует `LinkHandle` для локального доступа к `Memory`.

Нужно различать:

```text
semantic Link
LinkHandle / local slot
persistent record id
snapshot coordinate
physical address
```

`LinkHandle.slot` и owner-symbol являются implementation coordinates. Они не являются третьим полюсом и не участвуют в semantic identity.

Чужой/поддельный handle отклоняется как invalid access coordinate, но различие handles само по себе не доказывает semantic distinction.

## 13. Долговременное хранение

После повторного открытия памяти должна восстанавливаться та же каноническая topology modulo runtime-handle renaming.

Если сохраняемый артефакт содержит несколько технических записей одной semantic form, слой восстановления должен отклонить или канонизировать их до передачи в semantic model.

Нормативно важны свойства:

- полюса сохраняются;
- циклы сохраняются;
- sharing сохраняется;
- duplicate pair не превращается в semantic multiplicity;
- read/replay не пишет;
- physical address не становится semantic identity.

Current owners находятся в TypeScript persistence слоях (`persistence-topology.ts`, `persistent-store.ts`, `persistent-sequence.ts`), но конкретный storage format не является онтологией МТС.

## 14. Атомарное построение сложной группы

Для сложных persistent/import операций реализация может использовать временные строительные coordinates, позволяющие описать будущие взаимные ссылки до публикации результата.

Такие coordinates существуют только на инженерной границе построения и хранения.

После разрешения группы каждая semantic Link определяется финальной grounded structure. Если две разрешённые записи получают одну semantic форму, они должны канонизироваться или операция должна быть отклонена.

Публикация изменяющей операции должна иметь явную atomic effect boundary:

```text
успех  -> виден согласованный результат
ошибка -> видимо исходное состояние
```

## 15. Контекст хранится связями

Context не обязан быть скрытым объектом языка реализации.

Accepted MTS v0.9 использует:

```text
P = parent ⟼ current
K = K ⟼ P
I ⟼ K
```

Лексическая вложенность принадлежит `K.parent`, а временной порядок — Run/Act.

Повтор той же полной формы `K` обозначает ту же semantic Link. Если требуется различить два момента использования контекста, различие должно находиться в occurrence/history structure.

## 16. Словарь и определения

Словарь и определения также могут быть представлены сетью связей.

Пример схемы:

```text
Entry      = sourceContent ⟼ Form
Definition = D_before ⟼ Entry
H_after    = H_before ⟼ Definition
```

Если требуемая связь уже существует, её повторное получение не создаёт копию.

Если необходимо различать два объявления одного content/form, различие должно быть выражено provenance/history, а не вторым semantic `Entry` той же пары.

## 17. Исходная запись и результирующая сеть различны

Факт наличия описания:

```text
A B
```

не означает автоматически, что physical record:

```text
A ⟼ B
```

уже присутствует в данной апамяти.

Правильное разделение:

```text
source
→ decode / resolve
→ structural description
→ find / verify
```

и только при явном изменяющем действии:

```text
→ ensure/materialize
→ новая physical запись, если её ещё не было
```

## 18. Проверка доказательства не материализует факты

Поиск доказательства может быть сложным и недоверенным:

```text
индексы
эвристики
параллельный перебор
ранжирование
```

Доверенная проверка получает предъявленное evidence и только проверяет его.

Если нужная запись не найдена в памяти, checker не должен создавать её ради успешной проверки.

```text
proof search != proof checking
proof checking != materialization
```

## 19. Последовательность актов

Временной порядок действий хранится explicit Run/history structure.

Если один и тот же semantic Act или result упоминается повторно, последовательность может ссылаться на ту же semantic Link несколько раз.

Порядок хранится структурой positions/occurrences, а не экземплярностью элементов.

## 20. Текущий минимальный TypeScript interface

Понятийно и программно разделены capabilities:

```text
ReadMemory
  root
  linkCount
  poles(link)
  find(start,end)
  outgoing(start)
  incoming(end)

WriteMemory extends ReadMemory
  ensureRoot()
  ensureStartSelfClosed(end)
  ensureEndSelfClosed(start)
  ensure(start,end)
```

Специализированные read-only capabilities существуют отдельно:

```text
AppendOnlyReadMemory.issuanceIndex(link)
EnumerableReadMemory.allLinks()
```

Их технические coordinates не входят в semantic identity.

Критические свойства:

```text
semantic identity by grounded ordered poles
find не пишет
replay не пишет
ensure не создаёт duplicate semantic pair
root canonical
cycles/sharing сохраняются
position != semantic identity
LinkHandle != semantic identity
physical address != semantic identity
```

## 21. Current MTS v0.9 boundary

Текущий owner `ts/src/memory.ts` содержит один `Memory` kernel с indexed `find/outgoing/incoming` и отдельными `ReadMemory`/`WriteMemory` capabilities.

Accepted contract v0.9 подтверждает:

```text
single live semantic runtime = TypeScript
runtime handle is not semantic identity
storage id is not semantic identity
source position is not semantic identity
occurrence is not semantic identity
second fully-self-closed root is forbidden
read may not materialize
not-found does not imply non-existence
```

Python runtime и compatibility runtime отсутствуют.

Произвольный physical-ID graph не является автоматически semantic асетью МТС: он должен пройти rooted structural validation/canonicalization либо быть отклонён.

## Итог

Апамять должна сохранять одновременно два класса принципов:

```text
(A⟼B) однозначна по grounded ordered poles
повтор semantic form не создаёт второй Link
```

и:

```text
find/read/replay != ensure/materialize/write
verify != write
не найдено != не существует
```

Именно их совместное соблюдение отделяет semantic identity связи от инженерного факта наличия её записи в конкретной памяти.
