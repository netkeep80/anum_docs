# Пучки связей
<!-- версия документа МТС; mts-doc-version: v0.13 -->
> **Версия МТС: v0.13**

Пучок связей — производная структура МТС v0.13 над уже различёнными Связями. Он не вводит новый вид первичной сущности и не изменяет фундаментальное тождество Связи.

Текущая реализация использует две явные роли:

```text
ConstraintBundle
ValueBundle
```

Эти имена обозначают роли производного слоя, а не новые онтологические типы.

Связанные владельцы:

- [Система аксиом МТС](../theory/Система%20аксиом%20МТС.md) — тождество Связи;
- [Ачисла и сериализация](Ачисла%20и%20сериализация.md) — укоренённый структурный носитель;
- [Формальная нотация МТС](Формальная%20нотация%20МТС.md) — контекст и роли;
- [Апамять и управление сетью связей](Апамять%20и%20управление%20сетью%20связей.md) — чтение, поиск и граница материализации.

## 1. Фигурные скобки — только метанотация

Для краткости в этом документе используются записи:

```text
{a,b}
{}
a{b,c}
{a,b}c
```

Они являются метанотацией производной пучковой поверхности.

Фигурные скобки не становятся из этого внутренними знаками `F1` и не получают собственного фундаментального смысла.

```text
метанотация {...}
!=
внутренний FORMAL-оператор
```

## 2. Роль пучка определяется структурным контекстом

Пучковая форма может играть роль:

```text
ConstraintBundle
ValueBundle
```

Роль определяется структурным свидетельством и ожидаемой позицией, а не адресом синтаксического объекта и не текущим содержимым апамяти.

Непустой пучок может нести собственное свидетельство роли через содержимое. Смешанное свидетельство условия и значения отклоняется.

Пустая форма:

```text
{}
```

не имеет собственной внутренней подсказки роли.

Без ожидаемого контекста она неоднозначна:

```text
{}
-> ambiguous-empty-bundle-role
```

Явный окружающий контекст может выбрать для неё роль условия или значения.

## 3. Укоренённое структурное свидетельство

Пучковая форма представляется укоренённой связевой структурой.

Технически различаются:

```text
kind tag
rooted children
occurrence path
resolved Link
```

Но:

```text
path
!= semantic Link identity
```

Координата пути нужна только для происхождения и проверки конкретного вхождения.

Чужой `handle`, неверный словарь структурных тегов, неправильная арность или циклическое некорректное свидетельство отклоняются без частичного результата.

## 4. Сначала разрешаются вхождения

Каждое исходное вхождение разрешается отдельно.

Понятийно:

```text
occurrence
-> validate
-> resolve canonical Link
-> retain provenance
-> extensional deduplication
```

Свидетельство разрешённого вхождения можно записать как:

```text
(path, Link)
```

Два разных пути могут разрешиться в одну и ту же смысловую Связь. Это не создаёт второй смысловой экземпляр.

## 5. Экстенсиональное значение пучка

После разрешения `ValueBundle` задаётся совокупностью различных канонических Связей.

Поэтому в метанотации:

```text
{a,b} = {b,a}
{a,a} = {a}
```

Порядок и повтор вхождений не входят в экстенсиональное равенство.

Происхождение хранится отдельно:

```text
BundleValue.links
BundleValue.occurrences
```

Первое задаёт экстенсиональное значение, второе — исходные разрешённые вхождения.

## 6. Одноэлементный пучок не равен Связи

Автоматическое приведение:

```text
{a} = a
```

не принимается.

Производный слой различает:

```text
LinkValue
BundleValue
```

Это различие роли значения не создаёт второго онтологического вида: элементы обоих случаев остаются Связями.

## 7. Текущие ограничения вложенности

Текущая поверхность не разрешает вложенный `ValueBundle`:

```text
{{a,b},c}
-> nested-value-bundle-not-supported
```

Пучок значений также не становится автоматически скалярным операндом для операций, ожидающих одну Связь.

Пучковое значение в правой части определения остаётся вне текущей принятой поверхности:

```text
bundle-valued-definition-deferred
```

Эти ограничения не являются утверждением о невозможности таких производных теорий вообще; они задают только текущую поверхность v0.13.

## 8. Пустой разрешённый ValueBundle

Нужно отличать пустую **форму** с ещё не выбранной ролью от уже разрешённого пустого `ValueBundle`.

После того как роль значения установлена, допустим:

```text
ValueBundle{}
```

с нулём Связей.

В обычном экстенсиональном смысле это пустой пучок.

В позиции **полюса пучкового поиска** он имеет специальную роль отсутствия ограничения на этот полюс.

Это контекстное правило поиска, а не глобальный смысл `{}`.

## 9. Раскрытие пучкового запроса

Пучковый запрос читает только уже существующие Связи.

Примеры:

```text
a{b,c}
-> существующие a⟼b и a⟼c

{a,b}c
-> существующие a⟼c и b⟼c

{a,b}{c,d}
-> существующие пары декартова произведения
```

Пустой разрешённый `ValueBundle` в полюсе запроса означает отсутствие ограничения:

```text
a{}
-> все существующие исходящие Связи из a

{}b
-> все существующие входящие Связи в b

{}{}
-> все существующие Связи выбранной перечислимой апамяти
```

Пучковая поверхность применяется только когда хотя бы один полюс является пучком. Обычный запрос `Link-to-Link` не переопределяется этим слоем.

## 10. Поиск не материализует

Пучковое раскрытие является чтением.

```text
query
!=
materialize
```

Если требуемой пары нет:

```text
missing pair
-> absent result
```

Запрещено:

```text
missing pair
-> synthetic Link
```

Число Связей в памяти не должно меняться из-за разрешения пучка или пучкового запроса.

## 11. Пустой пучок не означает удаление

Специальный wildcard-смысл пустого `ValueBundle` существует только в полюсе пучкового поиска.

Из него не следуют:

```text
{} -> DELETE
{} -> global ANY in every context
{} -> ontological EMPTY entity
```

Удаление, если оно определяется производным слоем, требует отдельного явного смыслового правила.

## 12. Роли `ConstraintBundle` и `ValueBundle` не смешиваются автоматически

Пучок условий и пучок значений имеют разные роли.

Если структурное содержимое одновременно требует обе роли:

```text
mixed constraint/value evidence
```

свидетельство отклоняется.

Ожидаемая роль окружающего выражения может уточнять неоднозначную пустую форму, но не может превращать явно value-содержимое в пучок условий или наоборот.

## 13. Совместное использование не создаёт копий

Одна и та же связевая форма может участвовать в нескольких пучках и нескольких позициях одного пучка.

```text
shared Link
!= duplicated semantic Link
```

Экстенсиональная дедупликация выполняется после разрешения вхождений, поэтому происхождение не теряется.

## 14. Инженерная поверхность

Текущая эталонная реализация использует:

```text
ValueBundleVocabulary
BundleElaboration
ResolvedOccurrence
LinkValue
BundleValue
```

и читающие операции:

```text
elaborateBundleRoles
resolveFlatBundle
valuesEqual
expandResolvedBundleQuery
```

Эти имена являются реализационной поверхностью, а не новой онтологией.

Индексы `find/outgoing/incoming/allLinks` могут ускорять конкретный вид пучкового запроса, но не меняют его смысл.

## 15. Что пучок связей не утверждает

Из текущей поверхности не следуют:

```text
bundle -> primitive set ontology
{a} = a
occurrence path -> Link identity
empty syntax -> intrinsic role
empty ValueBundle -> global wildcard everywhere
query -> materialize
missing pair -> synthetic Link
nested ValueBundle -> accepted
bundle-valued definition -> accepted
{ } -> internal F1 operators
```

## Итог

Пучок связей v0.13 — производный read-only слой над уже различёнными Связями:

```text
структурное свидетельство
-> роль
-> разрешение каждого вхождения
-> канонические Связи
-> отдельное происхождение
-> экстенсиональное пучковое значение
-> read-only query expansion
```

Он не изменяет фундамент МТС и не добавляет второй вид существующего.
